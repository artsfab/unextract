# 文書メンテナンス原則

本書は文書メンテナンス原則の唯一の正本である。文書の新設・分割・統合・廃止、責務変更、情報の配置・保存判断を行うときに読む。通常の仕様変更を既存の担当節へ反映する場合や、誤字・既存リンクの修正だけなら、毎回の通読は不要である。

文書は現在と将来の変更を安全に行うために維持する。「この情報を削除すると、半年後の開発者・Coding Agentが困るか」を残す判断基準とする。保存する価値がある情報でも、毎回読む必要があるとは限らない。

<a id="owners"></a>
## 1. 情報の責務に合う正本を更新する

新しい情報は、[文書の入口](README.md)で担当を確認し、既存の正本へ書く。動作・制約は仕様、配置・依存は実装案内、非自明な判断理由・技術的根拠は理由の文書、検証方法・回帰の意図はテストの文書、未確認・未解決事項は課題の一覧が担う。利用者向けの説明とエージェントの作業規則も区別する。

ひとつの変更に含まれる情報でも、責務が異なれば書き先を分ける。作業ごとの報告書に現行知識を閉じ込めない。担当が不明なら、先に既存の責務を明確にする。

<a id="new-document"></a>
## 2. 新規文書は独立した読む目的がある場合に限る

原則として既存文書の該当節を更新する。機能・調査・作業が発生したことだけを理由にファイルや文書の種類を増やさない。新設・分割するのは、既存の責務に収まらない、または独立して読む領域を分けることで不要なコンテキストを明確に減らせる場合とする。

新設時は役割・読む条件・既存文書との境界を示し、入口を更新する。移した本文を旧側にも残さない。ファイル数の最小化や固定化を目的にせず、細分化による参照の往復と、統合による不要な読書の両方を避ける。

<a id="single-source"></a>
## 3. 同じ規則は一度だけ定義する

数値、条件、手順、例外、表示文言は担当正本に集約し、他の文書からは該当節へ直接参照する。理由の文書に手順を、テストの文書に仕様全文を再掲しない。

利用者向け要約、コードの局所的な説明、テストの具体的な期待値は、それぞれの目的に必要な範囲で記載してよい。ただし独立した仕様にせず、重要な例外を省いて意味を変えない。安全上の注意は必要な場所で短く示し、詳細の正本へ直接つなぐ。本書の詳細原則も入口やエージェント向け指示へ複製しない。

<a id="distillation"></a>
## 4. 履歴ではなく将来必要な知識を残す

完了した実装計画、migration記録、通常の検証ログ、成功件数、作業日誌はdocsへ蓄積しない。GitやCI等で十分に復元・確認できるものはそちらに任せる。履歴保存のためだけのarchiveや移行台帳を作らない。

調査・PoCから残すのは、判断への影響、非自明な理由、適用条件、既知の限界、未確認範囲、再確認が必要になる条件である。重要な観測には必要最小限の版・環境・方法・根拠を添え、観測・推定・保証を区別する。通常の変更に必要な知識は本文だけで理解できるようにし、詳細な原記録は必要時だけ辿れるようにする。原資料の丸ごと保存を蒸留の代わりにしない。

<a id="uncertainty"></a>
## 5. 未解決一覧は現在の不確実性だけを持つ

OPEN_ISSUESなどの未解決一覧には、影響、分かっている範囲、次に必要な確認・判断を記す。未実施、前提不成立、手順未確立、対象外を区別する。

解決したら、必要な仕様・理由・検証知識を担当正本へ反映し、一覧から項目を削除する。完了一覧へ移して蓄積しない。対象外になった項目も、今後必要な制約や理由を残して除く。未確認事項は古いという理由だけで削除せず、成立したものとしても扱わない。

<a id="synchronization"></a>
## 6. 変更の影響範囲を同期確認する

変更した内容に関係する仕様、理由、実装、テスト要件・期待値、利用者説明、参照元を確認する。担当節と参照検索から範囲を決め、無関係な文書の通読や更新を要求しない。動作変更なら理由・検証・利用者説明まで、移動・改題・廃止なら参照元と入口まで確認する。根拠だけの追加では、その根拠に依存する説明を確認する。

資料間の食い違いは、明示された決定・規定と実装・テストを照合する。コードが動くことや更新日の新しさだけで正しさを決めない。新しい製品判断が必要なら推測でそろえず、影響と必要な判断を未解決事項として明示する。文書整理を理由に製品動作やテストの期待値を変更しない。

<a id="reading-paths"></a>
## 7. 必要なときだけ読める状態を保ち、不要な情報は減らす

入口には変更対象から担当文書・節への直接経路を置き、詳細資料を読む条件を示す。各文書は役割と読む場面を短く示し、関連リンクをすべて必読にしない。安全上重要な理由・制約・未確認事項は、関係する変更の経路から見落とさず辿れるようにする。

古い本文に訂正を積み重ねず、現行の説明へ書き直す。責務の混在、重複、完了記録、長い参照連鎖、無関係な大節が増えたら整理する。まず削除・統合・蒸留を行い、それでも独立した読む目的が残る場合に分割する。価値を失った文書は参照元と入口を更新して廃止する。行数や経過時間だけで機械的に削らず、必要な安全知識を失わない。この原則自身にも同じ基準を適用し、細かな運用手順や変更履歴を追記し続けない。
