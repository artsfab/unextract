# unextract MVP 決定事項と判断理由

仕様の正は [`SPEC.md`](SPEC.md)。本書は判断の理由だけを記録する。ここに仕様の別版を置かない。実測の根拠は [`PLAN_VALIDATION.md`](PLAN_VALIDATION.md)。

判断の優先順位: 1. 利用者のファイルを誤削除しない 2. 不明・判定不能なら削除しない 3. 実装を必要以上に複雑にしない 4. Windows/.NET の公開された安定 API を使う 5. ZIP の完全検証ツールを作らない 6. 性能・互換性 7. 利便性。

## 全体方針

- 現在の全バイト一致だけを削除の根拠とし、展開来歴は判定しない。
- Windows 11 の NTFS target に限定し、ZIP は .NET 10 (LTS) の `ZipArchive` で読む。独自の ZIP 構造パーサは作らない。ZIP64/DD/SFX は特別扱いしない。
- Recycle Bin、ディレクトリ削除、クラウド対応、JSON、ログ、詳細 exit code、Ctrl+C 専用処理、benchmark は MVP から外す。
- 削除前の ZIP 異常・安全確認不能・対象読取不能 (共有違反を含む) は全体 FATAL。削除フェーズでは、同一性に疑義のない通常の OS 拒否だけを `DELETE_FAILED` として続行し、それ以外は停止する。

## DEC-1. 削除フロー: 初回比較後に閉じ、削除直前に開き直して全バイト再比較する (製品挙動として確定)

流れは「初回の全バイト比較 → 結果表示 → 利用者の確認 → 再オープン → 同一性の再検証 → 2回目の全バイト比較 → 同じハンドルから削除」。

- 比較用ハンドルを削除まで保持する旧案は採らない。数万件のハンドルを確認待ちの間保持すると、他アプリの操作を共有違反で長時間妨げ、ハンドル資源も消費する。
- 再オープン後に全バイト再比較を行う。比較から再オープンまでの間に File ID・サイズ・更新日時を保ったまま内容だけが変わる競合は、メタデータの再検証だけでは検出できないが、再比較なら検出できる。代償は削除対象の I/O が約2倍になることで、README に記載する。
- 削除用ハンドルは `GENERIC_READ | DELETE | FILE_READ_ATTRIBUTES | SYNCHRONIZE`、共有 `FILE_SHARE_READ` のみ。再比較の読み取りに `GENERIC_READ` が必要。`FILE_SHARE_WRITE` と `FILE_SHARE_DELETE` を含めないことで、再比較から削除までの間の書き込み・改名・削除を他者に許さない。
- パスを使うのはオープンの1回だけで、再検証・再比較・削除は同じハンドルで行う。再検証した個体と削除する個体が一致する。
- `OpenFileById` は採らない。パスを使わずに開けるが、利用者が target 外へ移動したファイルも開いてしまい、結局最終パスの確認が必要になる。
- 親ディレクトリの同一性は、同じハンドルへの `FSCTL_READ_FILE_USN_DATA` で得る親 File ID で確認する。親を別にパスで開くと、ファイルのオープンとの間で別の名前解決が入るため避けた。target ルートは `FILE_LIST_DIRECTORY` 付き・DELETE 非共有で保持し、改名・削除を防ぐ (`FILE_READ_ATTRIBUTES` だけのハンドルは共有モードの判定に参加しないことを実測した)。
- 削除の API は `SetFileInformationByHandle(FileDispositionInfoEx)`、flags は `DELETE | POSIX_SEMANTICS` (0x3) に確定した。理由は DEC-10。`IGNORE_READONLY_ATTRIBUTE` は使わず、read-only を最後の防壁として残す。
- パスを再解決するパスベースの削除は使わない。再検証した同じファイルオブジェクトを削除するという安全性を失うためである。
- 削除用ハンドルを開いている間も、別プロセスから ADS 作成・属性変更・hardlink 追加ができる (予備実測 V6 の後、SPEC §13 の PoC 6 で別プロセスでも確認)。2回目の比較が長くなり得るため、削除の直前に最終確認を入れて窓を狭め、残りを限界として記載した。PoC 6 では、いずれの変更も最終確認で検出できた。

## DEC-2. `DELETE_FAILED` と停止の境界 (製品挙動として確定)

- 再比較・再検証での不一致や異常は、初回に読めた・一致したものが変わったことを意味し想定外なので、`DELETE_FAILED` で続行せず停止する。
- 削除用オープンでの共有違反・アクセス拒否は、使用中や権限不足という通常の拒否の場合と、ディレクトリへの置換・削除保留中・別の個体の場合が同じコードになる。そこで、オープン失敗時にだけ `FILE_READ_ATTRIBUTES` のみの識別確認ハンドル (共有モードの判定に参加しない) でスナップショットと照合し、識別確認の時点でスナップショットと一致する通常ファイルに見えるときだけ `DELETE_FAILED` とする。識別確認は拒否されたオープンとは別のオープンなので、拒否された個体と同じであることも、拒否の理由も保証しない。それでも採るのは、一致した場合の結果が「削除せずに残して続行」だけで誤削除につながらず、不一致・失敗なら停止に倒せるからである。識別確認のハンドルでは削除しない。
- 対象消失、親の消失・差し替え、reparse 化は同一性を確認できない状態なので停止する。
- 削除指示 (`SetFileInformationByHandle`) の失敗は、再検証と最終確認の後に状態が変わったことを意味するため、エラーの種類を問わず停止する (DEC-12)。
- 対応表に無いエラーは停止する。未知のエラーを `DELETE_FAILED` と推測して続行しない。

## DEC-3. CRC-32 は必須のまま維持し、偶発的な不整合の検出と位置づける

- 期待 CRC は公開プロパティ `ZipArchiveEntry.Crc32` で得られる。導入は .NET Core 2.1 と .NET Standard 2.1 で、採用する .NET 10 に含まれる (V2a で参照アセンブリとランタイムを確認)。実測値は公式パッケージ `System.IO.Hashing` で計算する。独自パーサも reflection も不要で、追加コストは小さい。
- 採用版のランタイムは CRC 不一致を検出しない。
- CRC は ZIP の作成者が宣言値や実データと一緒に書き換えられるため、敵対的に作られた ZIP への防御にはならない。CRC で守れるのは、偶発的な破損、切り詰め、Central Directory の記録と実データの食い違い (宣言サイズが実データと合わず `ZipArchive` の出力が途中で切られる場合など) の検出である。こうした食い違いのある ZIP を FATAL にして、壊れた ZIP を基準に削除しないための補助検査と位置づける。
- 削除の根拠は全バイト一致であり、CRC ではない。
- 宣言サイズ超過の即中断、終端までのバイト数と宣言サイズの一致、CRC の一致の3つの検査は、初回比較と2回目の比較の両方で行う。
- Local Header の CRC との照合は独自パーサが必要になるため行わない。

## DEC-4. `ZipArchive` の保証の穴を unextract 側で埋める範囲

- ランタイムが検出しない異常のうち、公開 API と読み出したバイト列だけで検出できるもの (CRC、バイト数の不足・超過、暗号化フラグ) は unextract が検出する。
- ZIP 構造の照合 (LH と CD、DD、圧縮領域の重なり) は行わない。削除の根拠は読み出したバイト列と target の一致であり、構造の健全性証明は目的外である。
- 内容比較候補は一致・不一致にかかわらず終端まで読む。不一致の位置で MODIFIED と FATAL が入れ替わる非決定性をなくすため。
- 暗号化・未対応方式・破損の検査は内容比較候補に限る。`MISSING` とサイズ不一致の内容は読まないという方針に合わせる。

## DEC-5. 特殊属性は許可リスト方式

- 許可: ARCHIVE、NORMAL、HIDDEN、NOT_CONTENT_INDEXED、COMPRESSED、SPARSE_FILE、ENCRYPTED。データがローカルにあり、通常の読み取りで内容を比較でき、削除に特別な意味を持たない属性に限る。
- HIDDEN は許可する。表示だけの属性で格納や読み取りの意味を変えず、ZIP 展開ツールが復元することもある。全パスを削除前に表示する。SYSTEM と組み合わされたもの (desktop.ini、Thumbs.db など) は SYSTEM でスキップされる。
- スキップ: READONLY (削除からの明示的な保護)、SYSTEM、TEMPORARY (アプリの管理対象)、REPARSE_POINT・OFFLINE・RECALL 系・PINNED・UNPINNED (データがローカルにない、または読み取りで取得が起きる)、DEVICE、VIRTUAL、INTEGRITY_STREAM、NO_SCRUB_DATA、STRICTLY_SEQUENTIAL。
- 未定義・将来のビットもスキップする。属性値の取得自体は成功しているので FATAL ではなく SKIPPED とする。

## DEC-6. resource limits

- 宣言展開量 (1エントリ 16 GiB、合計 64 GiB) は `MISSING` を含む全エントリに適用する。target に触れる前に、target の状態と無関係に受理を決められること、改ざんされた宣言値による桁あふれを早期に拒否できること、MVP の受理範囲を明確にすることが理由である。展開しないデータが危険だという理由ではない。
- 実際の読み取り量は、読むたびに `Length` を超えた時点で中断して強制する。累計の実測上限も初回分類で確認する。再比較は初回に読んだエントリを読み直すだけである。
- `ZipArchive` が開く時点の Central Directory のメモリ割り当ては、独自パーサなしに事前制限できないため限界として記載する。メモリ不足は削除前の異常終了になり、誤削除にはつながらない。

## DEC-7. 名前とパス

- `entryNameEncoding` に CP437 を指定する。未指定ではフラグなしの名前が UTF-8 として扱われる。
- 不正 UTF-8 は例外にならず U+FFFD に置換されるため、復号名の U+FFFD を FATAL とする。生バイトが公開 API で得られないための安全側の制限である。
- ZIP の特殊エントリは `ExternalAttributes` の上位16ビットの種別と DOS 属性で判定する。作成元 OS が公開されないため保守的な規則にした。
- ZIP の特殊エントリの種別は、エントリの種類と組み合わせて判定する。ファイルエントリで種別 `0x4000`、ディレクトリエントリで種別 `0x8000` は、名前と属性が矛盾しどちらとして扱うべきか決められないため全体 FATAL とする。
- target 側の実名確認は、検証済みのディレクトリハンドルから `GetFileInformationByHandleEx(FileIdExtdDirectoryInfo)` で項目を列挙し、ZIP の成分名と序数比較する方式にした (SPEC §6.2)。`FindFirstFile` 系による1件ずつの検索と比べた理由は次のとおり。
  - 8.3 名: 列挙は8.3 名を項目として返さず、ロング名だけを返す (V7 で実測)。序数比較で一致しないので8.3 名だけの一致は自然に `MISSING` になる。`FindFirstFile` は8.3 名でも一致して項目を返すため、返った `cFileName` との比較を別に行う必要がある。
  - 失敗の扱い: 列挙はディレクトリハンドルに対する1つの API で、成功・終端 (`ERROR_NO_MORE_FILES`)・それ以外の失敗が区別でき、失敗をそのまま FATAL にできる。`FindFirstFile` は「見つからない」と「パスの途中が無い」「アクセス拒否」が別々のエラーになり、`MISSING` と FATAL の振り分けをエラーコードに依存する。
  - 一貫性: 親成分も最終成分も「親ディレクトリの列挙項目」から属性・reparse tag・128 ビット File ID を同時に得られ、§6.1 の表 (reparse の判定を含む) と手順2を同じ手段で処理できる。列挙するディレクトリ自体もハンドルで File ID・最終パスを検証してから使うため、ハンドル中心の設計 (削除フェーズ) とそろう。`FindFirstFile` はパス指定で毎回パス全体を解決し、128 ビット File ID を返さない。
  - 性能: 列挙は ZIP が触れるディレクトリごとに1回で、総量はそれらのディレクトリの項目数の合計に比例する。巨大なディレクトリに少数のエントリが対応する場合は `FindFirstFile` より遅くなり得るが、MVP では正確さと一貫性を優先した。問題になれば、同じ規則 (ロング名の序数比較、失敗は FATAL) を満たす検索方式への置き換えを検討する。
  - 「ZIP にない target ファイルは無視する」原則との関係: 列挙は名前を走査するが、照合に使うのは ZIP の成分名の集合だけで、照合しなかった名前は保持・表示・集計・分類しない。原則の趣旨 (無関係なファイルに作用しない、利用者に見せない) は保たれる。
- target 側の親成分は SPEC §6.1 の表で分類する。通常ファイルは、種類が判定でき対応するファイルが存在し得ないため `MISSING` (以前の FATAL から変更)。reparse point はファイル・ディレクトリを問わず `SKIPPED_SPECIAL_FILE` とする。種類は判定できているので FATAL にする理由がなく、target 内に junction が1つあるだけで全体を止めるのは利便性を大きく損なう。reparse 先はたどらず、その下は読まないので安全性は変わらない。種類を判定できないものだけを FATAL にする。

## DEC-8. dry-run

`--dry-run` は確認・削除フェーズに入る前まで (初回分類と結果表示) 通常実行と同じ処理を行う。検証を省略する dry-run は、通常実行で FATAL になる ZIP を dry-run で正常に見せてしまうため採らない。一方、削除直前再検証は削除のための確認なので dry-run では行わない。そのため初回分類後の外部変更で通常実行だけが停止し得るが、これは意図した差である。

## DEC-9. 比較中の共有違反は全体 FATAL

初回比較で対象を開けない (共有違反を含む) 場合は、内容を確認できないため全体 FATAL とする。1ファイルの問題で全体が止まるが、`MISSING` や `MODIFIED` と推測すると誤った分類を表示することになるため、判定不能として扱う。利用者は対象を閉じて再実行する。README に明記する。

## DEC-10. disposition flags は `DELETE | POSIX_SEMANTICS` (0x3) に確定

根拠は SPEC §13 の PoC 1〜3、5 (`PLAN_VALIDATION.md` の「削除 PoC」)。

- `FILE_DISPOSITION_FLAG_DELETE` (0x1) 単独でも削除は成立する (PoC 2)。POSIX semantics は成立の条件ではない。
- ただし、`FILE_SHARE_DELETE` 付きで対象を開いている他のハンドル (インデクサ・バックアップ相当の読み取り) があると、0x1 では unextract がハンドルを閉じた後も名前が削除保留のまま残り、相手が閉じるまで、その名前のオープンも同名の新規作成も 5 で失敗する (PoC 1〜3、5)。利用者からは「削除したはずのファイルが残っていて開けない」状態に見える。
- 0x3 では、その場合でも unextract のクローズで名前が消える。相手のハンドルは読み続けられ、その最終パスは `$Extend\$Deleted` 配下になるが、unextract は既にハンドルを閉じており、判断には影響しない。
- 0x3 でも 0x1 と同じく read-only の対象では指示が失敗する (`IGNORE_READONLY_ATTRIBUTE` を含めないため)。安全側の性質は変わらない。

## DEC-11. 削除の成立は `DeletePending` で判定する

- 判定は、削除指示の後、同じハンドルで `FILE_STANDARD_INFO.DeletePending == true` を確認して行う (PoC 3)。
- `SetFileInformationByHandle(FileDispositionInfoEx)` の成功だけでは判定しない。`DELETE` ビットを含まない flags (0x0、0x2、0x8) でも成功を返し、何も削除しないことを実測した (PoC 1〜3 の参考測定)。実装の誤りで flags が崩れた場合にも、成立確認で停止できる。
- 削除の指示が失敗した場合 (read-only) は `DeletePending` が false のままであることを実測した。
- 指示後に `NumberOfLinks` が 0 と報告されることも観測したが、公式資料で裏付けを確認していないため判定条件にしない。

## DEC-12. 段階5 (削除指示) の失敗は種類を問わず停止のまま

- 段階5で実測した失敗は read-only による 5 (`ERROR_ACCESS_DENIED`) で、`DeletePending` は false のままだった (PoC 1〜3、6)。
- 5 は段階1でも ACL による拒否、対象のディレクトリ化・ディレクトリ junction 化、削除保留中に共通であり、コードだけでは原因を識別できない (PoC 7)。段階5でも、5 から原因を識別する手段は無い。
- 原因を識別できない失敗を `DELETE_FAILED` で続行すると、再検証の前提が崩れた状態で次へ進むことになるため、停止を維持する。利用者向けには、そのファイルは残り以後の削除が停止すること、それまでに削除したファイルは戻らないことを README に記す。

### 対象の DELETE だけを ACL で拒否し、親が DELETE_CHILD を許可している場合 (PoC 7 #4、`PLAN_TESTS.md` D22)

- **方針 (案 A を採用し、E-2 の実測で確定): Windows の通常の ACL の挙動として受け入れる。** 親が DELETE_CHILD を許可していると、削除用オープンは成功する (PoC 7 #4)。
- 理由: 対象は全バイト一致を2回 (初回比較と削除直前の再比較) 確認したファイルであり、親ディレクトリの DELETE_CHILD による削除は、利用者が親ディレクトリに対して持つ権限の範囲内である。そのため unextract は個別ファイルの ACL を比較対象にしない。
- E-2 の実測 (`PLAN_VALIDATION.md` の「E-2 実測」、`PLAN_TESTS.md` D22) で、拒否した時点によって次の2通りになることを確認した。どちらも誤削除ではなく、SPEC の変更は不要である。
  - **初回分類の前に拒否した場合**: 段階1 (削除用オープン)・段階2 (同一性の再検証)・段階5 (削除の指示) がすべて成功し、同じハンドルの `DeletePending` が true になり、対象は削除される。これを Windows の通常の挙動として受け入れる。
  - **確認待ち中に拒否した場合**: ACL の変更で対象の `ChangeTime` が変わるため、段階2の再検証で不一致になり停止する。対象は残り、以後は未処理になる。
- 確認待ち中に親ディレクトリの ACL を変更すると、子の ACL も書き直され、対象と兄弟ファイルの `ChangeTime` が変わるため、削除直前再検証で停止し得る (E-2 の実測。`PLAN_VALIDATION.md` の「E-2 実測」)。
- PoC 7 #4 の「段階2の比較も差なし」は、PoC で比較した項目 (File ID、親 File ID、最終パス、`Directory`、`DeletePending`) に限った結果だった。`ChangeTime` を含む SPEC §8.3 の 2 の全項目を比べると、確認待ち中の ACL の変更は検出される。
- 段階5が失敗した場合 (今回の実測では起きていない) は、SPEC §8.4 (と本項の前半) のとおり停止する。
- 不採用 (案 B): ファイルの ACL をスナップショットの比較対象に加える案は採らない。ACL は内容の一致にも個体の同一性にも関係せず、上の場合に削除を認めているのは OS の権限判定そのものである。加えると、確認待ちの間に変わり得る比較項目が増えて停止の原因が増え、セキュリティ記述子の取得と比較 (継承 ACE の扱いを含む) の実装が加わるが、誤削除の防止には寄与しない (判断の優先順位 3)。

## DEC-13. 同一性の再検証では親 File ID と最終パスの両方を必須とする

実装で片方を省く最適化をしない。根拠は SPEC §13 の PoC 7・8。

- 親ディレクトリを同名の別ディレクトリに差し替え、同じファイルを移して入れた場合、File ID と最終パスは一致し、**親 File ID だけ**が不一致になった。
- 途中のディレクトリを junction に差し替えた場合と、途中のディレクトリを大文字小文字だけ改名した場合は、削除用オープンが成功し、**最終パスだけ**が不一致になった (親 File ID は一致)。
- どちらか一方を省くと、これらの差し替えの一方を見逃す。

## DEC-14. 列挙中の変更: 重複は最初の1件、見落としは `MISSING`

- 列挙中に改名された項目は、1回の列挙で見落とされることも、旧名と新名の両方で返ることもあった (PoC 8 (e)、2,347回の列挙で各426回)。名前が変わらない項目の見落としは観測しなかった。
- 同じ名前が複数回返った場合は最初の1件を採用する。採用した項目が実体と食い違っていても、比較用オープンでの File ID・最終パスの確認 (SPEC §6.1 の手順3・4) と、削除フェーズの再検証で検出されるため、どちらを採用しても安全性は変わらない。規則を固定して結果を決定的にするために最初の1件とした。
- 見落とされた名前は `MISSING` とする。内容を読まず削除もしないので、見落としが誤削除につながることはない。
- 列挙で見つけた名前が直後に改名された場合に比較用オープンで FATAL になるのは推定で、この組み合わせは実測していない。

## DEC-15. SDK は `global.json` で 10.0.401 に固定し、`rollForward` は `latestPatch`

- 技術検証 (V1〜V7) と削除 PoC (SPEC §13) は .NET SDK 10.0.401 / ランタイム Microsoft.NETCore.App 10.0.12 で行った (`PLAN_VALIDATION.md` の「実施環境」)。実測した `ZipArchive` の挙動を前提に SPEC を決めたため、ビルドに使う SDK をその版にそろえる。
- `latestPatch` は同じ機能帯 (10.0.4xx) のパッチ更新だけを許す。パッチ更新で `ZipArchive` の挙動が変わっても SPEC §5.2 の結果が変わらないことは、Z・C 系テストで継続的に確認する (`PLAN.md` §5)。

## DEC-16. 終了コードは成功 0、エラー 1、利用者による中止 2

- SPEC §2 の3区分を、プロセスの終了コードに 成功 = 0、エラー = 1、利用者による中止 = 2 と対応付ける。対応は Core の `ExitCodes` の1か所で定義する。
- 0 と 1 は Windows のコマンドで一般的な「成功」「失敗」の値で、スクリプトから `if errorlevel 1` 等でそのまま判定できる。中止を 2 として失敗と分けるのは、利用者が `n`・空入力・EOF で中止した場合や非対話で `--yes` が無い場合に、削除をしていないことは同じでも、検証の失敗ではないことを呼び出し側が区別できるようにするためである。
- これ以上の細分化 (FATAL の種別ごとのコードなど) はしない (SPEC §2、全体方針の「詳細 exit code」を外す判断)。

## DEC-17. UNC パスの target は拒否する (共有ルートとその配下)

- SPEC §2 の拒否対象を「UNC 共有ルート」から「UNC パス (共有ルートとその配下。最終パスが `\\?\UNC\` で始まるもの)」に広げ、正式な仕様とする。
- 理由: UNC 上の target では、サーバー側のファイルシステムが報告するファイルシステム名 (NTFS と報告されても実体は異なり得る)、File ID の安定性と一意性、共有モードとハンドルの意味論を、クライアントから保証できない。unextract の安全性は NTFS 上の File ID・最終パス・共有モードに依存するため (SPEC §6.1、§8.1)、MVP の対象外とする。
- 判定は保持用ハンドルの最終パスで行う (SPEC §8.1)。利用者が入力した文字列が UNC に見えるかどうかでは判定しない (ドライブ文字に割り当てたネットワークドライブも、最終パスが `\\?\UNC\` になれば拒否される)。

## DEC-18. `DELETE_FAILED` だけがあり停止がなかった場合の終了状態はエラー (1) とする方針

- 削除フェーズで `DELETE_FAILED` が1件以上あり、停止はなかった場合、終了状態はエラー (1) とする方針である。削除しなかった検証済みファイルが残っており、要求された処理を完了していないため、成功 (0) として報告しない。
- 段階 E-2 で SPEC §2 (終了状態) と §10 (終了時の要約) に反映した。
