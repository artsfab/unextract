# unextract MVP 決定事項と判断理由

仕様の正は [`SPEC.md`](SPEC.md)。本書は判断の理由だけを記録する。ここに仕様の別版を置かない。実測の根拠は [`PLAN_VALIDATION.md`](PLAN_VALIDATION.md)。

判断の優先順位: 1. 利用者のファイルを誤削除しない 2. 不明・判定不能なら削除しない 3. 実装を必要以上に複雑にしない 4. Windows/.NET の公開された安定 API を使う 5. ZIP の完全検証ツールを作らない 6. 性能・互換性 7. 利便性。

## 全体方針

- 現在の全バイト一致だけを削除の根拠とし、展開来歴は判定しない。
- Windows 11 の NTFS target に限定し、ZIP は .NET 10 (LTS) の `ZipArchive` で読む。独自の ZIP 構造パーサは作らない。ZIP64/DD/SFX は特別扱いしない。
- Recycle Bin、ディレクトリ削除、クラウド対応、JSON、ログ、詳細 exit code、Ctrl+C 専用処理、benchmark は MVP から外す。
- 削除前の ZIP 異常・安全確認不能・対象読取不能 (共有違反を含む) は全体 FATAL。削除フェーズでは、同一性に疑義のない通常の OS 拒否だけを `DELETE_FAILED` として続行し、それ以外は停止する。(2026-10-03 改訂: この項は旧方式の記述。現行は、Prepare の異常は両操作で FATAL・削除0件、`analyze` の判定不能は FATAL、`delete` のエントリ処理中の判定不能は STOP (DEC-26)、`delete` の同一性に疑義のない OS 拒否は `DELETE_FAILED` で続行 (DEC-27)。)

## DEC-1. 削除フロー: 初回比較後に閉じ、削除直前に開き直して全バイト再比較する (製品挙動として確定)

> **2026-10-03 改訂: DEC-25 で置き換え。** 再オープンと2回目の全バイト比較は廃止した。数万件のハンドルを保持しない点、削除用ハンドルの構成、パスを使うのはオープンの1回だけ、`OpenFileById` を採らない点、親 File ID の取得方法、flags 0x3、パスベースの削除をしない点、最終確認で窓を狭める点は DEC-25 でも維持する。以下は旧方式での判断の記録。

流れは「初回の全バイト比較 → 結果表示 → 利用者の確認 → 再オープン → 同一性の再検証 → 2回目の全バイト比較 → 同じハンドルから削除」。

- 比較用ハンドルを削除まで保持する旧案は採らない。数万件のハンドルを確認待ちの間保持すると、他アプリの操作を共有違反で長時間妨げ、ハンドル資源も消費する。
- 再オープン後に全バイト再比較を行う。比較から再オープンまでの間に File ID・サイズ・更新日時を保ったまま内容だけが変わる競合は、メタデータの再検証だけでは検出できないが、再比較なら検出できる。代償は削除対象の I/O が約2倍になることで、README に記載する。
- 削除用ハンドルは `GENERIC_READ | DELETE | FILE_READ_ATTRIBUTES | SYNCHRONIZE`、共有 `FILE_SHARE_READ` のみ。再比較の読み取りに `GENERIC_READ` が必要。`FILE_SHARE_WRITE` と `FILE_SHARE_DELETE` を含めないことで、再比較から削除までの間の書き込み・改名・削除を他者に許さない。
- パスを使うのはオープンの1回だけで、再検証・再比較・削除は同じハンドルで行う。再検証した個体と削除する個体が一致する。
- `OpenFileById` は採らない。パスを使わずに開けるが、利用者が target 外へ移動したファイルも開いてしまい、結局最終パスの確認が必要になる。
- 親ディレクトリの同一性は、同じハンドルへの `FSCTL_READ_FILE_USN_DATA` で得る親 File ID で確認する。親を別にパスで開くと、ファイルのオープンとの間で別の名前解決が入るため避けた。target ルートは `FILE_LIST_DIRECTORY` 付き・DELETE 非共有で保持し、改名・削除を防ぐ (`FILE_READ_ATTRIBUTES` だけのハンドルは共有モードの判定に参加しないことを実測した)。
- 削除の API は `SetFileInformationByHandle(FileDispositionInfoEx)`、flags は `DELETE | POSIX_SEMANTICS` (0x3) に確定した。理由は DEC-10。`IGNORE_READONLY_ATTRIBUTE` は使わず、read-only を最後の防壁として残す。
- パスを再解決するパスベースの削除は使わない。再検証した同じファイルオブジェクトを削除するという安全性を失うためである。
- 削除用ハンドルを開いている間も、別プロセスから ADS 作成・属性変更・hardlink 追加ができる (予備実測 V6 の後、SPEC §13 の PoC 6 で別プロセスでも確認)。2回目の比較が長くなり得るため、削除の直前に最終確認を入れて窓を狭め、残りを限界として記載した。PoC 6 では、いずれの変更も最終確認で検出できた。

## DEC-2. `DELETE_FAILED` と停止の境界 (製品挙動として確定)

> **2026-10-03 改訂**: 考え方 (同一性に疑義のない通常の OS 拒否だけを `DELETE_FAILED`、それ以外と未知のエラーは停止 (STOP)、識別確認は削除しない判定材料) は維持する。識別確認の比較基準はスナップショットから列挙由来の基準 (SPEC §8.2) に変わった。「再比較・再検証での不一致」は、新方式では「オープン直後の照合・最終確認の不一致」(STOP) と「1回だけの比較の不一致」(`MODIFIED` で続行) に分かれる (DEC-25、DEC-27)。

- 再比較・再検証での不一致や異常は、初回に読めた・一致したものが変わったことを意味し想定外なので、`DELETE_FAILED` で続行せず停止する。
- 削除用オープンでの共有違反・アクセス拒否は、使用中や権限不足という通常の拒否の場合と、ディレクトリへの置換・削除保留中・別の個体の場合が同じコードになる。そこで、オープン失敗時にだけ `FILE_READ_ATTRIBUTES` のみの識別確認ハンドル (共有モードの判定に参加しない) でスナップショットと照合し、識別確認の時点でスナップショットと一致する通常ファイルに見えるときだけ `DELETE_FAILED` とする。識別確認は拒否されたオープンとは別のオープンなので、拒否された個体と同じであることも、拒否の理由も保証しない。それでも採るのは、一致した場合の結果が「削除せずに残して続行」だけで誤削除につながらず、不一致・失敗なら停止に倒せるからである。識別確認のハンドルでは削除しない。
- 対象消失、親の消失・差し替え、reparse 化は同一性を確認できない状態なので停止する。
- 削除指示 (`SetFileInformationByHandle`) の失敗は、再検証と最終確認の後に状態が変わったことを意味するため、エラーの種類を問わず停止する (DEC-12)。
- 対応表に無いエラーは停止する。未知のエラーを `DELETE_FAILED` と推測して続行しない。

## DEC-3. CRC-32 は必須のまま維持し、偶発的な不整合の検出と位置づける

- 期待 CRC は公開プロパティ `ZipArchiveEntry.Crc32` で得られる。導入は .NET Core 2.1 と .NET Standard 2.1 で、採用する .NET 10 に含まれる (V2a で参照アセンブリとランタイムを確認)。実測値は公式パッケージ `System.IO.Hashing` で計算する。独自パーサも reflection も不要で、追加コストは小さい。
- 採用版のランタイムは CRC 不一致を検出しない。
- CRC は ZIP の作成者が宣言値や実データと一緒に書き換えられるため、敵対的に作られた ZIP への防御にはならない。CRC で守れるのは、偶発的な破損、切り詰め、Central Directory の記録と実データの食い違い (宣言サイズが実データと合わず `ZipArchive` の出力が途中で切られる場合など) の検出である。こうした食い違いのある ZIP を FATAL にして、壊れた ZIP を基準に削除しないための補助検査と位置づける。
- 削除の根拠は全バイト一致であり、CRC ではない。
- 宣言サイズ超過の即中断、終端までのバイト数と宣言サイズの一致、CRC の一致の3つの検査は、初回比較と2回目の比較の両方で行う。(2026-10-03 改訂: 新方式では `analyze` の比較と `delete` の比較の両方で行う。各実行でエントリの内容を読むのは1回だけ。DEC-25)
- Local Header の CRC との照合は独自パーサが必要になるため行わない。

## DEC-4. `ZipArchive` の保証の穴を unextract 側で埋める範囲

- ランタイムが検出しない異常のうち、公開 API と読み出したバイト列だけで検出できるもの (CRC、バイト数の不足・超過、暗号化フラグ) は unextract が検出する。
- ZIP 構造の照合 (LH と CD、DD、圧縮領域の重なり) は行わない。削除の根拠は読み出したバイト列と target の一致であり、構造の健全性証明は目的外である。
- 内容比較候補は一致・不一致にかかわらず終端まで読む。不一致の位置で MODIFIED と FATAL が入れ替わる非決定性をなくすため。
- 暗号化・未対応方式・破損の検査は内容比較候補に限る。`MISSING` とサイズ不一致の内容は読まないという方針に合わせる。

## DEC-5. 特殊属性は許可リスト方式

- 許可: ARCHIVE、NORMAL、HIDDEN、NOT_CONTENT_INDEXED、COMPRESSED、SPARSE_FILE、ENCRYPTED。データがローカルにあり、通常の読み取りで内容を比較でき、削除に特別な意味を持たない属性に限る。
- HIDDEN は許可する。表示だけの属性で格納や読み取りの意味を変えず、ZIP 展開ツールが復元することもある。全パスを削除前に表示する。SYSTEM と組み合わされたもの (desktop.ini、Thumbs.db など) は SYSTEM でスキップされる。
- スキップ: READONLY (削除からの明示的な保護)、SYSTEM、TEMPORARY (アプリの管理対象)、REPARSE_POINT・OFFLINE・RECALL 系・PINNED・UNPINNED (データがローカルにない、または読み取りで取得が起きる)、DEVICE、VIRTUAL、INTEGRITY_STREAM、NO_SCRUB_DATA、STRICTLY_SEQUENTIAL。
- 未定義・将来のビットもスキップする。属性値の取得自体は成功しているので FATAL ではなく SKIPPED とする。

## DEC-6. resource limits

- 宣言展開量 (1エントリ 16 GiB、合計 64 GiB) は `MISSING` を含む全エントリに適用する。target に触れる前に、target の状態と無関係に受理を決められること、改ざんされた宣言値による桁あふれを早期に拒否できること、MVP の受理範囲を明確にすることが理由である。展開しないデータが危険だという理由ではない。
- 実際の読み取り量は、読むたびに `Length` を超えた時点で中断して強制する。累計の実測上限も初回分類で確認する。再比較は初回に読んだエントリを読み直すだけである。(2026-10-03 改訂: 新方式では実測の累計をその実行の全ての比較で数え、`analyze` で超えれば FATAL、`delete` で超えれば STOP。宣言側の上限は `--entries` を指定しても ZIP 全体に適用する。DEC-25、DEC-30)
- `ZipArchive` が開く時点の Central Directory のメモリ割り当ては、独自パーサなしに事前制限できないため限界として記載する。メモリ不足は削除前の異常終了になり、誤削除にはつながらない。

## DEC-7. 名前とパス

- `entryNameEncoding` に CP437 を指定する。未指定ではフラグなしの名前が UTF-8 として扱われる。
- 不正 UTF-8 は例外にならず U+FFFD に置換されるため、復号名の U+FFFD を FATAL とする。生バイトが公開 API で得られないための安全側の制限である。
- ZIP の特殊エントリは `ExternalAttributes` の上位16ビットの種別と DOS 属性で判定する。作成元 OS が公開されないため保守的な規則にした。
- ZIP の特殊エントリの種別は、エントリの種類と組み合わせて判定する。ファイルエントリで種別 `0x4000`、ディレクトリエントリで種別 `0x8000` は、名前と属性が矛盾しどちらとして扱うべきか決められないため全体 FATAL とする。
- target 側の実名確認は、検証済みのディレクトリハンドルから `GetFileInformationByHandleEx(FileIdExtdDirectoryInfo)` で項目を列挙し、ZIP の成分名と序数比較する方式にした (SPEC §6.2)。`FindFirstFile` 系による1件ずつの検索と比べた理由は次のとおり。
  - 8.3 名: 列挙は8.3 名を項目として返さず、ロング名だけを返す (V7 で実測)。序数比較で一致しないので8.3 名だけの一致は自然に `MISSING` になる。`FindFirstFile` は8.3 名でも一致して項目を返すため、返った `cFileName` との比較を別に行う必要がある。
  - 失敗の扱い: 列挙はディレクトリハンドルに対する1つの API で、成功・終端 (`ERROR_NO_MORE_FILES`)・それ以外の失敗が区別でき、失敗をそのまま FATAL にできる。`FindFirstFile` は「見つからない」と「パスの途中が無い」「アクセス拒否」が別々のエラーになり、`MISSING` と FATAL の振り分けをエラーコードに依存する。
  - 一貫性: 親成分も最終成分も「親ディレクトリの列挙項目」から属性・reparse tag・128 ビット File ID を同時に得られ、§6.1 の表 (reparse の判定を含む) と手順2を同じ手段で処理できる。列挙するディレクトリ自体もハンドルで File ID・最終パスを検証してから使うため、ハンドル中心の設計 (削除フェーズ) とそろう。`FindFirstFile` はパス指定で毎回パス全体を解決し、128 ビット File ID を返さない。
  - 性能: 列挙は ZIP が触れるディレクトリごとに1回で、総量はそれらのディレクトリの項目数の合計に比例する。巨大なディレクトリに少数のエントリが対応する場合は `FindFirstFile` より遅くなり得るが、MVP では正確さと一貫性を優先した。問題になれば、同じ規則 (ロング名の序数比較、失敗は FATAL) を満たす検索方式への置き換えを検討する。
  - 「ZIP にない target ファイルは無視する」原則との関係: 列挙は名前を走査するが、照合に使うのは ZIP の成分名の集合だけで、照合しなかった名前は保持・表示・集計・分類しない。原則の趣旨 (無関係なファイルに作用しない、利用者に見せない) は保たれる。
- target 側の親成分は SPEC §6.1 の表で分類する。通常ファイルは、種類が判定でき対応するファイルが存在し得ないため `MISSING` (以前の FATAL から変更)。reparse point はファイル・ディレクトリを問わず `SKIPPED_SPECIAL_FILE` とする。種類は判定できているので FATAL にする理由がなく、target 内に junction が1つあるだけで全体を止めるのは利便性を大きく損なう。reparse 先はたどらず、その下は読まないので安全性は変わらない。種類を判定できないものだけを FATAL にする。

## DEC-8. dry-run

> **2026-10-03 改訂: DEC-24 と DEC-32 で置き換え。** `--dry-run` は廃止し、非破壊の全件解析は `analyze` が担う。「検証を省略する確認操作は採らない」という考え方は `analyze` に引き継ぐ (`analyze` は Strict で全バイト比較まで行う)。以下は旧方式での判断の記録。

`--dry-run` は確認・削除フェーズに入る前まで (初回分類と結果表示) 通常実行と同じ処理を行う。検証を省略する dry-run は、通常実行で FATAL になる ZIP を dry-run で正常に見せてしまうため採らない。一方、削除直前再検証は削除のための確認なので dry-run では行わない。そのため初回分類後の外部変更で通常実行だけが停止し得るが、これは意図した差である。

## DEC-9. 比較中の共有違反は全体 FATAL

> **2026-10-03 改訂**: この判断は `analyze` に限定して維持する。`delete` の削除用オープンの共有違反・アクセス拒否は DEC-27 に従う (識別確認が一致すれば `DELETE_FAILED` で続行)。

初回比較で対象を開けない (共有違反を含む) 場合は、内容を確認できないため全体 FATAL とする。1ファイルの問題で全体が止まるが、`MISSING` や `MODIFIED` と推測すると誤った分類を表示することになるため、判定不能として扱う。利用者は対象を閉じて再実行する。README に明記する。

## DEC-10. disposition flags は `DELETE | POSIX_SEMANTICS` (0x3) に確定

根拠は SPEC §13 の PoC 1〜3、5 (`PLAN_VALIDATION.md` の「削除 PoC」)。

- `FILE_DISPOSITION_FLAG_DELETE` (0x1) 単独でも削除は成立する (PoC 2)。POSIX semantics は成立の条件ではない。
- ただし、`FILE_SHARE_DELETE` 付きで対象を開いている他のハンドル (インデクサ・バックアップ相当の読み取り) があると、0x1 では unextract がハンドルを閉じた後も名前が削除保留のまま残り、相手が閉じるまで、その名前のオープンも同名の新規作成も 5 で失敗する (PoC 1〜3、5)。利用者からは「削除したはずのファイルが残っていて開けない」状態に見える。
- 0x3 では、その場合でも unextract のクローズで名前が消える。相手のハンドルは読み続けられ、その最終パスは `$Extend\$Deleted` 配下になるが、unextract は既にハンドルを閉じており、判断には影響しない。
- 0x3 でも 0x1 と同じく read-only の対象では指示が失敗する (`IGNORE_READONLY_ATTRIBUTE` を含めないため)。安全側の性質は変わらない。

## DEC-11. 削除の成立は `DeletePending` で判定する

- 判定は、削除指示の後、同じハンドルで `FILE_STANDARD_INFO.DeletePending == true` を確認して行う (PoC 3)。
- `SetFileInformationByHandle(FileDispositionInfoEx)` の成功だけでは判定しない。`DELETE` ビットを含まない flags (0x0、0x2、0x8) でも成功を返し、何も削除しないことを実測した (PoC 1〜3 の参考測定)。実装の誤りで flags が崩れた場合にも、成立確認で停止できる。
- 削除の指示が失敗した場合 (read-only) は `DeletePending` が false のままであることを実測した。
- 指示後に `NumberOfLinks` が 0 と報告されることも観測したが、公式資料で裏付けを確認していないため判定条件にしない。

## DEC-12. 段階5 (削除指示) の失敗は種類を問わず停止のまま

> **2026-10-03 改訂**: 削除指示の失敗を種類を問わず STOP とすること、#4 の ACL を Windows の通常の挙動として受け入れること (案 A、ファイルの ACL を比較対象にしない) は維持する。新方式では「段階5」は SPEC §8.3 の手順8 にあたる。下の理由のうち「全バイト一致を2回確認した」は旧方式の Strict の理由で、新方式の Strict では「削除する同じハンドルで全バイト一致を1回確認した」になる (DEC-25)。時点ごとの結果 (「初回分類の前」「確認待ち中」) は旧方式での実測で、新方式での結果は `PLAN_TESTS.md` S34 で実測する。

- 段階5で実測した失敗は read-only による 5 (`ERROR_ACCESS_DENIED`) で、`DeletePending` は false のままだった (PoC 1〜3、6)。
- 5 は段階1でも ACL による拒否、対象のディレクトリ化・ディレクトリ junction 化、削除保留中に共通であり、コードだけでは原因を識別できない (PoC 7)。段階5でも、5 から原因を識別する手段は無い。
- 原因を識別できない失敗を `DELETE_FAILED` で続行すると、再検証の前提が崩れた状態で次へ進むことになるため、停止を維持する。利用者向けには、そのファイルは残り以後の削除が停止すること、それまでに削除したファイルは戻らないことを README に記す。

### 対象の DELETE だけを ACL で拒否し、親が DELETE_CHILD を許可している場合 (PoC 7 #4、`PLAN_TESTS.md` D22)

- **方針 (案 A を採用し、E-2 の実測で確定): Windows の通常の ACL の挙動として受け入れる。** 親が DELETE_CHILD を許可していると、削除用オープンは成功する (PoC 7 #4)。
- 理由 (Strict): 対象は全バイト一致を2回 (初回比較と削除直前の再比較) 確認したファイルであり、親ディレクトリの DELETE_CHILD による削除は、利用者が親ディレクトリに対して持つ権限の範囲内である。そのため unextract は個別ファイルの ACL を比較対象にしない。
- Fast (SPEC §15) は全バイト比較を行わないため、「全バイト一致を2回確認した」という上の理由は Fast には適用しない。Fast でも本項の扱い (受け入れる。ファイルの ACL を比較対象にしない) は同じで、SPEC §15.4 と DEC-22 に従って維持する (削除用ハンドル、削除方式、`DELETE_FAILED` と停止の境界は両モードで同じ)。本項の判断と既存の挙動は変えない。この ACL の扱い自体を理由として、別のファイルを削除対象とするものではない。
- E-2 の実測 (`PLAN_VALIDATION.md` の「E-2 実測」、`PLAN_TESTS.md` D22) で、拒否した時点によって次の2通りになることを確認した。どちらも誤削除ではなく、SPEC の変更は不要である。
  - **初回分類の前に拒否した場合**: 段階1 (削除用オープン)・段階2 (同一性の再検証)・段階5 (削除の指示) がすべて成功し、同じハンドルの `DeletePending` が true になり、対象は削除される。これを Windows の通常の挙動として受け入れる。
  - **確認待ち中に拒否した場合**: ACL の変更で対象の `ChangeTime` が変わるため、段階2の再検証で不一致になり停止する。対象は残り、以後は未処理になる。
- 確認待ち中に親ディレクトリの ACL を変更すると、子の ACL も書き直され、対象と兄弟ファイルの `ChangeTime` が変わるため、削除直前再検証で停止し得る (E-2 の実測。`PLAN_VALIDATION.md` の「E-2 実測」)。
- PoC 7 #4 の「段階2の比較も差なし」は、PoC で比較した項目 (File ID、親 File ID、最終パス、`Directory`、`DeletePending`) に限った結果だった。`ChangeTime` を含む SPEC §8.3 の 2 の全項目を比べると、確認待ち中の ACL の変更は検出される。
- 段階5が失敗した場合 (今回の実測では起きていない) は、SPEC §8.4 (と本項の前半) のとおり停止する。
- 不採用 (案 B): ファイルの ACL をスナップショットの比較対象に加える案は採らない。ACL は内容の一致にも個体の同一性にも関係せず、上の場合に削除を認めているのは OS の権限判定そのものである。加えると、確認待ちの間に変わり得る比較項目が増えて停止の原因が増え、セキュリティ記述子の取得と比較 (継承 ACE の扱いを含む) の実装が加わるが、誤削除の防止には寄与しない (判断の優先順位 3)。

## DEC-13. 同一性の再検証では親 File ID と最終パスの両方を必須とする

> **2026-10-03 改訂**: 維持する。新方式では、両方を `delete` のオープン直後の照合 (列挙由来の基準と) と最終確認 (M0 と) で比較する (DEC-29)。

実装で片方を省く最適化をしない。根拠は SPEC §13 の PoC 7・8。

- 親ディレクトリを同名の別ディレクトリに差し替え、同じファイルを移して入れた場合、File ID と最終パスは一致し、**親 File ID だけ**が不一致になった。
- 途中のディレクトリを junction に差し替えた場合と、途中のディレクトリを大文字小文字だけ改名した場合は、削除用オープンが成功し、**最終パスだけ**が不一致になった (親 File ID は一致)。
- どちらか一方を省くと、これらの差し替えの一方を見逃す。

## DEC-14. 列挙中の変更: 重複は最初の1件、見落としは `MISSING`

> **2026-10-03 改訂**: 維持する。下の「削除フェーズの再検証」は、新方式では `delete` のオープン直後の照合と最終確認にあたる。列挙結果を逐次削除で再利用する理由は DEC-25。

- 列挙中に改名された項目は、1回の列挙で見落とされることも、旧名と新名の両方で返ることもあった (PoC 8 (e)、2,347回の列挙で各426回)。名前が変わらない項目の見落としは観測しなかった。
- 同じ名前が複数回返った場合は最初の1件を採用する。採用した項目が実体と食い違っていても、比較用オープンでの File ID・最終パスの確認 (SPEC §6.1 の手順3・4) と、削除フェーズの再検証で検出されるため、どちらを採用しても安全性は変わらない。規則を固定して結果を決定的にするために最初の1件とした。
- 見落とされた名前は `MISSING` とする。内容を読まず削除もしないので、見落としが誤削除につながることはない。
- 列挙で見つけた名前が直後に改名された場合に比較用オープンで FATAL になるのは推定で、この組み合わせは実測していない。

## DEC-15. SDK は `global.json` で 10.0.401 に固定し、`rollForward` は `latestPatch`

- 技術検証 (V1〜V7) と削除 PoC (SPEC §13) は .NET SDK 10.0.401 / ランタイム Microsoft.NETCore.App 10.0.12 で行った (`PLAN_VALIDATION.md` の「実施環境」)。実測した `ZipArchive` の挙動を前提に SPEC を決めたため、ビルドに使う SDK をその版にそろえる。
- `latestPatch` は同じ機能帯 (10.0.4xx) のパッチ更新だけを許す。パッチ更新で `ZipArchive` の挙動が変わっても SPEC §5.2 の結果が変わらないことは、Z・C 系テストで継続的に確認する (`PLAN.md` §5)。

## DEC-16. 終了コードは成功 0、エラー 1、利用者による中止 2

- SPEC §2 の3区分を、プロセスの終了コードに 成功 = 0、エラー = 1、利用者による中止 = 2 と対応付ける。対応は Core の `ExitCodes` の1か所で定義する。
- 0 と 1 は Windows のコマンドで一般的な「成功」「失敗」の値で、スクリプトから `if errorlevel 1` 等でそのまま判定できる。中止を 2 として失敗と分けるのは、利用者が `n`・空入力・EOF で中止した場合や非対話で `--yes` が無い場合に、削除をしていないことは同じでも、検証の失敗ではないことを呼び出し側が区別できるようにするためである。
- これ以上の細分化 (FATAL の種別ごとのコードなど) はしない (SPEC §2、全体方針の「詳細 exit code」を外す判断)。

## DEC-17. UNC パスの target は拒否する (共有ルートとその配下)

- SPEC §2 の拒否対象を「UNC 共有ルート」から「UNC パス (共有ルートとその配下。最終パスが `\\?\UNC\` で始まるもの)」に広げ、正式な仕様とする。
- 理由: UNC 上の target では、サーバー側のファイルシステムが報告するファイルシステム名 (NTFS と報告されても実体は異なり得る)、File ID の安定性と一意性、共有モードとハンドルの意味論を、クライアントから保証できない。unextract の安全性は NTFS 上の File ID・最終パス・共有モードに依存するため (SPEC §6.1、§8.1)、MVP の対象外とする。
- 判定は保持用ハンドルの最終パスで行う (SPEC §8.1)。利用者が入力した文字列が UNC に見えるかどうかでは判定しない (ドライブ文字に割り当てたネットワークドライブも、最終パスが `\\?\UNC\` になれば拒否される)。

## DEC-18. `DELETE_FAILED` だけがあり停止がなかった場合の終了状態はエラー (1) とする方針

- 削除フェーズで `DELETE_FAILED` が1件以上あり、停止はなかった場合、終了状態はエラー (1) とする方針である。削除しなかった検証済みファイルが残っており、要求された処理を完了していないため、成功 (0) として報告しない。
- 段階 E-2 で SPEC §2 (終了状態) と §10 (終了時の要約) に反映した。

## DEC-19. Fast モードの位置づけと契約: 内容読み取りステージを実行しないだけの差分とする

> **2026-10-03 改訂**: 位置づけと契約は維持する。下の「処理差は2点」は旧方式のもので、新方式では2回目の比較が無くなり、処理差は内容を読むかどうかの1点になる (DEC-34)。

- Fast は、アーカイブの内容物らしいファイルを、誤判定のリスクを利用者が受け入れたうえで高速に削除するモードとする (SPEC §15)。既定は Strict で、Strict を基準仕様とし、Fast は「Strict から内容読み取りステージを実行しないだけ」の差分として SPEC §15 に集約した。
- Strict との処理差は、SPEC §6.1 の手順7 (初回の内容検証・全バイト比較) と §8.3 の手順3 (2回目の全バイト比較) を実行しないことの2点に限る。
- Fast は内容一致も、対象エントリの復元可能性 (正常に展開できること、暗号化・破損・未対応方式でないこと、宣言内容と実データの整合) も保証しない。同一パス・同一サイズの別内容のファイルは削除され得る。これは判断の優先順位 1 (誤削除しない) を、利用者が明示的に選んだ実行に限って緩めるものである。
- ファイルシステムの安全性 (パス検証、実名解決、reparse、hardlink、ADS、File ID、最終パス、TOCTOU 対策、判定不能なら削除しない、削除直前の同一性・安全性の再検証) は Strict と共通とし、Fast 専用のファイルシステム安全モデル、FATAL 規則、resource limits、終了コードは作らない。Fast の誤判定のリスクは内容に限られ、target 外や特殊な対象への作用のリスクは Strict と変わらない。
- CRC を使う中間モード (宣言 CRC や圧縮データの CRC で内容一致を近似する案) は設けない。主な理由は、Fast を「内容を読まない」という単純な差分として維持するためである。CRC を使えば target か ZIP エントリの内容を読むことになり、モードの差分と検証の組み合わせが増える。加えて、CRC は ZIP の作成者が書き換えられるため、Strict の保証 (読み出した内容と target の全バイト一致) にも届かない (DEC-3 の CRC の位置づけ)。
- Fast 専用のアーカイブ健全性検査・復元可能性検査は設けない。Fast が対象エントリの暗号化・破損・未対応方式を検出しないことは、内容読み取りステージを実行しないことの帰結として扱う。エントリを開いて検査すれば内容を読むことになり、モードの差分が増える。
- 0 byte のエントリに特例は設けず、通常のサイズ一致として扱う。規則を1つに保つため。
- 宣言側の resource limits (SPEC §11 の、エントリ総数から宣言展開量の合計まで) は Fast でも同じに適用する。target に触れる前に target の状態と無関係に受理を決めるという DEC-6 の理由はモードに依存しない。実測展開量の上限は、Fast では内容を読まないため発生しない。
- 将来、Fast の結果の一部を Strict に昇格させる機能や、ファイル単位でモードを混在させる機能は設けない。モードは1回の実行全体で固定する。
- 「全体方針」の「現在の全バイト一致だけを削除の根拠とし」は Strict の方針である。Strict ではこの方針を維持し、Fast は本項で定める明示的な例外とする。

## DEC-20. Fast の CLI と警告: `--fast` のみ、警告は2か所で標準出力

> **2026-10-03 改訂**: `--fast` だけの opt-in、`--strict` を設けないこと、警告の文言、警告を標準出力に書くことは維持する。`--dry-run` との併用・一致の記述は `--dry-run` の廃止 (DEC-32) で無効になった。警告の表示箇所は、`analyze` のヘッダー、`delete` のヘッダー、`delete` の `[y/N]` の直前になった (DEC-33、DEC-34)。

- CLI は opt-in の `--fast` だけを加え、`--strict` は設けない。既定が Strict なので、明示する必要がない。
- `--fast` は `--dry-run`、`--yes` と併用できる。`--yes` は Fast でも確認のみを省略し、検証は省略しない (SPEC §2)。Fast 専用の追加承認や二重確認は設けない。`--fast` の明示指定そのものを Fast の opt-in とする。
- `--dry-run` と通常実行の初回分類の一致 (SPEC §2) は同じモード同士の規定とする。モードが違えば分類の集合が違う (`MATCHED` と `SAME_SIZE`) ため。

- 正確な文言は SPEC では固定せず、`PLAN.md` で決める。

## DEC-21. 分類名は `SAME_SIZE` とする

- 主な理由: `SAME_SIZE` は、観測した事実である「サイズが同じ」を直接表す。名前に `MATCH` を含まないため、既存の `MATCHED` (全バイト一致の確認済み) と意味・文字列の両面で混同しにくく、内容の一致も示唆しない。
- 不採用: `SIZE_MATCHED` は `MATCHED` (全バイト一致の確認済み) と混同しやすく、SPEC §5.2 の「宣言サイズなどだけで一致としない」という文言とも衝突する。`FAST_MATCH` は同じく `MATCH` を含むうえ、モード名が分類名に入る。分類は観測した事実を表し、モードを表さない。
- 内部名と表示名は分けず、分類名は1つとする。
- `MATCHED` の意味は変えず、Strict でのみ出現する。`MODIFIED` は両モードで「差異を観測した」を意味し、Fast ではサイズ不一致だけを観測する。削除候補は Strict では `MATCHED`、Fast では `SAME_SIZE` とし、SPEC §6 の表の「削除候補」列で定義する。

### カテゴリーの表示 (分類名の命名とは別の、表示上の判断)

- 解析結果のカテゴリーは、そのモードで意味のあるものだけを表示する (SPEC §10)。Fast で `MATCHED: 0` を表示しないのは、そのモードで意味のない分類を表示しないためである。補助的には、内容を比較した結果一致が0件だったという誤読も防ぐ。

## DEC-22. Fast の削除直前再検証: §8.3 の手順3 だけを省き、手順4 (最終確認) は MVP では残す

> **2026-10-03 改訂**: 「削除方式と検証モードは別の軸」「削除用ハンドルの構成をモードで変えない」「Fast でも最終確認を行う」は維持する。手順番号は新方式の SPEC §8.3 (全バイト比較が手順6、最終確認が手順7) に変わり、最終確認は M0 の全項目の照合になった (DEC-29)。Fast で行わないのは手順6 だけである (DEC-34)。

- Fast は SPEC §8.3 の手順1、2、4、5、6 を Strict と同じに行い、手順3 (2回目の全バイト比較) だけを行わない。「削除直前再検証」は §8.3 の手順1〜6 の全体を指し、Strict では手順3 を含み、Fast では手順3 を実行しない (SPEC §3 の手順6)。
- 手順4 は、手順3 の読み取りが長時間になり得るために窓を狭める目的で入れた (DEC-1)。Fast では手順3 が無く、手順2 と近接するため、将来の統合候補ではある。MVP では、Fast と Strict の削除フローの差を §8.3 の手順3 (全バイト再比較) の省略だけに限定し、手順4 (最終確認) は Fast でも維持する。手順4 の将来の統合・省略は別途判断する。手順4 の省略・統合の可否は SPEC では扱わず、関数分割や重複の最適化も固定しない。
- 削除方式と検証モードは別の軸として扱う。削除用ハンドル (SPEC §8.1)、`SetFileInformationByHandle(FileDispositionInfoEx)` と flags 0x3 (DEC-10)、`DeletePending` による成立確認 (DEC-11)、`DELETE_FAILED` と停止の境界 (DEC-2、DEC-12) は両モードで同じである。削除用ハンドルの `GENERIC_READ` は Fast では読み取りに使わないが、ハンドルの構成をモードで変えない。
- Fast では初回判定から削除までの内容の変化を検出できない。確認できるのはメタデータがスナップショットと一致することまでであり、SPEC §15.5 の「保証しない事項」として明記した。

## DEC-23. 先行設計を MVP に持ち込まない

- Fast の追加にあたり、既存の `Unextract.Core`・`Unextract.Windows`・`Unextract.Cli` の構成を超える追加の分離 (Fast 用の別の層など)、アーカイブ形式の抽象化、追加の状態管理などの先行設計は MVP に持ち込まない (判断の優先順位 3)。
- バッチ処理、再帰検索、RAR などの他形式、GUI などの将来の拡張は、必要になった段階で設計する。

## DEC-24. `analyze` と `delete` を分ける (2026-10-03)

- 旧方式では、`--dry-run` と通常実行が同じ全件の初回分類を行い、通常実行は確認の後に削除候補を開き直して2回目の全バイト比較をしていた。「dry-run → 通常実行」で削除されるファイルは全バイト比較が3回行われ、通常実行は全件の事前解析と全候補のスナップショット保持を必要とした。
- 新方式では、全件を解析して利用者が確認するための非破壊の `analyze` と、指定されたエントリを実行時点の状態で検証してその場で削除する `delete` に責務を分けた。`analyze` は比較用ハンドルだけを使い、削除用ハンドルを開かない (実装では削除の能力を型として持たせない)。
- `delete` は `analyze` の結果を信用しない。`analyze` の後に内容・名前・親・属性・ADS・hardlink・reparse 状態が変わり得るため、`analyze` の結果を削除の許可証にすると時間差の検証 (旧スナップショットに相当するもの) が再び必要になる。`delete` は常に現在状態を検証するので、`analyze` の結果を持ち込む必要がない。
- そのため、`analyze` と `delete` の分類の一致は保証しない (旧方式の「dry-run と通常実行の初回分類の一致」は廃止)。差が出得る原因 (時間差、削除権限、共有違反の扱い、事前判定の手段) は SPEC §2・§12 に明記した。
- Strict の全バイト比較の回数は、`analyze` → `delete` で計2回、`delete` だけなら1回になる。
- 名称は、単なる ZIP の一覧ではなく target との対応付け・安全判定・内容検証まで行うことから `list` ではなく `analyze` とした。

## DEC-25. 逐次削除: 削除用ハンドルで検査・1回の比較・削除を行い、全件の候補を保持しない (2026-10-03)

DEC-1 を置き換える。

- `delete` は処理対象を ZIP の順に1件ずつ処理し、各エントリで削除用ハンドルを1回だけ開き、同じハンドルで照合・特殊判定・(Strict の) 全バイト比較・最終確認・削除の指示・成立確認を行い、閉じてから次へ進む (SPEC §8.3)。全バイト比較した対象と削除する対象は、ハンドルで固定された同じファイルオブジェクトである。
- 削除用ハンドルは既に読み取りと全ての情報取得ができ、旧方式の2回目の比較はこのハンドルから読んでいた。したがって、最初から削除用ハンドルで開けば Win32 API もハンドル構成も追加せずに済む。比較用ハンドルで比較してから削除用ハンドルを追加で開く構成は、比較用ハンドルが `FILE_SHARE_DELETE` を許さないため共有違反になると推定され (未実測)、採らない。
- 数千〜数万件のハンドルを同時に保持しない (DEC-1 の理由を維持)。確認待ちの間も個々のファイルのハンドルを開かない (DEC-31)。
- 時間差を越えて同一性を引き継ぐ旧スナップショットは不要になった。代わりに、エントリ処理中だけ、列挙由来の基準 (列挙項目の File ID、ボリューム、たどった親の File ID、期待パス) と M0 (オープン直後に同じハンドルから取得した値) を持つ (SPEC §8.2)。エントリをまたいで保持しない。
- 旧方式で2回目の比較が検出していた「確認待ち中の、メタデータを保った内容だけの書き換え」(旧 D10) は、確認が比較より前に移ったため、比較そのものが現在の内容を見ることで扱われる。比較から削除までの間の書き込みは共有モードで防がれる (PoC 5)。
- 新方式の1回の比較での不一致 (SPEC §5.2 の 6) は `MODIFIED` で続行する (旧方式の2回目の比較では、初回と食い違うため停止だった)。ZIP 側の異常 (1〜5) は ZIP そのものの問題であり、STOP とする。
- 列挙結果 (ディレクトリごとに1回の列挙で記録した照合結果) は逐次削除でも再利用し、再列挙しない。削除するのはファイルエントリの最終成分だけで、ZIP の事前検証により同じ名前が後続のエントリで再び引かれることはない。ディレクトリは削除しない。あるディレクトリ内の削除の前にそのディレクトリの列挙は終わっている。POSIX semantics で削除保留の名前は残らない。外部の変更で古くなった照合結果は、開いたハンドルでの照合 (File ID・親 File ID・最終パス) で STOP になるか、`MISSING` (削除しない) になるだけである。毎エントリの再列挙は総量を二乗に増やし、安全性に寄与しない。
- 抽出した共通関数 (解決、ハンドル上の検査、内容検証) を `analyze` と `delete` が共有し、両者の差 (ハンドルの種類、FATAL / STOP、削除の有無) は呼び出し側に明示する。既存の `ClassificationPipeline` に「候補が出たら削除フェーズを呼ぶ」分岐を足す案は、`DeletionPhase` が再オープンとスナップショットを前提にしているため「比較したハンドルで削除」と「1回の比較」を満たせず、採らない。

## DEC-26. 削除0件の範囲と逐次 STOP の境界 (2026-10-03)

- Prepare (引数、ZIP のオープン、entries の読み込みと検査、拒否位置、target ルート、ZIP 全体の事前検証、ZIP 自身の個体、entries と ZIP の照合) の失敗と、確認での中止では、削除0件を保証する。
- `delete` の逐次処理を始めた後の STOP では、STOP より前に削除したファイルはそのまま残し、STOP の対象は削除せず、以後は未処理とする。自動復元はしない。
- これは部分削除を新しく導入するものではない。旧方式でも削除フェーズ開始後の停止では、それまでに削除したファイルを復元していなかった。変わるのは、旧方式で全件の事前解析により削除開始前の FATAL になっていた target 側の判定不能 (列挙・情報取得の失敗、File ID の不一致、比較対象の ZIP エントリの異常など) が、`delete` では処理途中の STOP になる点である。
- 全件の事前解析で削除0件を保証し続けるには、`delete` の中で全件解析を先に行う (旧方式に戻る) か、全件のハンドルを保持する必要があり、DEC-24・DEC-25 の目的に反する。利用者が削除前に全体を確認したい場合は `analyze` を使う。CLI は STOP の際に、削除済みのファイルが戻らないこと、STOP の対象を削除していないこと、未処理のエントリに触れていないことを明示する (SPEC §10.3)。

## DEC-27. `delete` の削除用オープンの共有違反・アクセス拒否は、識別確認が一致すれば `DELETE_FAILED` で続行する (2026-10-03)

- 列挙由来の基準を使った識別確認が一致すれば `DELETE_FAILED` として対象を残し、後続へ進む。不一致・失敗・判定不能なら STOP。旧方式の削除フェーズの扱い (DEC-2) と同じで、比較基準だけを列挙由来に変えた。
- S09 は 2026-10-03 の人間判断で (b) (現行実装の挙動を正式仕様とする) を採用。実行中に DELETE を共有せず保持している ZIP 自身にもこの一般則を適用し、`DELETE_FAILED`、終了 1、ZIP を残して後続へ進む。ZIP 自身を事前判定で特別に SKIPPED とする分岐は追加しない (SPEC §8.1・§8.4)。
- Strict でもこの場合は内容比較を行っていないため、その旨を結果の理由に表示する。読めるが削除の権限が無い、内容の異なるファイルも `DELETE_FAILED` になる (`analyze` では `MODIFIED`)。分類のために比較用ハンドルで開き直す案は、経路が増えるため採らない。
- `analyze` では従来どおり共有違反などのオープン失敗を FATAL とする (DEC-9)。`analyze` と `delete` で扱いが異なるのは意図した仕様である。`delete` では対象を削除しないことは同じで、他のエントリはそれぞれ独立に現在状態で検証されるため、続行しても安全性は下がらない。STOP にすると、編集中のファイル1つで残りが全て未処理になる。

## DEC-28. 最終成分のディレクトリ・reparse・許可外属性は、列挙の属性で事前に `SKIPPED_SPECIAL_FILE` とする (D1、2026-10-03)

- 削除用ハンドルは `FILE_FLAG_BACKUP_SEMANTICS` を持たず、ディレクトリを開けない (5 になる。PoC 7 #6・#11)。そのまま開くと識別確認が「ディレクトリ」と判定し、STOP になる。ZIP のファイルに対して target にディレクトリがあるだけで `delete` が止まるのは、`analyze` (`SKIPPED_SPECIAL_FILE`) との差が大きい。
- `delete` では、最終成分の列挙項目の属性・reparse tag がディレクトリ・reparse・許可集合外の属性なら、削除用ハンドルを開かずに `SKIPPED_SPECIAL_FILE` とする。この判定は「削除しない」側にだけ働くため、列挙から時間が経っていても安全側である。reparse point・placeholder・read-only などに `DELETE` アクセスのハンドルを開かずに済む。親成分は旧方式から列挙の属性で分類しており、手段も一貫する。
- 事前判定を通過した対象は、削除用ハンドルの上で全ての特殊判定を改めて行う。列挙の属性とハンドルの属性の一致は未実測で (PLAN_TESTS S38)、安全性はこの一致に依存しない。
- 不採用: D2 (削除用ハンドルに `FILE_FLAG_BACKUP_SEMANTICS` を加える) は SPEC §8.1 と PoC で確定した構成の変更で、PoC のやり直しが要り、ディレクトリに `DELETE` アクセスのハンドルを開くことになる。D3 (5 のときの識別確認がディレクトリなら SKIPPED) は、識別確認が別のオープンで「判定できた」根拠が弱く、分岐も増える。

## DEC-29. `delete` の最終確認は M0 の全項目を照合し、オープン直後に親 File ID を列挙でたどった親と照合する (2026-10-03)

- 旧方式の最終確認はリンク数・ストリーム一覧・属性・`DeletePending` の4項目だった (2回目の比較の前に全項目の再検証をしていたため)。新方式では全バイト比較の前に全項目を照合する時点が無いので、オープン直後に取得した M0 を基準に、削除の直前に全項目 (File ID とボリューム、親 File ID、最終パス、`EndOfFile`、`LastWriteTime`、`ChangeTime`、属性、リンク数、ストリーム一覧、reparse 状態) と `Directory`・`DeletePending` を照合する。旧方式の `Revalidate` 相当の検査を流用する。
- 比較は長時間になり得る。共有モードで防げない変更 (属性・ADS・hardlink。PoC 6) に加え、祖先ディレクトリの改名による最終パスの変化の可能性がある (配下のファイルを開いている間に祖先を改名できるかは未実測。PLAN_TESTS S26)。旧方式も2回目の比較の後に最終パスを見ていなかったので、これは安全側の強化である。追加の API 呼び出しは数回で、比較の I/O に比べて小さい。
- オープン直後の親 File ID の照合は、旧方式の初回分類には無かった (旧方式はスナップショットに記録して削除時に比べた)。時間差のある2回の照合が無くなったため、PoC 8 / DEC-13 の「同名の別ディレクトリに同じファイルを移す」差し替え (旧 D19、新 S22) を、列挙からオープンまでの間について検出するために加える。値は既存の `GetParentFileId` (`FSCTL_READ_FILE_USN_DATA`) で得る。新しい Win32 API は追加しない。
- 不一致・取得失敗はいずれも STOP。実際の競合のときだけ新しい STOP の原因になる。

## DEC-30. `--entries` は1行1つの exact な ZIP FullName のテキストとする (2026-10-03)

- `--entries` は `delete` の処理対象を限定するフィルタで、安全性の判断材料にしない。`delete` が現在状態を全て検証する以上、File ID・日時・ハッシュ・分類結果などを持つ JSON plan は安全性に寄与せず、許可証のように見えるだけなので MVP では導入しない。
- 各行は ZIP の FullName (復号後の名前そのもの) で、`StringComparison.Ordinal` で照合し、大小文字も区切り (`/`、`\`) も補正しない。`analyze` の表示の Entry を変換せずに書けば一致する (DEC-33)。Windows のパスとして解釈せず、文字列からパスを組み立てない。
- UTF-8 (不正なバイト列は入力エラー)。先頭の UTF-8 BOM は1個だけ許す (Windows PowerShell 5.1 の `Out-File -Encoding utf8` などは BOM を付ける)。UTF-16・UTF-32 の BOM は入力エラーとし、UTF-16 なら UTF-8 が必要と分かるメッセージにする (Windows PowerShell 5.1 の `>` は UTF-16LE で保存すると一般に知られているが、本プロジェクトでは未実測。PLAN_TESTS L18)。
- LF・CRLF・混在を受け付け、末尾の改行は任意。CR はエントリ名に現れない文字なので曖昧にならない。空行・空ファイル・重複・未知のエントリ・ディレクトリエントリは入力エラー (指定ミスを途中で気付く設計にしない)。trim、コメント、glob、ワイルドカードは無い (規則を1つにする)。大小文字・区切りだけ違うエントリがあれば正しい FullName をヒントに出してよい。
- 上限はファイル 128 MiB (= メタデータ総量の上限)、1行 4,096 バイト (名前の上限 1,024 UTF-16 単位は UTF-8 で最大 3,072 バイト)、100,000 行 (= エントリ総数の上限。重複不可で全て ZIP に存在する必要があるため、正当な入力はこれを超えない)。全体を読んで検証してから削除を始めるため、読み込み量を制限する。
- entries の読み込み・検証・照合は全て、確認と最初の target エントリの処理より前に完了させ、どの入力エラーでも削除0件とする (DEC-26)。ZIP 全体の事前検証と宣言側の上限は、選ばれなかったエントリを含む ZIP 全体に適用する (受理が `--entries` の内容で変わらないようにする。DEC-6)。
- `analyze` は `--entries` を受け付けない (責務を「`analyze` は ZIP 全体を解析」「`delete` は全体または `--entries` で限定」に固定する。部分的な `analyze` は将来必要になれば検討する)。

## DEC-31. `delete` の確認は Prepare の後、最初のエントリの処理の前に1回だけ行う (案 A、2026-10-03)

- 確認は Prepare が全て成功した後、target のエントリ (target ルート以外の列挙・削除用オープン) に触れる前に1回だけ行う。確認待ちの間、個々のファイルのハンドルを開かない。中止なら target のエントリに一切触れない。
- 不採用 (案 B: 最初の削除対象が見つかった時点で確認): そのハンドルを確認待ちの間開いたままにする (ファイルを長時間ロックし、確認待ち中の変更を最終確認まで持ち越す) か、閉じて開き直す (その1件だけ二重比較・再オープン方式に戻る) かのどちらかになり、DEC-25 の目的に反する。確認の前に列挙・比較が走る点も好ましくない。
- 削除される件数は確認の時点では分からないため、処理対象のファイルエントリの件数 (最大件数) を示す。削除対象が結果として0件になる場合も確認が出ることは許容する (事前の確認には `analyze` を使う)。
- Fast では確認の直前に警告を表示する (DEC-20 の「`[y/N]` の直前」を維持)。`--yes` は確認だけを省略する。

## DEC-32. 旧 CLI 形式と `--dry-run` を廃止し、互換動作を設けない (2026-10-03)

- サブコマンド (`analyze`・`delete`) を必須とする。サブコマンドの無い旧形式 (`unextract <archive.zip> --target <dir>`) と `--dry-run` は、入力エラーとして削除処理を開始せず、新しい使い方を案内する。deprecated alias は作らない。
- 理由: `--dry-run` を `analyze` の別名として残すと、同じ旧形式から `--dry-run` を外した場合の意味が問題になる。`delete` に割り当てると、旧来「全件確認 → 削除」だった操作が、途中の STOP で一部だけが削除される逐次方式に黙って変わる。旧形式を「全件解析 → 確認 → 削除」として残すと二重比較が戻る。入力エラーにすれば、旧来の使い方は何も削除せずに失敗するだけで安全側である。
- ローカルにタグ `v0.1.0`・`v0.2.0` があり、外部利用者がいる可能性を否定できない (公開状況は確認していない) ため、破壊的変更として README に移行を説明する。

## DEC-33. `analyze` / `delete` の表示: 1件1行、Entry は変換しない、Target は確認用 (2026-10-03)

- 1件1行で `<状態名 (20 桁固定)>  <Entry> -> <Target>` とする。Entry と Target の列はそろえない。最長 1,024 文字の名前に列幅を合わせると Target が右へ飛び、全角文字の表示幅はコンソールで正確に計算できないため。ブロック形式 (1件3行) は大量件数に弱い。
- Entry は ZIP の FullName を変換せずに表示し、そのまま `--entries` に書けるようにする。既存の `SafeDisplay.Escape` は表記を一意にするため `\` を `\\` にするが、`\` 区切りのエントリ名を転記できなくなるため Entry には使わない。端末上で危険・誤認しやすい文字 (書式文字、C1 制御、行・段落区切り) を含む名前だけをエスケープ表示し、転記できないことが分かる印を付ける。`>` はエントリ名にも Windows パスにも現れないため、` -> ` の区切りは一意である。
- Target は target の最終パスと ZIP の成分から組み立てた、人間が確認するための対応場所で、`delete` の入力に使わない。ラベルは状態によらず `Target` とし (状態ごとに `Expected Target` などに変えると列の意味が揺れる)、`MISSING` では実在しない期待位置を示すことを凡例で一度説明する。
- `SKIPPED_SPECIAL_FILE` は保持している `SkipReason` を表示する。
- 利用者向けの文言は既存どおり日本語を基本とする (DEC-20 の文体)。

## DEC-34. Strict と Fast の処理差は内容を読むかどうかの1点にする (2026-10-03)

- 旧方式の処理差は、初回の全バイト比較と2回目の全バイト比較の2点だった (DEC-19、DEC-22)。新方式では比較が各操作で1回になり、`analyze` と `delete` が内容検証の関数を共有するため、Strict と Fast の明示的な分岐はその関数の1か所になる。
- Fast の `delete` も、事前判定、オープン直後の照合、M0、最終確認 (全項目)、削除方式、成立確認、`DELETE_FAILED` と STOP の境界を Strict と同じに行う。Fast の最終確認は M0 の取得の直後になりほぼ冗長だが、分岐を増やさないため残す (DEC-22 の考え方を維持)。
- Fast の契約 (内容の一致を保証しない。同一パス・同一サイズで内容の異なるファイルが削除され得る) は変えない。新方式では、Fast の `delete` は内容を一度も読まないため、確認できるのは削除用ハンドルを開いた時点のメタデータと、それが削除の直前まで M0 と一致することまでである (SPEC §15.5)。
