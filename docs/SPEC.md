# unextract MVP 仕様 v4

## 1. 目的

ZIPファイルの内容と現在も完全に一致するtarget内のファイルだけを、安全側に倒して削除するOSS CLIツール。

ファイルが「過去にそのZIPから展開されたものか」は判定しない。判定するのは「現在の内容がZIP内のエントリと検証可能な形で一致するか」のみ。

最優先事項: ユーザー自身が作成・変更したファイルを誤って削除しないこと。

> unextract does not determine whether a file "probably came from" an archive.
> It removes a file only when its current contents can be verified against the archive.

## 2. 設計原則

- 「ZIPと現在のファイルが同一であると検証できた場合だけ」削除する
- 少しでも不確実なら削除しない(Fail Safe)
- 保証に関わる条件が確認できない場合は、保証できないものとして扱う。対象単位で隔離できるものは当該対象を `ERROR` / `SKIPPED_SPECIAL_FILE` とし、処理全体の安全前提を確立できない場合に限り、削除を開始せず終了コード 3 とする
- ZIPのヘッダー情報(CRC-32、サイズ)は自己申告値であり、同一性の根拠にしない
- ZIP内のパスは信用しない
- 再帰削除APIは使用しない(コード規約)
- ZIP全体・エントリ全体をメモリに展開しない(ストリーミング必須)
- ZIPの構造を信頼できない場合は何も削除しない。個別エントリの内容検証の失敗は、他のエントリの独立した検証結果を無効にしない。判断に迷う異常は構造を信頼できない側(archive-fatal)に倒す(§12)
- 既定のごみ箱削除では、完全削除へフォールバックしないことを削除開始前に保証できない場合、削除しない(§10.1)

## 3. MVPの対象

- Windows 11 / CLI / ZIP形式のみ / 単一ZIP
- 実装言語: C#(.NET 現行LTS、`global.json` で固定)
- OSSとして公開可能な構成(LICENSE、README、CI)

## 4. CLI

```
unextract <archive.zip> --target <dir> [options]
```

| オプション | 説明 |
|---|---|
| `--target <dir>` | 必須。展開先ディレクトリ |
| `--dry-run` | 解析結果の表示のみ。ファイルシステムを一切変更しない |
| `--yes`, `-y` | 確認プロンプトを省略 |
| `--delete-permanently` | ごみ箱を使わず完全削除する(明示指定時のみ) |

挙動:

- 通常実行でも、削除前に必ず dry-run と同じ解析を行い、結果を表示する
- 確認プロンプトは `[y/N]`、デフォルトは中止
- stdin がTTYでなく `--yes` もない場合は、何も削除せず終了コード 2 で中止する
- `--target` の拒否条件(解決後の実パスで判定):
  - ドライブルート(`C:\` など)
  - `target == %USERPROFILE%`(ユーザープロファイルディレクトリそのもの)。配下の通常ディレクトリ(`Downloads` など)は許可する
  - Windowsディレクトリ、`Program Files`、`Program Files (x86)`、`ProgramData`、およびそれらの配下
  - UNCパスのルート
- 上記のシステムディレクトリ配下の拒否は、技術的な必然ではなく、MVPが受理する範囲を意図的に狭める安全ポリシーである
- 指定されたパスの最終成分が reparse point の場合は、target不正として何も分類・削除せず終了コード 3 とする。この判定は、実パスへの解決より前に行う。祖先に reparse point がある場合は §7.2 に従う
- 拒否条件に該当する場合も、target不正として何も分類・削除せず終了コード 3 とする

## 5. 分類カテゴリ

ZIP内の各エントリは、次のいずれか1つに分類される。

| カテゴリ | 意味 | 削除 |
|---|---|---|
| `MATCHED` | ZIPの内容とバイト単位で一致 | する |
| `MODIFIED` | 存在するが内容が異なる | しない |
| `MISSING` | targetに存在しない | - |
| `UNSAFE_PATH` | パス検証で拒否 | しない |
| `SKIPPED_SPECIAL_FILE` | symlink / junction / reparse point / ハードリンク / 名前付きデータストリームを持つファイル(§7.4) / クラウドplaceholder(§7.3) / 通常ファイル以外 | しない |
| `ERROR` | 判断不能。entry-local error(§12.3)を含む(読み取り不能、権限なし、暗号化、CRC不整合、圧縮ストリームの正常終端の欠落、1エントリの上限超過、パス解決不能、読み取り専用属性(§10.1)、個別対象の状態取得不能など) | しない |
| `AMBIGUOUS` | 重複・衝突など曖昧なエントリ | しない |

注:

- `Unrelated files`(target内でZIPに無いファイル)はMVPでは集計しない
- 上表はエントリごとの外部カテゴリである。実装は、カテゴリとは別に内部で分類理由(reason)を保持してよい(例: 名前付きデータストリームを、他の特殊ファイルと区別して保持する)。理由の追加によって、CLI上のカテゴリは増やさない
- archive-level rejection(§12)が検出された場合は、エントリの分類結果を出さず、異常の内容を表示して終了コード 3 とする(§13)

## 6. 同一性判定

ファイルごとに次の順で判定する。0バイトファイルも例外にしない。

1. `stat` でディスク上のサイズを取得し、ZIPエントリのサイズと比較する。不一致なら `MODIFIED`(この場合、ZIPエントリの展開は行わない)
2. サイズ一致なら、ZIPエントリをストリーム展開しながら、ディスク上のファイルとバイト比較する。差異があれば即 `MODIFIED`。ただし、宣言サイズが内部ハードリミット(§6.1)を超える場合は、展開せず `ERROR` とする
3. 展開量が「ZIPエントリ宣言サイズ」または「ディスク上のファイルサイズ」を超えた時点で打ち切り、`ERROR` とする
4. 展開完了後、圧縮ストリームが正常に終端していること、展開バイト数が宣言サイズと一致すること、CRC-32がZIPエントリの値と一致することを確認する。いずれかが満たされなければ、当該エントリを `ERROR`(entry-local error、§12.3)とする
5. 全バイト一致、かつ手順4も成功した場合のみ `MATCHED`

0バイトエントリも、展開が正常終了し、圧縮ストリームが正常に終端し、出力が0 bytesで、CRC-32が正常であることを確認して初めて `MATCHED` とする。

比較の対象はファイルの無名データストリームである。名前付きデータストリームを持つファイルは、同一性を検証できないため `MATCHED` としない(§7.4)。

CRC-32は、ZIPエントリの内容整合性の検査(手順4)に使用する。targetとの同一性はバイト比較(手順2)によって確認し、CRC-32単独を同一性の根拠にしない。

### 6.1 リソース制限

- 展開は必ずストリーミングで行い、固定サイズのチャンクで読んで比較する。ZIP全体・エントリ全体をメモリに展開してはならない
- 打ち切り条件として「ディスク上のファイルサイズを超えた瞬間」を必須とする
- 内部ハードリミットとして、エントリ総数と1エントリあたりの展開量の絶対上限を定数で持つ(値は実装PLANで実測して決定。初期案: エントリ総数 100,000、1エントリ 16 GiB)
  - 1エントリの展開量の上限超過は、当該エントリの `ERROR`(entry-local error)とする
  - エントリ総数の上限超過は archive-fatal(§12.2)とする
- 内部上限として、メタデータの総量、1エントリの名前の長さ、パスの深さ(成分数)を設ける。超過は archive-fatal とする。値は実装PLANで、測定条件(名前長・深さ)を明記した実測に基づいて決める。これらの上限は、性能のための値であると同時に、MVPが受理する入力の範囲を定める互換性上の上限である
- MVPでは `--max-file-size` のようなユーザー向けオプションは設けない

### 6.2 実装が満たすべき検証能力

実装方式(使用するZIP読み取り方式)はSPECでは定めない。ただし、採用する方式は次の能力をすべて満たさなければならない。満たせない方式は採用しない。

1. 圧縮ストリームが正常に終端したことを確認できる(終端の欠落を検出できる)
2. 宣言された展開サイズを超える出力を検出できる(超過分を黙って切り捨てない)
3. エントリ総数・メタデータ量の上限を、エントリの内容を処理する前に検査できる
4. archive-fatal(§12.2)の検査を、削除を開始する前に、全エントリに対して完了できる

## 7. パス検証(最重要)

### 7.1 正規化前の拒否ルール

次のいずれかに該当するエントリは `UNSAFE_PATH` とし、ファイルシステムにアクセスしない。

- `..` 成分を含む(正規化すればtarget内に収まるものも拒否)
- 絶対パス、先頭が `/` または `\`
- ドライブレター(`C:\...`、`C:foo` のドライブ相対形式を含む)
- UNCパス(`\\server\share`)、`\\?\`、`\\.\`
- コロンを含む成分(NTFS代替データストリーム)
- NUL文字、制御文字
- Windows予約名(`CON`、`PRN`、`AUX`、`NUL`、`COM1-9`、`LPT1-9`。拡張子付きも含む)
- 成分の末尾がドットまたはスペース
- `\` と `/` の区切りはどちらも成分区切りとして扱う
- 区切りで分割した結果に、空成分(`a//b`、`a\\b`、`a/\b` など)または `.` 成分が生じる場合は、`UNSAFE_PATH` とする。ただし、ディレクトリエントリを表すパス末尾の区切り(1個)は、空成分とは扱わず、§8 とディレクトリエントリの規則に従う
- UTF-8フラグ付きのエントリ名が不正なUTF-8である場合は、置換文字で復号せず `UNSAFE_PATH` とする

### 7.2 対象の解決(安全性要件)

- targetディレクトリは、最終成分の reparse point 検査(§4)の後に、実パスへ解決する。祖先に reparse point(junction等)がある場合も、解決後の実ディレクトリを個体として保持し、以降の解決はその個体を起点に行う。個体として固定できない経路は、target不正として終了コード 3 とする
- 対象(ファイル・ディレクトリ)の解決は、**検証済みの親ディレクトリ個体を起点として、単一のパス成分ずつ子要素を解決する**。未検証の祖先パスを再解決してはならない。この要件は、検査・再検証・削除のすべての解決に適用する
- 包含(target配下であること)は、上記の解決の構造によって保証する。パス文字列の比較(`startswith` を含む)を、包含の根拠にしてはならない(例: `C:\extracted2` は `C:\extracted` の配下ではない)
- 大文字小文字を区別しない比較は、重複判定(§8)と拒否リスト(§4)にのみ用いる(いずれも、多めに拒否する方向)。包含の判定には用いない。Windowsにはディレクトリ単位で大文字小文字を区別する設定があり、`Foo` と `foo` が別のディレクトリとして存在しうるためである
- 解決のために使用するAPIはSPECでは定めない

### 7.3 reparse point・クラウドplaceholder の検査

- targetから対象ファイルまでの全中間ディレクトリ、および対象ファイル自身について `FILE_ATTRIBUTE_REPARSE_POINT` を検査する(target自体は §4)
- 1つでも該当すれば `SKIPPED_SPECIAL_FILE`
- ZIPエントリ側のsymlink属性(external attributes のUnixモード)がある場合も `SKIPPED_SPECIAL_FILE`
- 対象が通常ファイル以外(デバイス等)の場合も `SKIPPED_SPECIAL_FILE`
- ハードリンク(リンク数 > 1)は `SKIPPED_SPECIAL_FILE` として削除しない
- クラウド同期のplaceholder: 削除可否の判断に必要なクラウド/placeholder状態を、安全に識別できなければならない。識別されたplaceholderは `SKIPPED_SPECIAL_FILE` とする。識別する前に、対象の内容を読んではならない(読み取りによるダウンロードを起こさない)
  - 識別の機構を、処理全体として初期化・利用できない場合は、削除を開始せず終了コード 3 とする
  - 個別の対象について状態を取得できない場合は、当該対象を `ERROR` とする
  - SPECが保証するのは、採用した識別機構によって安全に識別できることを確認した範囲である。識別できない可能性がある状態を通常ファイルとして扱ってよいことを意味しない
  - 特定の製品・APIにはSPECは依存しない。どの状態まで識別できるかは、実装PLANの調査で確定する

### 7.4 名前付きデータストリーム

- 対象ファイルが、無名データストリーム以外のデータストリーム(名前付きデータストリーム)を持つ場合は、`SKIPPED_SPECIAL_FILE` とし、削除しない。例外は設けない(`Zone.Identifier` を含む)
- 削除候補のディレクトリ(§10.2)が名前付きデータストリームを持つ場合も、そのディレクトリは削除しない
- 名前付きデータストリームの有無を確認できない場合は、削除しない(`ERROR`)
- 理由: 比較するのは無名データストリームだけであり、名前付きデータストリームの内容はZIPと照合できない。ファイルやディレクトリを削除すると、それらも失われる
- 例外(特定のストリームを無視してよいとする)を設ける場合は、SPECで明示的に決める

## 8. 曖昧なエントリ

次は `AMBIGUOUS` とし、関連するすべてのエントリを削除しない。

- 同一パスの重複エントリ
- 大文字小文字違いのみのパス重複
- ファイルエントリとディレクトリエントリのパス衝突

(`AMBIGUOUS` はエントリの分類であり、archive-fatal(§12.2)ではない。)

## 9. ファイル名の文字コード

- UTF-8フラグ付きエントリはそのままUTF-8として扱う
- UTF-8フラグなしのエントリはCP437として解釈する
- 文字化けにより対応ファイルが見つからなければ `MISSING` になる(安全側)
- CP932対応はMVP対象外。READMEの制限事項に明記する
- 実装ライブラリの実際の挙動が上記と一致するかは、実装PLANで実機確認する

## 10. 削除処理

### 10.1 ファイル

- 解析結果の表示 → 確認 → 削除の順
- 各ファイルの削除直前に、サイズ確認とバイト比較を再実行する。再検証で不一致・失敗なら削除せず `MODIFIED` または `ERROR` に再分類する。再検証での失敗は、当該エントリだけの結果として扱い、他のエントリの処理は妨げない
- 削除対象の解決には §7.2 を適用する
- 内容が一致しても、読み取り専用属性を持つファイルは `ERROR` とし、削除しない。`--delete-permanently` 指定時も同じとする。理由: 削除に通常と異なる追加操作(属性の無視・解除)が必要となるため、MVPではその対象を受理しない。将来対応する場合は、SPECを改訂して決める
- デフォルトはごみ箱へ送る
- **既定モードでは、完全削除へフォールバックしないことを削除開始前に保証できない場合、削除してはならない。** 保証できない対象は `ERROR` とする。完全削除は `--delete-permanently` 指定時のみ
- 削除の後で完全削除を検出できることは、上記の保証の代替にならない
- 保証の条件(どの環境・どの手段で保証できるとみなすか)はSPECでは定めず、実装PLANの調査で確立する。実機で確認できていない条件は、保証できないものとして扱い、削除しない(§2)

**TOCTOUについて**

- 再検証によってリスクは縮小するが、比較後にファイルを閉じ、パスをごみ箱APIへ渡すまでの間の置換は完全には防げない
- 実装PLANでの調査項目:
  - 比較時に取得したファイルID(`FILE_ID_INFO` またはボリュームシリアル+ファイルインデックス)を、削除直前に再取得して同一か確認できるか
  - `IFileOperation` に、ShellItem経由で対象を渡せるか(パス文字列を経由せずに済むか)
  - 比較中は共有モードで開いたままにして、置換・削除を抑止できるか

**実装PLANでの調査項目(ごみ箱)**

- `IFileOperation` の呼び出し(CsWin32、STAスレッド、COM初期化)
- 完全削除フォールバックを検出または抑止するフラグ(`FOF_ALLOWUNDO`、`FOFX_RECYCLEONDELETE`、`FOF_WANTNUKEWARNING` 等)
- ファイル単位の削除結果の取得(`IFileOperationProgressSink`)
- 長いパス(260文字超)、ロック中ファイルの扱い

### 10.2 ディレクトリ

- 対象は「今回の実行で削除したファイルの祖先ディレクトリ」のみ(targetは含まない)
- ZIPの明示的な空ディレクトリエントリ、および事前から存在した空ディレクトリはMVPでは対象外
- ディレクトリを削除する前に、そのディレクトリが、今回削除したファイルの祖先として確認したディレクトリ個体と同一であることを再確認する。同一性を確認できない場合は削除しない。同一性をどう保証するかはSPECでは定めない
- 子から親の順に処理し、各ディレクトリが空であることを確認してから削除する
- 削除は非再帰のrmdirのみ(`RemoveDirectory` 相当)
- ZIPに無いファイルが1つでも残るディレクトリは削除しない
- reparse point のディレクトリは削除しない
- 名前付きデータストリームを持つディレクトリは削除しない(§7.4)
- targetは削除しない

## 11. Dry Run

- ファイルシステムを一切変更しない
- 全カテゴリのファイル一覧に加え、「削除予定ディレクトリ」も表示する(ファイル削除後に空になるかをシミュレートして判定)
- 削除予定ディレクトリの判定のため、候補ディレクトリ(今回削除予定のファイルの祖先に限る)の子の有無を、非再帰で確認してよい。これは §15 の「無関係ファイルの走査・集計」には含まれない。候補ディレクトリ以外のtarget内を列挙してはならない
- archive-level rejection(§12)の検査も、通常実行と同じく行う。検出された場合の挙動は通常実行と同じ(§13、終了コード 3)
- 実行前後でtarget全体のスナップショットが一致すること

## 12. ZIPの扱い

archive-level rejection は、アーカイブ全体を処理対象から外す上位概念である。次の2種類を含み、いずれも削除を開始する前に判定し、1件でも該当すれば、targetを削除せず、終了コード 3 とする。

- **archive-fatal**(§12.2): ZIPの構造を信頼できない
- **unsupported archive format**(§12.5): 構造は認識できるが、MVPの受理範囲外

### 12.1 基本

- 読み取り専用で開く(書き換え・移動・削除をしない)
- 暗号化エントリは `ERROR`(entry-local error)
- ZIPとして読み取れない場合は、何も削除せず終了コード 3(archive-fatal)

### 12.2 archive-fatal

ZIP内のエントリの境界、metadata、参照位置、または他のエントリからの独立性を信頼できなくする異常。

- 削除を開始する前に、**全エントリ**について検査する(展開を伴わずに判定できる構造の検査が対象。MISSING・MODIFIEDのエントリも含む)
- 1件でも存在すれば、targetを削除せず、終了コード 3
- 分類の詳細な列挙は実装PLANで行う。例:
  - EOCD / Zip64 EOCD / locator の不整合・欠落、複数候補による曖昧さ
  - Central Directory の切断、件数の詐称、宣言された領域外への参照
  - エントリのオフセット・サイズが範囲外、または算術的にあふれる
  - Local Header の位置・長さの異常、Central Directory との整合を確認できない
  - 圧縮データの範囲が、他のエントリ・Central Directory・その他の構造と重なる
  - Data Descriptor の境界を確定できない
  - Zip64 情報の矛盾
  - エントリ総数その他の内部上限の超過(§6.1)

### 12.3 entry-local error

archive-fatal の検査を通過したエントリについて、そのエントリ自身の内容検証だけが失敗した状態。

- 該当エントリを `ERROR` とし、削除しない
- 他のエントリについて独立に成立した `MATCHED` の判定は、無効にしない
- 例: CRC-32の不一致、圧縮ストリームの正常終端の欠落、展開サイズと宣言サイズの不一致、暗号化、未対応の圧縮方式、1エントリの展開量の上限超過
- これらは、展開を要するため、サイズが一致して比較に進んだエントリについてのみ確認すればよい(§6)

### 12.4 分類の原則

> ある異常を entry-local と分類してよいのは、その異常が当該entry以外のentryについて、境界、metadata、参照位置、および内容検証の独立性を損なわないことを確認できる場合に限る。確認できない場合は archive-fatal とする。

分類に迷う異常は、archive-fatal として扱う。

### 12.5 unsupported archive format(受理範囲外、互換性判断)

次の形式は、ZIPの仕様(APPNOTE)で許容されうるが、MVPでは**意図的に受理しない**。これは壊れていることを意味しない。安全原則から自動的に導かれる要件でもなく、MVPの実装範囲を限定する互換性判断である。受理範囲外の形式は unsupported archive format とし、archive-fatal とは区別する(終了コードは同じ 3)。後で受理範囲を広げる場合は、SPECを改訂して決める。

- 複数ディスク(split / multi-disk)のアーカイブ
- 自己展開形式(SFX)、およびZIP構造の前後に付いた余剰データ
- Central Directory が暗号化されているアーカイブ

認識できない・曖昧で何の形式か判断できない場合は、unsupported ではなく archive-fatal とする。

圧縮方式は Stored と Deflate のみを扱う。それ以外の方式のエントリは entry-local error(`ERROR`)とする。

### 12.6 内部安全性エラー(削除開始後)

archive-level rejection の検査は、削除を開始する前に完了する(§6.2 の能力)。通常のフローでは、削除開始後に archive-fatal や unsupported archive format が判明することはない。

それにもかかわらず、削除開始後に、削除前の構造検証で検出されなかった異常によって、archive-level rejection の前提が成立していなかったことが判明した場合は、通常の entry-local error ではなく**内部安全性エラー**として扱う。以降の削除を直ちに中止し、終了コード 3 とする。この場合、それまでに削除したファイルは戻らない。これは実装の欠陥の存在を示すものであり、仕様上の通常の結果ではない。

内部安全性エラーには、少なくとも次を区別する。いずれも以降の削除を直ちに中止し、終了コード 3 とするが、原因を別の reason として表示・記録する。

- 完全削除の発生(§10.1 の保証の破綻)
- 対象の同一性の不一致(別のファイルやディレクトリを操作した、または操作しうる状態になったこと)
- 削除前の構造検証で検出されなかった archive-level rejection 相当の異常

## 16. READMEに明記する内容

**ツールの位置づけ**

- 避ける表現: 「ZIPから展開されたファイルを特定して削除する」
- 使う表現: 「ZIP内のファイルと現在も同一であることが検証できた、target内のファイルだけを削除する」
- manifestを持たないため、「展開した事実」は検証できない。検証できるのは「内容の同一性」だけである

**制限事項**

- 内容が同一であれば、ZIP由来でなくても削除対象になる(別経路で置いた同一ファイル、0バイトの `.gitkeep` など)
- 同じファイルを含む別のZIPから展開されたファイルも削除対象になる
- UTF-8フラグなしの日本語ファイル名ZIPは、Missingと判定されることがある
- ハードリンク、symlink、junction(およびクラウドplaceholder)は削除しない
- 名前付きデータストリーム(ダウンロード元を示す `Zone.Identifier` を含む)を持つファイル・ディレクトリは削除しない
- 読み取り専用属性を持つファイルは、内容が一致していても削除しない(`--delete-permanently` 指定時も同じ)
- Windows、Program Files、Program Files (x86)、ProgramData の配下は、targetに指定できない
- クラウド同期フォルダでは、識別できる範囲でのみ保護される。環境によっては、ほぼ全件がスキップされる、またはクラウド状態を識別できず処理を中止することがある
- ZIPの構造を信頼できない場合は、何も削除しない。一部のエントリの内容だけが壊れているZIPでは、そのエントリは削除せず、独立に検証できた他のエントリは削除される
- 受理するZIPの範囲を意図的に狭めている(複数ディスク、自己展開形式、ZIPの前後の余剰データ、Central Directory の暗号化には対応しない。Stored / Deflate 以外の圧縮方式のエントリは削除対象にならない)
- ごみ箱が使えない場所では、デフォルトでは削除しない。完全削除へフォールバックしないことを事前に保証できない場合も、削除しない
- 再検証によってリスクは縮小するが、パスベースのごみ箱APIを使用する限り、検証から削除までの競合窓を完全には排除できない。unextract実行中は、targetディレクトリを他のプロセスで変更しないこと

## 17. テスト要件

### 判定
1. 完全一致 → `MATCHED`
2. 1byte変更(サイズ同一) → `MODIFIED`
3. 同名でサイズ違い → `MODIFIED`
4. ZIPにあるがtargetに無い → `MISSING`
5. ZIPに対応するエントリがないファイル、またはZIPのエントリと内容が一致しないファイル(ユーザー作成ファイルを含む) → 削除しない(ZIPと完全に一致する内容のファイルは、由来にかかわらず削除対象になる。§16)
6. 0バイトファイル(正常な0バイトエントリ → `MATCHED`、CRC不正などの壊れた0バイトエントリ → `ERROR`)
7. 暗号化エントリ、CRC不整合エントリ、圧縮ストリームの正常終端が欠けたエントリ → 当該エントリのみ `ERROR`(削除しない)。同じZIP内で独立に検証できた `MATCHED` のエントリは削除される
8. targetのサイズと宣言サイズが一致し、実際の展開出力が宣言サイズを超えるエントリ → `ERROR`
9. 宣言サイズが巨大で、targetのサイズと一致しないエントリ → `MODIFIED`。展開せず、メモリが増加しない
10. エントリ総数の上限超過 → archive-fatal(終了コード 3、何も削除しない)

### ディレクトリ
11. 空になったZIP由来ディレクトリ → 削除
12. ユーザーファイルが残ったディレクトリ → 削除しない
13. 事前から存在した空ディレクトリ・明示ディレクトリエントリ → 削除しない
14. targetが削除されない

### パス安全性
15. `../` を含む → target外にアクセスしない
16. `a/../b`(正規化するとtarget内) → `UNSAFE_PATH`
17. 絶対パス、`C:foo`、UNC、`\\?\`、ADS、予約名、末尾ドット、空成分、`.` 成分 → `UNSAFE_PATH`
18. `C:\extracted2` のような兄弟ディレクトリの接頭辞一致 → target外として扱う
19. 親ディレクトリがjunction(`mklink /J` で作成) → `SKIPPED_SPECIAL_FILE`
20. symlink / reparse point / ハードリンク → スキップ(symlinkは権限が必要なためCIではjunction中心)

### 曖昧エントリ
21. 同一パス重複、大文字小文字違い重複、ファイル/ディレクトリ衝突 → `AMBIGUOUS`

### 動作
22. `--dry-run`: 実行前後でtarget全体(パス、サイズ、ハッシュ、更新日時)が一致
23. 処理後も元ZIPが残り、ZIPのハッシュと更新日時が不変
24. 検証後・削除前にファイルを書き換える → 再検証で削除されない
25. 検証後・削除前にファイルを別ファイルへ置換する → ファイルID確認で削除されない(実現可能性は実装PLANで調査)
26. 読み取り不能・ロック中ファイル → 削除されない
27. ごみ箱が使えない場所、または完全削除へフォールバックしないことを事前に保証できない場合 → デフォルトでは削除されず(`ERROR`)、`--delete-permanently` 指定時のみ削除
28. 非TTYで `--yes` なし → 何も削除されず終了コード 2
29. `--target` がドライブルート、`%USERPROFILE%` 自体、システムディレクトリ、およびその配下 → 拒否(終了コード 3)
30. `--target` が `%USERPROFILE%` 配下の通常ディレクトリ → 許可

### 宣言サイズと上限(v4追加)
31. 宣言サイズがtargetのサイズと一致し、かつ内部ハードリミットを超える → 展開前に `ERROR`(ハードリミットはテストで小さい値を注入する)

### archive-level rejection / entry-local(v4追加)
32. ZIPの構造異常(EOCD・Zip64の不整合、Central Directoryの切断・件数詐称、範囲外参照) → archive-fatal。終了コード 3、何も削除せず、target・ZIPとも不変
33. 先頭に正常な `MATCHED` エントリ、後続にCRC不一致のエントリ → 先頭のみ削除、後続は `ERROR`、終了コード 1
34. 出力サイズとCRCが一致するが、圧縮ストリームの正常終端が欠けたエントリ → `ERROR`(`MATCHED` にしない)
35. 圧縮データの範囲が、他のエントリまたはCentral Directoryと重なる → archive-fatal。先頭のエントリが正常でも何も削除しない
36. Local Headerの位置異常、Zip64情報の矛盾、Data Descriptorの境界を確定できない → archive-fatal
37. 受理範囲外の形式(複数ディスク、SFX、前後の余剰データ、Central Directoryの暗号化) → unsupported archive format(終了コード 3、何も削除しない)
38. 分類の原則: 独立性を確認できない異常を、entry-local ではなく archive-fatal に分類する(境界ケースのfixtureで確認)

### 名前付きデータストリーム(v4追加)
39. 無名ストリームがZIPと一致し、名前付きデータストリームを持つファイル → `SKIPPED_SPECIAL_FILE`、削除しない(`Zone.Identifier` を含む)
40. 名前付きデータストリームを持つ削除候補ディレクトリ → 削除しない

### 経路解決(v4追加)
41. 大文字小文字を区別するディレクトリ配下に `Foo` と `foo` が別個体として存在する → 包含判定・解決で同一視しない
42. 検証後に親ディレクトリが差し替えられる(rename、junction化) → 未検証の経路を再解決せず、target外・別個体を開かない

### Dry Run の走査範囲(v4追加)
43. 削除予定ディレクトリの判定: 候補内に予定外の子があれば削除予定に含めない。候補ディレクトリ以外のtarget内を列挙しない

### 内部安全性エラー・パス規則(v4追加)
44. 削除開始後に、削除前の構造検証で検出されなかった異常を発見する(フックで注入) → 内部安全性エラー。以降の削除を中止し、終了コード 3
45. 空成分・`.` 成分(`a//b`、`a\\b`、`a/\b`、`./a`) → `UNSAFE_PATH`。末尾の区切り1個のディレクトリエントリは受理
46. unsupported archive format と archive-fatal の区別: 正常なSFX・multi-disk(認識できる)と、EOCDが壊れた入力(認識できない)で、表示される理由が異なる。どちらも終了コード 3、何も削除しない

### target・読み取り専用・ディレクトリ個体・クラウド・内部安全性エラー(v4確定で追加)
47. 指定されたtargetの最終成分がjunction → 何も分類・削除せず終了コード 3
48. 祖先にjunctionがあり、最終成分は通常ディレクトリ → 実ディレクトリを個体として保持し、そこから解決できる場合のみ処理する。固定できない場合は終了コード 3
49. 内容一致かつ読み取り専用属性 → `ERROR`(ごみ箱モード・`--delete-permanently` の両方)
50. 削除候補ディレクトリが、削除したファイルの祖先個体と異なるもの(同名の別個体)に差し替えられる → 削除しない
51. クラウド識別の機構を初期化できない → 削除を開始せず終了コード 3
52. 1つの対象についてのみクラウド状態を取得できない → 当該対象が `ERROR`、他の対象は処理される
53. 完全削除の発生と、対象の同一性の不一致を、別の内部安全性エラー(別reason)として扱い、どちらも以降を中止して終了コード 3
54. UTF-8フラグ付きで不正なUTF-8のエントリ名 → 置換復号せず `UNSAFE_PATH`

## 18. 実装方針

- 構成: `Unextract.Core`(判定ロジック、Win32非依存)/ `Unextract.Windows`(reparse、hardlink、ファイルID、ごみ箱)/ `Unextract.Cli`
- 判定ロジックは `IFileSystemProbe` / `IDeleter` の抽象越しにし、実際には何も消えない偽Deleterで「削除しない」ことを大量に検証できるようにする
- Win32呼び出しは CsWin32 を使う
- ZIPの読み取り方式、および対象の解決(§7.2)に使うAPIは、SPECでは固定しない(§6.2 の能力と §7.2 の要件を満たす方式を、実装PLANで選ぶ)
- フェーズ: Phase 0(調査スパイク)→ Phase 1(Core + dry-run)→ Phase 2(Windows実装)→ Phase 3(ごみ箱削除、再検証、ディレクトリ削除)→ Phase 4(CLI仕上げ、README、CI)

## 19. MVP完成条件

```
unextract example.zip --target ./example --dry-run
  ↓ 削除対象と残す対象を確認
unextract example.zip --target ./example
```

ZIPのエントリとバイト単位で一致することを検証できたtarget内のファイルだけがごみ箱へ送られる。ZIPと内容が一致しないファイル(変更済みファイル、ユーザー作成ファイルを含む)、ZIPに対応するエントリがないファイル、およびZIP本体は残る。全テストが通ること。
