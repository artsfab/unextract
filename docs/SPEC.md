# unextract MVP 仕様

本書が unextract MVP の唯一の仕様上の基準である。`PLAN.md` と `PLAN_TESTS.md` は本書を実現・検証する文書であり、仕様を追加・変更しない。旧 v4 文書の節番号や分類規則は引き継がない。技術判断の根拠は `PLAN_DECISIONS.md`、実測記録は `PLAN_VALIDATION.md` に置く。

## 1. 目的と対象

Windows 11 の CLI。単一の ZIP と、利用者が明示した既存の NTFS ディレクトリ `target` を受け取り、ZIP 内の通常ファイルと現在の target 内の通常ファイルの内容を比較する。**全バイト一致を確認したファイルだけ**を削除候補にし、削除直前にもう一度全バイト一致を確認したものだけを削除する。「その ZIP から展開された」という来歴は証明しない。利用者が追加・変更したファイルを誤って削除しないことを最優先とし、不明・判定不能なら削除しない。

**削除安全性の根拠は、`ZipArchive` から実際に読み出した内容と target の全バイト一致である。** CRC-32 は偶発的な破損・切り詰め・記録と実データの食い違いを検出する補助検査であり、削除の根拠でも、敵対的に作られた ZIP への防御でもない (§5.3)。

ZIP にない target 内のファイルは表示・集計・分類・削除しない (完全に無視する)。実名を確認するために target 内のディレクトリの項目を走査することはあるが (§6.2)、走査した名前は ZIP エントリの成分名との照合にだけ使い、照合しなかった名前は保持も出力もしない。ディレクトリは、ZIP に明示されていても、ファイル削除後に空になっても削除しない。target と ZIP 自身も削除しない。クラウド placeholder やクラウド同期の意味論は対象外とし、安全に通常ファイルと認定できない対象は削除候補にしない。

実装は .NET 10 (LTS) と `System.IO.Compression.ZipArchive`、Windows の文書化された Win32 API (kernel32 と `winioctl.h` の FSCTL) を使う。独自の ZIP 構造パーサは作らない。

## 2. CLI と実行結果

```text
unextract <archive.zip> --target <dir> [--dry-run] [--yes|-y]
```

- 引数は上の形だけを受け付ける。`--target` はオプション名と値を別々の引数で渡す `--target <dir>` の形だけとし、`--target=dir` の形、値が無い・空、値が `-` で始まる、不明なオプション (`-` で始まる引数のうち `--target`、`--dry-run`、`--yes`、`-y` 以外)、同じオプションの重複、ZIP の指定が無い・複数は、いずれも入力エラーとする。
- `--target` は必須。存在しない、またはディレクトリでなければ入力エラーとし、推測・作成しない。対象ボリュームが NTFS でない場合も入力エラーとする。ドライブルート、UNC パス (共有ルートとその配下。最終パスが `\\?\UNC\` で始まるもの、§8.1)、ユーザープロファイルそのもの、Windows ディレクトリ、Program Files、Program Files (x86)、ProgramData とその配下は拒否する (拒否対象の実パスの求め方は §3 の手順1)。target の最終成分が reparse point の場合も拒否する (確認の方法は §3 の手順1)。祖先の reparse point は許すが、target は解決後の最終パス (§8.1) で固定し、以後の包含判定はその最終パスに対して行う。
- `--dry-run` と通常実行は、**確認・削除フェーズに入る前までの初回分類 (§3 の 1〜5) を同一の処理で行い、同じ分類結果・同じ FATAL 判定になる。** `--dry-run` は検証を省略せず、結果表示後に削除せず終了する。
- `--dry-run` は削除用ハンドルの再オープン、削除直前再検証、2回目の全バイト比較、削除を行わない。そのため、初回分類の後に target が外部から変更された場合、通常実行だけが削除直前再検証で停止し得る。この差は意図したものであり、dry-run と通常実行の一致の要件には含めない。
- 削除候補がある通常実行では `[y/N]` を表示し、`y`/`Y` の明示入力だけで開始する。空入力、EOF、その他の入力は中止。標準入力が非対話で `--yes` がない場合も中止。`--yes` は確認のみを省略し、検証は省略しない。
- 削除は通常の完全削除であり、ごみ箱は使わない。削除するのは検証済みの個別ファイルだけ。再帰削除はしない。
- 終了状態は「成功」「利用者による中止」「エラー」の簡易区分とし、細分化した終了コード体系は設けない。プロセスの終了コードは成功 0、エラー 1、利用者による中止 2 とする (`PLAN_DECISIONS.md` DEC-16)。
  - 成功: 解析を完走し、削除候補を全て削除した場合。削除候補0件、`--dry-run` も成功とする。
  - 利用者による中止: 確認で `y`/`Y` 以外が入力された、または非対話で `--yes` がない場合 (削除0件)。
  - エラー: 入力エラー、削除開始前の FATAL、内部エラー、削除フェーズの停止 (§8.4) に加え、**停止はなかったが `DELETE_FAILED` が1件以上ある場合** (削除しなかった検証済みのファイルが残り、要求された処理を完了していないため。DEC-18)。いずれの場合も終了時の要約に件数を表示する (§10)。

## 3. 処理順

1. 引数を検査し、ZIP を `FileShare.Read` (他者の書き込み・削除・改名を拒否) で開いて**実行終了まで保持**する。target ルートを保持用ハンドルで開く**前に**、最終成分が reparse point でないことを確認する: 同じパスを `FILE_READ_ATTRIBUTES` のみ・`FILE_FLAG_BACKUP_SEMANTICS | FILE_FLAG_OPEN_REPARSE_POINT` で開き (確認用ハンドル)、`FileAttributeTagInfo` で reparse point でないことと、`FileIdInfo` の File ID を確認する (reparse なら入力エラー)。確認用ハンドルを閉じた後に、target ルートを保持用ハンドル (§8.1。`FILE_SHARE_DELETE` なし) で開いて**実行終了まで保持**し、その File ID が確認用ハンドルの File ID と一致すること、保持用ハンドルがディレクトリであることを確認する (不一致は入力エラー)。続けて存在・NTFS・安全な位置・最終パスを確認する。安全な位置の判定では、拒否対象 (ユーザープロファイルそのもの、Windows ディレクトリ、Program Files、Program Files (x86)、ProgramData) のパスを .NET の `Environment.GetFolderPath` (または文書化された `SHGetKnownFolderPath`) で得て、読み取り専用のハンドル (`FILE_READ_ATTRIBUTES` のみ) で開き (このハンドルは `FILE_FLAG_OPEN_REPARSE_POINT` を付けず reparse をたどる。既知フォルダーが junction の場合に実体のパスへ直すため)、`GetFinalPathNameByHandleW` の最終パスに直してから、target の最終パスと大小文字を区別せずに序数比較する。拒否対象のパスの取得・解決に失敗した場合は、安全を確認できないため入力エラーとする。判定不能ならエラー終了する。ZIP 自身の個体 (§7) のボリュームシリアルと File ID も、ZIP のパスを同じく `FILE_READ_ATTRIBUTES` のみで reparse をたどるハンドルで開いて得る (ZIP は保持済みで改名・削除されないため、実体の ID になる)。実行全体で保持するハンドルはこの2つ (ZIP と target ルート) だけである。
2. `ZipArchive` で ZIP を読み取り専用で開く。ZIP64、Data Descriptor (DD)、SFX は独自の形式判定を設けず、`ZipArchive` の読み取り結果に委ねる (§5)。
3. **全エントリ**の名前、種類、重複・衝突、resource limits (§11) を検査する。この段階は target に触れず、target の状態に依存しない。1件でも不正または判定不能なら全体 FATAL、削除0件。この FATAL の時点で手順1の target ルートの確認と保持は済んでいるが、target の列挙や比較用ハンドルのオープン (手順4) には進まない。
4. ZIP の順にエントリを target 側で解決・分類する (§6、§7)。内容比較候補だけ ZIP の内容を読んで**初回の全バイト比較**を行う。比較用ハンドルは**そのエントリの判定が終わった時点で閉じる**。数千〜数万件のハンドルを保持しない。
5. 全件の結果を表示する。FATAL があれば削除せず終了する。`--dry-run` または利用者の中止でも削除しない。削除候補が0件なら確認プロンプトなしで正常終了する。
6. 確認後、各 `MATCHED` について、**再オープン → 同じハンドルでの同一性再検証 → 同じハンドルからの2回目の全バイト比較 → 同じハンドルからの削除**を行う (§8)。これを「削除直前再検証 (全バイト再比較を含む)」と呼ぶ。

削除開始前の FATAL は、他のエントリが `MATCHED` でも**削除0件**とする。処理順の最適化は許すが、この観測可能な結果を変えてはならない。

## 4. ZIP エントリとパス

### 4.1 名前の復号

- `ZipArchive` に `entryNameEncoding` として CP437 (`CodePagesEncodingProvider` 経由の code page 437) を渡す。採用版では UTF-8 フラグ (general purpose bit 11) 付きのエントリは UTF-8、フラグなしは CP437 で復号される (`PLAN_VALIDATION.md` V1)。`entryNameEncoding` を渡さないとフラグなしも UTF-8 として扱われるため、必ず渡す。CP932 等の推測はしない。
- `ZipArchive` は不正な UTF-8 を例外にせず U+FFFD に置換する。生の名前バイトは公開 API で得られないため、**復号後の名前に U+FFFD を含むエントリは全体 FATAL** とする。正当に U+FFFD を含む名前も拒否されるが、安全側の制限として許容する。

### 4.2 パスの検査

- `/` と `\` を区切りとして扱い、正規化前に絶対パス、ドライブ指定、UNC・デバイスパス、`..`、`.`、空成分、コロン、NUL・制御文字 (U+0000〜U+001F、U+007F)、Windows 予約名 (下記)、末尾ドット・空白、`<>"|?*` を含む名前を拒否する。ディレクトリエントリの末尾区切り1個だけは許す。target の外へ出得る名前は拒否する。
- Windows 予約名は `CON`、`PRN`、`AUX`、`NUL`、`COM0`〜`COM9`、`COM¹`、`COM²`、`COM³`、`LPT0`〜`LPT9`、`LPT¹`、`LPT²`、`LPT³`、`CONIN$`、`CONOUT$` とする (`¹` `²` `³` は上付き数字 U+00B9、U+00B2、U+00B3)。各成分について、**最初のドット (`.`) より前の部分 (ドットが無ければ成分全体) から末尾の空白 (U+0020) を除いたもの**が、予約名のいずれかと大小文字を区別せずに (`OrdinalIgnoreCase`) 一致すれば拒否する。したがって拡張子付き (`CON.txt`、`Prn.tar.gz`)、拡張子の前の空白 (`NUL .txt`)、ディレクトリ成分 (`CON/a.txt`、`aux/`) も拒否し、`CONSOLE.txt`、`COM10`、`LPT`、`xCON` は予約名ではない。末尾が空白の成分 (`CON `) は、予約名の判定より先に末尾の空白として拒否される。
- 名前長と深さは §11 の上限に従う。

### 4.3 ZIP 内部の構造

- 同一パスの重複、大文字小文字だけが違う重複 (`OrdinalIgnoreCase` での衝突)、ファイルとディレクトリの同名衝突、ファイルを親とする子エントリは全体 FATAL。明示ディレクトリと暗黙ディレクトリも含め、Windows 上で一意に対応付けられない構造は全体 FATAL。
- **ZIP 内部構造の衝突と target の実在状態は別概念である。** ZIP 内で `a` がファイルなのに `a/b.txt` もある場合は ZIP 内部構造衝突で全体 FATAL。ZIP に `a/b.txt` があり target に `a/` 自体が存在しない場合は、そのエントリが `MISSING` になるだけで正常である (§6.1)。

### 4.4 ZIP の特殊エントリ

`ZipArchiveEntry` は作成元 OS (version made by) を公開しないため、`ExternalAttributes` だけで次のように判定する。

- ディレクトリエントリは名前が `/` (または `\`) で終わるもの。`Length` が 0 でないディレクトリエントリは全体 FATAL。
- `ExternalAttributes` の上位16ビットのファイル種別 (`(attr >> 16) & 0xF000`) は、エントリの種類ごとに次だけを許す。それ以外は全体 FATAL。
  - ファイルエントリ (名前が区切りで終わらない): 0 または `0x8000` (通常ファイル)。**種別が `0x4000` (ディレクトリ) のファイルエントリは全体 FATAL。**
  - ディレクトリエントリ (名前が区切りで終わる): 0 または `0x4000`。**種別が `0x8000` (通常ファイル) のディレクトリエントリは全体 FATAL。**
  - symlink `0xA000`、FIFO `0x1000`、文字デバイス `0x2000`、ブロックデバイス `0x6000`、socket `0xC000` などは、どちらのエントリでも全体 FATAL。
- 下位の DOS 属性に `0x10` (ディレクトリ) があるのに名前が区切りで終わらない、または `0x400` (reparse point) があるエントリは全体 FATAL。read-only、hidden、system、archive などその他の DOS 属性は unextract が復元しないため無視する。
- 判定できないエントリを通常ファイルとみなさない。

## 5. ZIP 内容の読み取りと検証

### 5.1 読む範囲

ZIP の内容を読むのは**内容比較候補** (target に対象が存在し、§7 の特殊判定を通った後で安全な通常ファイルと判定され、かつサイズが `ZipArchiveEntry.Length` と一致するエントリ。§6.1 の手順 5→6→7 の順に判定する) だけである。`MISSING`、サイズ不一致の `MODIFIED`、`SKIPPED_SPECIAL_FILE`、`DIRECTORY` の内容は開かず、CRC も確認しない。そのため、これらのエントリの圧縮データだけが壊れていても FATAL にならない。

### 5.2 エントリ内容の検証基準

次の基準を「エントリ内容の検証基準」と呼び、初回比較 (§6.1) と削除直前の2回目の比較 (§8.3) の両方で同じように適用する。

1. `ZipArchiveEntry.IsEncrypted` が false。採用版の `ZipArchive` は暗号化フラグ付きの Deflate エントリを拒否せずに読み出すため、unextract が `Open()` の前に確認する。
2. `Open()` と読み取り中に例外が発生しない。`InvalidDataException` (破損・未対応圧縮方式)、`IOException` などは種類を問わず異常とする。
3. 読み出したバイト数が `Length` を**超えた時点で直ちに**異常とする (実測展開量の上限、§11)。
4. ストリーム終端までのバイト数が `Length` と等しい。採用版では Deflate 圧縮データが途中で切れても例外なく短く終わり、Stored は宣言サイズでなく圧縮サイズ分を返すため、unextract が数える。
5. 読み出した全バイトの CRC-32 が `ZipArchiveEntry.Crc32` と等しい (§5.3)。
6. 固定サイズのバッファで target と比較し、全バイトが一致する。

ZIP ストリームは**一致・不一致にかかわらず必ず終端まで読み切る**。途中でバイトが異なっても 1〜5 の検査は省略しない。これにより、不一致の位置によって結果が変わらない。target 側は不一致を確定した後は読み続けなくてよい。0バイトのエントリも、ストリームが0バイトで正常に終わり CRC が 0 で、target が0バイトなら一致とする。

初回比較では、1〜5 の違反は全体 FATAL、1〜5 を満たし 6 だけが不成立なら `MODIFIED`、全て満たせば `MATCHED`。2回目の比較では、1〜6 のどの違反も安全性不変条件の破綻として以後の削除を停止する (§8.4)。

mtime、ZIP の宣言サイズ、CRC 値だけで一致としない。

### 5.3 CRC-32

- 期待値は公開プロパティ `ZipArchiveEntry.Crc32` (Central Directory の CRC-32 フィールド) から得る。このプロパティは .NET Core 2.1 と .NET Standard 2.1 で追加された公開 API であり (.NET Core 2.0・.NET Standard 2.0 の参照アセンブリには無い。.NET Framework には無い)、採用する .NET 10 (LTS) に含まれる。.NET 10.0.12 のランタイムで直接参照してコンパイル・実行できることを確認した (`PLAN_VALIDATION.md` V2)。
- 実測値は Microsoft 公式パッケージ `System.IO.Hashing` の `Crc32` で、読み出したストリームについて計算する。reflection、private field、独自の ZIP 構造解析は使わない。
- 採用版の `ZipArchive` は、読み切っても CRC 不一致を検出しない (`PLAN_VALIDATION.md` V2)。したがって CRC-32 の照合は unextract の責務であり、内容比較候補では必須とする。将来の .NET が CRC 不一致を例外で通知するようになっても、§5.2 の 2 により同じく異常になる。
- **CRC の位置づけ**: CRC は ZIP の作成者が宣言サイズや実データと一緒に自由に書き換えられるため、敵対的に作られた ZIP への防御にはならない。CRC で検出するのは、偶発的な破損、切り詰め、Central Directory の記録と実データの食い違い (宣言サイズが実データと合わず出力が途中で切られる場合を含む) である。削除の根拠は §1 のとおり全バイト一致であり、CRC は補助検査である。Local Header の CRC との照合はしない。

### 5.4 `ZipArchive` に委ねる範囲

ZIP64、DD、SFX、Stored/Deflate 以外の方式は形式だけで拒否も受理もせず、`ZipArchive` が開けるかどうかに委ねる。`ZipArchive` が開けない ZIP、または内容比較候補で §5.2 の 1〜5 を満たさないエントリは FATAL。採用版の実測挙動は `PLAN_VALIDATION.md` に記録する。EOCD、Central Directory、Local Header、DD の照合、圧縮領域の重なり・隙間の検査はしない。unextract は ZIP の完全な健全性を証明するツールではない。

## 6. target 側の分類

全ての ZIP エントリに表示行を与える。

| 分類 | 条件 | ZIP 内容を読むか | 削除候補 |
|---|---|---|---|
| `MATCHED` | 安全な通常ファイルで、§5.2 をすべて満たし全バイト一致 | 読む | はい |
| `MODIFIED` | 安全な通常ファイルだが、サイズが `Length` と異なる (内容を読まない)、またはサイズ一致で内容が異なる | サイズ一致時のみ | いいえ |
| `MISSING` | 大小文字まで完全一致する名前のファイルがない。途中の親成分の扱いは §6.1 | 読まない | いいえ |
| `SKIPPED_SPECIAL_FILE` | 安全判定 API が成功し、特殊な対象であると**判定できた**もの (§6.1、§7) | 読まない | いいえ |
| `DIRECTORY` | ZIP のディレクトリエントリ。ディレクトリは削除対象外 | — | いいえ |
| `FATAL` | 特殊かどうか、存在するかどうかを**判定できなかった**もの。内容比較候補の §5.2 の 1〜5 の違反 | — | 全体中止 |

「特殊だと判定できた」(`SKIPPED_SPECIAL_FILE`) と「判定できなかった」(FATAL) を混同しない。

### 6.1 解決手順

1. 途中の各親成分を target ルートから1成分ずつ、§6.2 の実名確認で確認し、下表で分類する。最初に該当した成分で分類を確定し、その先を読まない。

   | 親成分の位置にある対象 | 分類 | 理由 |
   |---|---|---|
   | 存在しない | `MISSING` | 対応するファイルは存在し得ない |
   | 大小文字だけ違う名前のディレクトリ | `MISSING` | case strict。完全一致する名前が存在しない |
   | 通常ファイル (reparse でない) | `MISSING` | 種類は判定できており、その下にファイルは存在し得ず、削除も起こらない |
   | reparse point (ディレクトリ・ファイルを問わず。junction、symlink、placeholder を含む) | `SKIPPED_SPECIAL_FILE` | 種類は判定できている。reparse 先をたどらず、その下を読まない。全体を止める必要はない。reparse の判定は他の種類より優先する |
   | 完全一致する名前の通常ディレクトリ (reparse でない) | 次の成分へ進む | — |
   | 種類・属性を判定できない (列挙・検証 API の失敗、想定外の種類) | FATAL | 判定不能。「想定外の種類」は、列挙で得た属性からディレクトリ・通常ファイル・reparse point のいずれとも分類できないもので、`FILE_ATTRIBUTE_DEVICE` を持つ項目を含む |

2. 最終成分も、手順1と同じ §6.2 の実名確認で、親ディレクトリの項目から実名が大小文字まで一致するものを探す。無ければ `MISSING`。大小文字だけ違うもの、8.3 名など別名だけで到達するものも `MISSING`。
3. 比較用ハンドルを開く (§8.1)。開いたハンドルの File ID が手順2で見つけた項目の File ID と一致しなければ FATAL (解析中の変化)。存在を確認した後に開けない場合は FATAL とする。**他プロセスが対象を書き込みで開いている (エディタで編集中など) ための共有違反も FATAL であり、1ファイルの問題で全体が中止され削除0件になる。** 見つからない、アクセス拒否も同じ。
4. そのハンドルで最終パスが期待パス (target の最終パス + `\` + ZIP の成分を `\` で連結したもの) と序数比較で一致することを確かめる。不一致は FATAL。最終パスと期待パスの形式は §8.1 のとおり (`\\?\` 接頭辞を含むまま比較する)。
5. 同じハンドルで、§7 の順序で特殊判定を行う。該当すれば `SKIPPED_SPECIAL_FILE`。内容は読まない。
6. サイズ (`EndOfFile`) が `Length` と異なれば `MODIFIED`。ZIP 内容は読まない。
7. サイズ一致なら §5.2 の基準で初回比較を行う。
8. 判定が `MATCHED` なら、閉じる前に同じハンドルから再検証用スナップショット (§8.2) を記録する。ハンドルを閉じる。

名前が存在するのに種類・属性・読み取り可否を安全に判定できない場合は、`MISSING` にせず FATAL とする。

### 6.2 実名の確認手段

親成分 (§6.1 の手順1) と最終成分 (手順2) の実名は、**確認済みの親ディレクトリをハンドルで開き、そのハンドルから項目を列挙して、成分名と序数比較する**方式で確認する。親成分と最終成分で同じ手段を使う。

1. 列挙するディレクトリを、列挙用ハンドル (§8.1) で開く。target ルートは保持しているハンドルをそのまま使う。それ以外のディレクトリは、1つ上の列挙で見つけた項目のパスで開き、そのハンドルで File ID が列挙で見つけた項目の File ID と一致すること、ディレクトリであること、reparse でないこと、最終パスが期待パスと序数一致することを確かめる。不一致・取得失敗は FATAL。
2. 同じハンドルで `GetFileInformationByHandleEx(FileIdExtdDirectoryRestartInfo / FileIdExtdDirectoryInfo)` によって項目を列挙する。各項目の名前 (ロング名)、属性、reparse tag、128 ビット File ID が得られる。`.` と `..` は照合から除く。
3. 列挙した各項目の名前を、そのディレクトリ直下で探している ZIP エントリの成分名の集合と照合する。**ディスク上の名前と ZIP の成分名が序数比較で完全に一致した項目だけ**を対応させ、その属性・reparse tag・File ID を §6.1 の表と手順3で使う。
4. 列挙は8.3 の短い名前を項目として返さないため、8.3 名だけで一致するものは対応せず `MISSING` になる。大小文字だけ違うものも序数比較で一致せず `MISSING` になる。ディレクトリごとに大文字小文字を区別する設定の NTFS ディレクトリでも同じ規則になる。
5. 1回の列挙で同じ名前の項目が複数回返った場合は、**最初の1件を採用し、2件目以降は無視する**。採用した項目も、§6.1 の手順3・4 (比較用ハンドルの File ID と最終パスの確認) と、削除フェーズの再オープン時の同一性再検証 (§8.3 の 2) で保護される。
6. 照合しなかった項目は保持・表示・集計・分類しない (§1)。照合結果だけをそのディレクトリについて記録し、列挙を終えたら列挙用ハンドルを閉じる。同じディレクトリは1回だけ列挙する。
7. 列挙用ハンドルのオープン、項目の列挙 (終端を示す `ERROR_NO_MORE_FILES` 以外のエラー)、ハンドルの検証のいずれかが失敗した場合は FATAL とする。

**列挙中のディレクトリの変更**: 列挙の途中で改名された項目は、その列挙で見落とされることも、旧名と新名の両方で返ることもある (§13、PoC 8)。名前が変わらない項目の見落としは観測していない。見落とされた名前は `MISSING` になり、内容は読まず削除もしない。同じ名前の重複は上の 5 で扱う。列挙で見つけた名前が直後に改名された場合は、手順3の比較用オープンの失敗 (見つからない) または File ID の不一致で FATAL になると推定しているが、この組み合わせは実測していない。

ディレクトリの大きさに比例して列挙の時間がかかるが、ZIP が触れるディレクトリをそれぞれ1回ずつ列挙するだけなので、総量は「ZIP が触れるディレクトリの項目数の合計」に比例する。巨大なディレクトリに少数の ZIP エントリが対応する場合は、`FindFirstFile` による1件ずつの検索より遅くなり得るが、MVP では正確さと手段の一貫性を優先する。

## 7. 特殊ファイルと属性

比較用ハンドルから取得した情報で、次のいずれかに該当すれば `SKIPPED_SPECIAL_FILE` とする。

**判定は次の順に行う。** 比較用ハンドルで最初に `FILE_STANDARD_INFO.Directory` を判定する。ディレクトリであれば、ストリーム一覧など他の情報を取得せず `SKIPPED_SPECIAL_FILE` とする (データストリームを持たないディレクトリでは `FileStreamInfo` が `ERROR_HANDLE_EOF` で失敗するため)。ディレクトリでない対象については、以降の取得 API が1つでも失敗した場合 (`ERROR_HANDLE_EOF` を含む) は FATAL とする。初回分類では `DeletePending` を判定項目にしない (削除保留中の対象は開けず、比較用ハンドルのオープン失敗として FATAL になる)。

- ディレクトリである (`FILE_STANDARD_INFO.Directory`)。
- reparse point である (`FILE_ATTRIBUTE_REPARSE_POINT` または reparse tag が 0 でない)。symlink、junction、クラウド placeholder を含む。
- hardlink のリンク数が2以上 (`FILE_STANDARD_INFO.NumberOfLinks`)。
- 既定の `::$DATA` 以外の名前付きデータストリーム (ADS) がある (`FileStreamInfo`)。`Zone.Identifier` を含む。
- ZIP 自身と同じ個体 (ボリュームシリアルと 128 ビット File ID が一致)。
- 属性に次の**許可集合以外のビット**が1つでもある。

許可する属性 (これらだけを理由にスキップしない):

| 属性 | 値 | 許可の理由 |
|---|---|---|
| `ARCHIVE` | 0x20 | 通常の作成・更新で付く |
| `NORMAL` | 0x80 | 他の属性がない状態 |
| `HIDDEN` | 0x2 | 表示上の属性で、格納や読み取りの意味を変えない。ZIP 展開ツールが復元することがある。削除前に全パスを表示する |
| `NOT_CONTENT_INDEXED` | 0x2000 | 検索インデックスの指定だけ |
| `COMPRESSED` | 0x800 | NTFS 透過圧縮。データはローカルにあり通常の読み取りで比較できる |
| `SPARSE_FILE` | 0x200 | 未割り当て範囲は0として読める。データはローカル |
| `ENCRYPTED` | 0x4000 | EFS。所有者は透過的に読める。読めなければ読み取り失敗で FATAL |

スキップする属性の例: `READONLY` (0x1。削除からの明示的な保護)、`SYSTEM` (0x4。OS・アプリの管理対象)、`DIRECTORY` (0x10)、`DEVICE` (0x40)、`TEMPORARY` (0x100。アプリが使用中の一時ファイル)、`REPARSE_POINT` (0x400)、`OFFLINE` (0x1000)、`INTEGRITY_STREAM` (0x8000)、`VIRTUAL` (0x10000)、`NO_SCRUB_DATA` (0x20000)、`RECALL_ON_OPEN` (0x40000)、`PINNED` (0x80000)、`UNPINNED` (0x100000)、`RECALL_ON_DATA_ACCESS` (0x400000)、`STRICTLY_SEQUENTIAL` (0x20000000)、および**未定義・将来のビット**。許可リスト方式とし、知らない属性は削除しない。

target ファイルの内容は特殊判定の後でだけ読む。比較用・削除用ハンドルは `FILE_FLAG_OPEN_NO_RECALL` と `FILE_FLAG_OPEN_REPARSE_POINT` で開くため、オープンや特殊判定でクラウドのオンライン取得を起こさず、最終成分の reparse point をたどらない。

## 8. ハンドルと削除

### 8.1 ハンドルの開き方

| 用途 | アクセス | 共有モード | フラグ | 保持期間 |
|---|---|---|---|---|
| ZIP | 読み取り | `FILE_SHARE_READ` | — | 実行終了まで |
| target ルート | `FILE_LIST_DIRECTORY \| FILE_READ_ATTRIBUTES` | `FILE_SHARE_READ \| FILE_SHARE_WRITE` (DELETE を共有しない) | `FILE_FLAG_BACKUP_SEMANTICS` | 実行終了まで |
| 列挙用 (target ルート以外のディレクトリ) | `FILE_LIST_DIRECTORY \| FILE_READ_ATTRIBUTES` | `FILE_SHARE_READ \| FILE_SHARE_WRITE` | `FILE_FLAG_BACKUP_SEMANTICS \| FILE_FLAG_OPEN_REPARSE_POINT` | そのディレクトリの検証と列挙の間だけ |
| 比較用 | `GENERIC_READ` | `FILE_SHARE_READ` | `FILE_FLAG_BACKUP_SEMANTICS \| FILE_FLAG_OPEN_REPARSE_POINT \| FILE_FLAG_OPEN_NO_RECALL \| FILE_FLAG_SEQUENTIAL_SCAN` | そのエントリの初回判定中だけ |
| 削除用 | `GENERIC_READ \| DELETE \| FILE_READ_ATTRIBUTES \| SYNCHRONIZE` | `FILE_SHARE_READ` | `FILE_FLAG_OPEN_REPARSE_POINT \| FILE_FLAG_OPEN_NO_RECALL` | 1件の再検証・再比較・削除の間だけ |

- 比較用・削除用の共有モードは `FILE_SHARE_WRITE` と `FILE_SHARE_DELETE` を含めない。開いている間、他プロセスは書き込み・改名・削除のために開けず、書き込み・削除アクセスのハンドル (または `FILE_SHARE_DELETE` を許さないハンドル) が既にあれば、こちらのオープンが共有違反で失敗する。削除用ハンドルは自分自身の `DELETE` のために `FILE_SHARE_DELETE` を必要としない。読み取りだけで `FILE_SHARE_DELETE` を許すハンドル (インデクサ・バックアップ相当) や `FILE_READ_ATTRIBUTES` だけのハンドルとは共存し、その場合も削除は成立する (§13、PoC 5)。
- 共有モードの判定に参加するのは、読み取り・書き込み・削除のいずれかのデータアクセスを持つハンドルだけである。`FILE_READ_ATTRIBUTES` だけのハンドルを保持しても他者の改名を防げないため、target ルートは `FILE_LIST_DIRECTORY` を付けて開く。これで実行中の target ルートの改名・削除を防ぐ。途中のディレクトリは保持しないため改名され得るが、最終パスと親 File ID の比較で検出する。
- target ルートの保持用ハンドルには `FILE_FLAG_OPEN_REPARSE_POINT` を付けない (最終成分の reparse をたどる)。そのため、最終成分の reparse の確認は §3 の手順1の確認用ハンドル (`FILE_READ_ATTRIBUTES` のみ、`FILE_FLAG_BACKUP_SEMANTICS | FILE_FLAG_OPEN_REPARSE_POINT`) で行い、保持用ハンドルの File ID との一致で、確認した個体と保持した個体が同じであることを確かめる。
- 比較用ハンドルの `FILE_FLAG_BACKUP_SEMANTICS` はディレクトリも開けるようにしてハンドル上で `Directory` を判定するためのもので、特権の有効化はしない。削除用ハンドルには付けない (ディレクトリは開けずアクセス拒否になり、§8.4 の識別確認で扱う)。
- 最終パスは `GetFinalPathNameByHandleW(FILE_NAME_NORMALIZED | VOLUME_NAME_DOS)` で取得する。ディスク上の実際の大小文字が返るため、case strict と、途中の reparse point による経路のすり替えをこの序数比較で確認できる。
- 最終パスは `GetFinalPathNameByHandleW` が返す形式 (`\\?\C:\...`) のまま保持・比較する。target の最終パスは保持用ハンドルから取得した値を使い、期待パスは「target の最終パス + `\` + ZIP の成分を `\` で連結したもの」で組み立てる。利用者が入力したパスの文字列を正規化して比較に使わない。`\\?\UNC\` で始まる最終パスの target は §2 の UNC 拒否として入力エラーとする。
- 情報取得は `GetFileInformationByHandleEx` の `FileIdInfo`、`FileStandardInfo`、`FileBasicInfo`、`FileAttributeTagInfo`、`FileStreamInfo` と、親ディレクトリの File ID を返す `DeviceIoControl(FSCTL_READ_FILE_USN_DATA)` (USN_RECORD_V3 の `ParentFileReferenceNumber`) で行う。`FSCTL_READ_FILE_USN_DATA` は USN ジャーナルが非アクティブなボリュームでも親 File ID を返す (§13、PoC 4)。
- .NET からは `LibraryImport` による kernel32 の P/Invoke と `SafeFileHandle` で呼ぶ。ntdll の未文書 API、reflection は使わない。

### 8.2 再検証用スナップショット

スナップショットの各項目は、内容比較 (§6.1 の手順7) の**前に**同じハンドルから取得し、その対象が `MATCHED` と判定されたときに、比較用ハンドルを閉じる前に記録する。内容比較の間の変更 (属性の変更など、共有モードで防げないもの) は、削除フェーズの同一性の再検証 (§8.3 の 2) で検出する。記録する項目は次のとおり: ボリュームシリアル番号と 128 ビット File ID、親ディレクトリの 128 ビット File ID、`EndOfFile`、`LastWriteTime`、`ChangeTime`、属性、`NumberOfLinks` (=1)、ストリーム一覧 (`::$DATA` のみ)、reparse でないこと、最終パス。

### 8.3 削除手順

削除開始後、各 `MATCHED` について次を順に行う。パスを使うのは 1 のオープンだけで、2〜6 は全て同じハンドルに対して行い、パスを再解決しない (1 が失敗したときの §8.4 の識別確認だけは例外で、削除は行わない)。

1. 期待パスを削除用ハンドルとして開く (§8.1)。
2. **同一性の再検証**: File ID とボリュームシリアル、親ディレクトリの File ID、`EndOfFile`、`LastWriteTime`、`ChangeTime`、属性、リンク数、ストリーム一覧、reparse 状態、最終パスがスナップショットと完全に一致し、`Directory` と `DeletePending` が false であること。target ルートは保持ハンドルで固定されている。親 File ID と最終パスは、片方だけでは検出できない差し替えがあるため、**どちらも省略しない** (同名の別ディレクトリへ同じファイルを移した場合は親 File ID だけが、途中のディレクトリの junction 化や大文字小文字だけの改名では最終パスだけが変わる。§13、PoC 8)。
3. **2回目の全バイト比較**: 同じハンドルから target の内容を先頭から読み、ZIP エントリの展開ストリームを新たに開いて、§5.2 の基準 (暗号化、例外、`Length` 超過、終端までのバイト数、CRC-32、全バイト一致) を初回と同じように適用する。
4. **最終確認**: 3 の読み取りが長時間になり得るため、削除の直前に同じハンドルでリンク数、ストリーム一覧、属性、`DeletePending` をもう一度確認する。
5. **削除**: 同じハンドルに対して `SetFileInformationByHandle(FileDispositionInfoEx)` で削除を指示する。flags は `FILE_DISPOSITION_FLAG_DELETE | FILE_DISPOSITION_FLAG_POSIX_SEMANTICS` (0x3) とする。`FILE_DISPOSITION_FLAG_IGNORE_READONLY_ATTRIBUTE` は指定しない。POSIX semantics により、`FILE_SHARE_DELETE` 付きで開いている他のハンドルがあっても、このハンドルを閉じた時点で名前が消える。
6. **成立確認**: 同じハンドルで `FILE_STANDARD_INFO.DeletePending` が true であることを確認し、ハンドルを閉じて `DELETED` とする。**`SetFileInformationByHandle` の成功だけでは成立としない** (`DELETE` ビットを含まない flags でも成功を返し、何も削除しないため)。削除の指示が失敗した場合 (read-only など) は `DeletePending` は false のままである。`NumberOfLinks` は指示後に 0 と報告されることを観測しているが、公式資料の裏付けがないため判定条件にせず、補助的な観測にとどめる。

削除は再検証・再比較したこのハンドルに対してだけ行う。**パスを再解決して別に削除する方式 (パスベースの `File.Delete` など) は使わない。**

### 8.4 `DELETE_FAILED` と停止の境界

削除フェーズの失敗は「その対象を残して次へ進む `DELETE_FAILED`」と「その対象を削除せず以後の削除を全て止める停止 (安全性不変条件の破綻)」に分ける。**どちらか確定できないもの、未知・曖昧なエラーは停止側に倒す。**

| 段階 | 状況 | 扱い |
|---|---|---|
| 1 (オープン) | 共有違反、アクセス拒否で、**識別確認**の時点で対象がスナップショットと一致する通常ファイルに見える | `DELETE_FAILED`、続行 (削除しない) |
| 1 (オープン) | 共有違反、アクセス拒否で、識別確認が失敗・不一致 (別の個体、ディレクトリ、reparse、削除保留中に見えるなど) | 停止 |
| 1 (オープン) | 対象が見つからない、途中のパスが見つからない (対象消失、親の差し替え) | 停止 |
| 1 (オープン) | reparse・クラウド関連のエラー、名前解決のエラー、その他の未知・曖昧なエラー | 停止 |
| 2 (再検証) | いずれかの値の不一致、情報取得の失敗 | 停止 |
| 3 (再比較) | §5.2 の 1〜6 のいずれかの違反 (初回に読めた・一致したものが読めない・一致しない) | 停止 |
| 4 (最終確認) | 不一致、取得失敗 | 停止 |
| 5 (削除) | 失敗 (エラーの種類を問わない。再検証後に read-only が付いた場合などを含む) | 停止 |
| 6 (成立確認) | 削除の成立を確認できない | 停止 (その対象は「削除された可能性あり」と報告) |

**識別確認**: 段階1が共有違反またはアクセス拒否で失敗したときだけ、同じ期待パスを `FILE_READ_ATTRIBUTES` のみ (共有モードの判定に参加しない) と `FILE_FLAG_BACKUP_SEMANTICS | FILE_FLAG_OPEN_REPARSE_POINT | FILE_FLAG_OPEN_NO_RECALL` で開き、File ID、親 File ID、最終パス、ディレクトリでないこと、reparse でないこと、`DeletePending` が false であることをスナップショットと比較する。全て一致すれば「識別確認の時点で、スナップショットと一致する通常ファイルに見える」とする。このハンドルでは削除しない。

識別確認の限界:

- 識別確認は、拒否された削除用オープンとは別のオープンである。2回のオープンの間に対象が差し替えられる可能性を排除できないため、**拒否された削除用オープンが見た個体と識別確認が見た個体が同じであることは保証しない。** また、識別確認は削除用オープンが拒否された理由 (使用中、権限不足など) を確定するものでもない。
- 識別確認が一致した場合の結果は「そのファイルを削除せずに残して次へ進む (`DELETE_FAILED`)」だけであり、削除は行わない。したがって、この限界が誤削除につながることはない。識別確認は、同一性に疑いのある状況で処理を続けないための判定材料として使う。
- 識別確認が不一致または失敗した場合は停止する。

Windows のエラーコードと上表の対応は、§13 の PoC 7 の実測に基づいて `PLAN.md` §4 で定義する。削除用オープンで観測したコードは 32、5、2、3 の4種類で、5 は ACL による拒否、対象のディレクトリ化・ディレクトリ junction 化、削除保留中に共通であり、コードだけでは区別できない。対応表に載っていないエラーは停止とする。既に削除したファイルは自動復元しない。

## 9. FATAL と停止の条件

削除開始前に次のいずれかが1件でもあれば全体 FATAL、削除0件。

- ZIP を開けない・`ZipArchive` が読めない。target の入力エラー (§2)。
- 危険な ZIP パス、Windows 不正名、U+FFFD を含む名前、重複・case 衝突、ZIP 内部の file/dir 構造衝突、ZIP の特殊エントリ (§4)。
- resource limits の超過 (§11)。
- 内容比較候補の §5.2 の 1〜5 の違反: 暗号化、`Open()`・読み取り中の例外 (破損・未対応圧縮方式を含む)、実測バイト数が `Length` を超過または不足、CRC-32 不一致。
- target 側で存在・種類・属性・特殊性を判定する API の失敗 (§6.2 の実名確認の列挙・列挙用ハンドルの検証の失敗を含む)、存在確認後のオープン失敗 (**他プロセスによる共有違反を含む**)、列挙で見つけた項目と開いたハンドルの File ID の不一致、比較中の target 読み取り失敗、最終パスの不一致 (§6、§7)。

`MISSING`・サイズ不一致の `MODIFIED`・`SKIPPED_SPECIAL_FILE` のエントリについては内容を読まないため、その圧縮データの破損・暗号化・未対応方式だけでは FATAL にならない。名前・パス・構造・特殊種別・resource limits の検査は全エントリに行う。

削除開始後は §8.4 に従う。

## 10. 表示と進捗

正常に解析を完走した場合、`MATCHED`、`MODIFIED`、`MISSING`、`SKIPPED_SPECIAL_FILE`、`DIRECTORY` の**各カテゴリーの全パス**と件数を表示する。削除開始前の FATAL では、判定済みのパスと原因エントリ (と原因) を表示し、未判定はパスを列挙せず件数だけを表示して、削除0件を明示する。削除フェーズでは `DELETE_FAILED` のパスと理由を表示し、停止した場合は停止の原因となったパスと理由、削除済み・`DELETE_FAILED`・未処理の件数を表示する。停止の原因が削除の成立確認 (§8.3 の 6) の場合は、その対象を「削除された可能性あり」と表示する。名前を安全に表示できなければエスケープ表記またはエントリ番号で識別する。

解析中・削除中は `Checking n / total`、`Deleting n / total` 程度の進捗を表示する。終了時は削除成功数、通常削除失敗数 (`DELETE_FAILED`)、未処理数、スキップ数 (`SKIPPED_SPECIAL_FILE`。解析結果の合計行に含める)、停止理由を要約する。`DELETE_FAILED` が1件以上あれば、停止がなくてもエラーで終了すること (§2) を件数とともに表示する。

出力先: 解析結果の一覧 (各カテゴリーのパスと件数、判定済み・未判定の件数) と削除フェーズの結果 (`DELETE_FAILED` のパスと理由、件数の要約) は標準出力に書く。入力エラー、削除開始前の FATAL の原因、削除フェーズの停止の原因、内部エラー (想定外の例外) と、エラーで終わる理由は標準エラー出力に書く。進捗表示も標準エラー出力に書く。標準エラー出力がリダイレクトされているときは進捗を表示しない。JSON 出力、ログファイル、詳細な終了コード、Ctrl+C 専用の後処理は MVP に含めない。Ctrl+C などの中断で未検証のファイルを削除しないことは守る。

## 11. リソース制限

ZIP と target ファイルはストリーミングで読み、ZIP 全体やエントリ全体をメモリに展開しない。次の上限を定数として実装する。境界は「上限以下を許可、超過を拒否」。超過は全て削除前の全体 FATAL (削除フェーズの再比較での超過は §8.4 の停止)。ユーザー向けの上限変更オプションは設けない。

| 上限 | 値 | 対象・時点 |
|---|---|---|
| エントリ総数 | 100,000 | 全エントリ、§3 の 3 |
| 復号後のエントリ名 | 1,024 UTF-16 コード単位 (復号後の `FullName` のまま数える。ディレクトリの末尾区切りを含む) | 全エントリ、§3 の 3 |
| パス深さ | 128 成分 | 全エントリ、§3 の 3 |
| メタデータ総量 | 128 MiB (134,217,728 バイト) | 全エントリの復号後の名前の UTF-16 バイト数 + 1エントリ当たり 128 バイトの合計、§3 の 3 |
| 1エントリの宣言展開量 | 16 GiB (17,179,869,184 バイト) | 全ファイルエントリの `Length`、§3 の 3 |
| 宣言展開量の合計 | 64 GiB (68,719,476,736 バイト) | 全ファイルエントリの `Length` の合計、§3 の 3 |
| 1エントリの実測展開量 | そのエントリの `Length` | 内容を読むたび (初回比較・再比較)、超過した時点 |
| 実測展開量の合計 | 64 GiB | 初回分類の内容比較候補の累計、超過した時点 |

- 名前長は、復号後の `FullName` を区切りの変換や末尾区切りの除去をせずにそのまま数える (ディレクトリエントリ `d/` は 2 コード単位)。メタデータ総量の名前の UTF-16 バイト数も同じ `FullName` で数える。
- ファイルエントリの宣言 `Length` が負の場合は、宣言展開量として扱えないため全体 FATAL (`InvalidDeclaredLength`) とする (§3 の 3)。ディレクトリエントリの `Length` が 0 でない場合 (負を含む) は §4.4 により全体 FATAL になる。
- メタデータ総量はエントリ数とは独立したハード上限である。長い名前が大量にある ZIP で 100,000 エントリより先にこの上限へ達しても、意図した拒否とする。
- **宣言展開量の上限は、内容を読まない `MISSING` を含む全エントリに適用する。** 全エントリが `MISSING` になる ZIP でも、宣言合計が 64 GiB を超えれば FATAL とする。理由は次のとおりで、展開しないデータそのものが危険だからではない。
  1. 受理・拒否を target に触れる前に、target の状態と無関係に決められる。同じ ZIP が target の状態や `--dry-run` の有無で受理されたりされなかったりしない。
  2. 宣言値は ZIP 作成者が自由に書ける 64 ビット値であり、上限で合計の桁あふれと異常なメタデータを早期に拒否できる。
  3. MVP の受理範囲を「宣言展開量 64 GiB 以下の ZIP」と明確に定める。
- 実際に読む量の上限は実測側で必ず強制する。内容を読むたびに `Length` を1バイトでも超えた時点で中断するため、実測量は常に宣言量以下になる。初回分類の累計の実測上限も読み取り中に確認する。削除フェーズの再比較は初回に読んだエントリを読み直すだけなので、その量は初回の実測量を超えない。
- `ZipArchive` は開いた時点で Central Directory 全体をメモリに読み込む。この割り当ては unextract の上限検査より前に起こり、独自パーサなしには事前に制限できない。異常に大きな Central Directory でメモリが不足した場合は削除前に異常終了し、削除は起こらない。
- エントリ数と1エントリ展開量は旧 v4 の暫定案を採用した。その他は MVP で新たに固定した値である。値決定のための benchmark は要求しない。
- 空 ZIP、空 target は正常に扱う。削除候補が0なら確認プロンプトなしで終了する。

## 12. 既知の限界

- **初回比較から再オープンまで**: この間 (結果表示と確認待ちを含む) の変更は、同一性の再検証と2回目の全バイト比較で検出し、停止する。更新日時などを保ったまま内容だけを書き換えた場合も、全バイト再比較で検出する。
- **削除用ハンドルを開いた後の内容の書き換え**: 共有モード (`FILE_SHARE_READ` のみ) により、他者は書き込み・改名・削除のために開けない。既存の書き込みハンドルがあればこちらのオープンが失敗する。
- **削除用ハンドルを開いている間の属性変更・ADS 作成・hardlink 追加**: これらは共有モードでは拒否されない。同じ構成の削除用ハンドルを開いている間に、別プロセスからの ADS の作成、属性の変更 (read-only の付与を含む)、hardlink の追加がいずれも成功し、いずれも同じハンドルでの最終確認で検出できた (§13、PoC 6)。unextract は削除の直前に最終確認 (§8.3 の 4) を行うため、これらが問題になるのは最終確認から削除の指示までの短い間に限られる。その間に追加された ADS は、ファイルと一緒に削除される。追加された hardlink では、削除されるのは unextract が開いた名前だけで、データは他の名前に残る。read-only の付与は削除の失敗となり停止する。
- **性能**: 削除するファイルは、削除直前に ZIP エントリの展開と target の読み取りがもう一度行われるため、そのファイルの I/O は約2倍になる。巨大なファイルでは削除用ハンドルを開いている時間が長くなり、その間そのファイルは他プロセスから書き込めない。
- ZIP の完全な健全性は証明しない。`MISSING` などの内容は読まないため、その破損は検出しない。CRC は敵対的な ZIP への防御にならない (§5.3)。
- `ZipArchive` が開いた時点のメモリ使用量は §11 の上限で制限できない。

## 13. 実装前 PoC の結果

実ファイルの削除と他プロセスとの競合を伴う確認を、作業専用の一時ディレクトリと、その中に作成した VHD (USN ジャーナル非アクティブの NTFS) で実施した (2026-10-02、Windows 11 10.0.26300、.NET 10.0.12)。他プロセスの操作は独立した別プロセスで行った。手順・値・環境の詳細は `PLAN_VALIDATION.md` の「削除 PoC」にある。

| # | 確認した事項 | 結果 |
|---|---|---|
| 1 | §8.1 の削除用ハンドルへの `SetFileInformationByHandle(FileDispositionInfoEx)` による削除 | 成立。0x1 でも 0x3 でも削除できた |
| 2 | 必要な disposition flags | 成立。削除の成立に必要なのは `FILE_DISPOSITION_FLAG_DELETE` だけで、POSIX semantics は `FILE_SHARE_DELETE` 付きの他のハンドルがある場合に名前が消える時点だけを変える (0x1 は全ハンドルが閉じるまで名前が削除保留のまま残り、その間は同名のオープン・新規作成が 5 で失敗する。0x3 は自分のクローズで消える)。§8.3 の 5 で 0x3 に確定した。理由は `PLAN_DECISIONS.md` |
| 3 | 削除の成立の観測 | 成立。指示後・クローズ前に同じハンドルの `DeletePending` が true になり、失敗時 (read-only) は false のまま。`DELETE` ビットを含まない flags でも API は成功を返すため、API の成功では判定できない (§8.3 の 6) |

| 6 | 削除用ハンドルを開いている間の、別プロセスからの ADS 作成・属性変更・hardlink 追加 | いずれも成功し、いずれも §8.3 の 4 の最終確認で検出できた。§12 の記述と一致する |
