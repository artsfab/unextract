# 依頼: unextract の実装PLAN作成(コード変更禁止)

`docs/SPEC.md`(v3)を読み、C# (.NET 現行LTS) による unextract の**実装PLANだけ**を作成してください。

## 厳守事項

### リポジトリの扱い

- リポジトリ内のソースコード、プロジェクトファイル、ソリューション、CI設定を**作成・変更しない**。変更してよいのは `docs/PLAN.md` の新規作成のみ
- `docs/SPEC.md` を**書き換えない**。仕様と矛盾する調査結果が出ても、勝手に仕様を変えず、PLANの「仕様との矛盾・要確認事項」に列挙する

### スパイク(実機調査)の事前確認

スパイクを始める前に、次を確認する。

- `%TEMP%` の実パスを確認する(junction等を解決した最終パスで判定する)
- `%TEMP%` の実パスがCドライブ上でない場合、または別ドライブへのreparse pointを経由している場合は、**実機スパイクを一切行わず**、該当項目をすべて「未確認」としてPLANを作成する
- 確認結果(`%TEMP%` の実パス、判定)をPLANの冒頭に記載する

### スパイク(実機調査)の許可範囲

実機での調査は、次の**許可リスト**の範囲内でのみ行う。許可リストにない場所・操作は、すべて禁止とする。

- 調査用スパイクは、リポジトリ**外**の専用ディレクトリ `%TEMP%\unextract-spike` の中だけで行う。リポジトリには残さない。ただし、結果の再現に必要な最小限のコード断片は PLAN に引用してよい
- **ファイルの作成・変更・削除・ごみ箱への移動は、`%TEMP%\unextract-spike` 配下に自分で作成したダミーファイルだけを対象にする。** これ以外の場所は読み書きしない
- ごみ箱を使うスパイクも、上記のダミーファイルだけを対象にする。実行後、ごみ箱に残ったダミーファイルを後始末する。ごみ箱の中の、自分が作成したもの以外は触らない

次の場所には、**一切アクセスしない**。列挙の漏れがあっても、上記の許可リスト以外はすべて禁止とする。

- Cドライブ以外のすべてのドライブ(Dドライブ等の固定ドライブ、USBメモリ、リムーバブルメディア)
- ネットワークドライブ、UNCパス
- ユーザーホーム、ドキュメント、デスクトップ、ダウンロード等の既存フォルダ
- システムディレクトリ、Program Files、ProgramData

迷ったら実行せず、「未確認」として報告する。

### 環境の保全

- OS設定の変更、ソフトウェア・SDK・グローバルツールのインストール、winget / choco / scoop 等によるパッケージ導入は**禁止**する
- スパイク内で作成する一時的な .NET プロジェクトについてのみ、調査に必要なNuGet依存を追加してよい(取得するのはNuGetパッケージのみ。スクリプトの実行、インストーラや実行ファイルのダウンロードは禁止)
- 7-Zip等の外部ツールが必要になった場合は導入せず、その項目を「未確認」とするか、.NETのコードだけで検証用ZIPを生成する
- 調査終了後、`%TEMP%\unextract-spike` を削除する。削除前に、中にダミーファイル以外が存在しないことを確認する
- 削除したことと、ごみ箱に残ったダミーファイルの後始末結果を、完了時の報告に含める

### 調査の姿勢

- 実機で確認できなかった事項は「未確認」と明記する。推測で断定しない
- 机上調査では、**一次資料を優先**する。Microsoft Learn、Windows SDK / API ドキュメント、.NET API ドキュメント、.NET runtime の公式ソースコードなど
- 一次資料で確認できない事項に二次資料(ブログ、Q&Aサイト等)を使う場合は、その旨と確度(高/中/低)を明記する。二次資料だけを根拠に、安全性に関わる結論(特にA-2、B-5)を確定しない
- すべての根拠に出典(URLまたはドキュメント名)を書く

## 調査項目

### A. ごみ箱 / IFileOperation

1. CsWin32 で `IFileOperation` を呼べるか(STAスレッド要件、COM初期化、single-file publish / NativeAOT との相性)
2. 完全削除へのフォールバックを**抑止または検出**できるか。`FOF_ALLOWUNDO`、`FOFX_RECYCLEONDELETE`、`FOF_WANTNUKEWARNING` などの挙動を、次の範囲で確認する
   - **実機確認してよいのは**: `%TEMP%\unextract-spike` 配下の通常フォルダのみ
   - **実機確認しない**: 別ドライブ、USBメモリ、ネットワークドライブ、ごみ箱容量超過のケース。これらは、一次資料や既知の挙動を根拠に**机上調査**(出典を明記)し、PLANに「人間が手動で確認する手順」(必要な環境、操作手順、期待される結果)を書く
   - 机上調査だけで結論を出さず、「未確認(要手動確認)」と明記する
3. `IShellItem` 経由で対象を渡せるか。パス文字列を経由しない形にでき、ファイルIDによる同一性確認と組み合わせてTOCTOUを狭められるか
4. ファイル単位の削除結果の取得方法(`IFileOperationProgressSink`)
5. `--delete-permanently` の実装方式(`File.Delete` で足りるか、読み取り専用属性の扱い)
6. `Microsoft.VisualBasic.FileIO.FileSystem.DeleteFile` では要件を満たせない理由の確認(フォールバック検出の可否)

### B. Windowsパス / reparse / hardlink

1. 実パス解決(`GetFinalPathNameByHandle`)と、reparse検査の併用方法
2. target自体、全中間ディレクトリ、対象ファイルの `FileAttributes.ReparsePoint` 検査の実装方針
3. クラウドプレースホルダ(OneDrive等)の扱い。reparse point として検出できるか、スキップした場合の実用上の影響(実機確認は許可範囲内で再現できる場合のみ。それ以外は机上調査)
4. ハードリンク数の取得(`GetFileInformationByHandle`)
5. ファイルID(`FILE_ID_INFO`)の取得と、比較時・削除直前での同一性確認の実現可否
6. 通常パス(`\\?\` なし)での260文字超パスの挙動。.NET側とShell API側で分けて確認する(許可範囲内のみ)
7. 大文字小文字の扱い。比較は `OrdinalIgnoreCase` で足りるか、ディレクトリ単位の大文字小文字区別設定(WSL連携)をどう扱うか(机上調査中心)
8. `%USERPROFILE%`、Windowsディレクトリ、`Program Files` 系、`ProgramData` の**取得方法**(環境変数・既知フォルダAPI)と、`--target` 拒否判定の実装方針(§4)。これらのディレクトリの中身には触れず、パス文字列の取得のみ行う

### C. ZIPライブラリ(System.IO.Compression)の挙動

1. エントリ名のエンコーディング。UTF-8フラグなしのエントリがどう解釈されるか、`entryNameEncoding` にCP437を指定する場合に `CodePagesEncodingProvider` の登録が必要か。**SPEC §9(UTF-8フラグなしはCP437)と実装が一致するか**を実機で確認する
2. 暗号化エントリの検出方法(汎用ビットフラグを読む手段があるか)
3. エントリのCRC-32・サイズの取得可否。ヘッダー値と実データが食い違う壊れたZIPで、例外が出るか、黙って通るか
4. 重複エントリ(同一パス、大文字小文字違い)が `Entries` に全て列挙されるか
5. `ExternalAttributes` からのsymlink判定(Unixモード上位16ビット、`0xA000`)
6. ストリーミング読み出し時にエントリ全体をバッファしないか。メモリ使用量を実測する
7. 宣言サイズが巨大なZIP、宣言サイズと実データが食い違うZIPでの挙動
8. `System.IO.Hashing.Crc32` の利用可否と依存の評価

(検証用ZIPは、`%TEMP%\unextract-spike` 配下に、.NETのコードで自分で生成する。ディスク使用量が大きくなるテストは、`%TEMP%` の空き容量を確認し、上限を決めてから行う)

### D. ハードリミット

- SPEC §6.1 の初期案(エントリ総数 100,000、1エントリ 16 GiB)の妥当性を、許可範囲内で可能な実測で評価する
- チャンクサイズを複数試し、スループットとメモリ使用量から推奨値を出す
- 上限超過のテスト方法(巨大な宣言サイズを持つZIPを生成するヘルパーの設計)

## 決定が必要な方針案(PLANで推奨を示す)

SPECで「方針案・未確定」としたもの:

- システムディレクトリ配下も `--target` として拒否するか
- クラウドプレースホルダをスキップするか

それ以外にも、調査の結果、判断が必要になった点があれば、選択肢とトレードオフを添えて列挙してください。
