# 依頼: PLAN の全面再監査と更新(SPEC v4 を唯一の正とする)

`docs/SPEC.md`(v4)を唯一の仕様上の正として、`docs/PLAN.md` を**全面的に再監査し、更新**してください。旧PLANへの追記ではありません。旧PLANは旧SPEC(v3)前提で書かれており、旧前提が残っている可能性があります。

実装には進みません。コード、プロジェクトファイル、CI設定は作成しないでください。

## このセッションの作業範囲

このセッションの作業は、**`docs/PLAN.md` の更新と完了報告まで**とする。独立レビュー、事実検証、PLANの再修正、Phase 1 は実行しない。これらは別セッションで、人間の指示の後に行う。

このセッションは権限設定で制限されている。シェルは使用しない。追加の実機調査は行わない。実機確認が必要な事項は「未確認(要実機)」としてPLANに残す。操作が権限設定によって拒否された場合は、別の手段で回避せず、拒否された内容を報告して停止する。

## 編集範囲

- 編集してよいのは **`docs/PLAN.md` のみ**
- `docs/SPEC.md`、ソース、テスト、project / solution、CI設定など、他のファイルは変更しない
- SPEC と矛盾する、または SPEC が曖昧な点は、SPEC を直さず、PLAN の「SPECとの矛盾・要確認事項」に列挙する
- 読んでよい `docs/` 配下は `SPEC.md` と `PLAN.md` のみ。過去のレビュー・検証結果・決定メモは読まない
- ファイル探索を前提とせず、`docs/SPEC.md` と `docs/PLAN.md` を明示的に読み込んで作業する

## 進め方

1. **再監査(更新より先に行う)**: 旧PLANの全節を、SPEC v4 の §1〜§19 およびテスト #1〜#54 と突合する。旧SPEC前提の記述、v4 と矛盾する記述、v4 で不足している記述を、一覧にする(PLAN 内の「再監査結果」節に記載)
2. **更新**: 再監査結果に基づき PLAN を更新する。旧い記述は、v4 に合わせて書き換えるか、削除する。残す場合は理由を書く
3. **自己点検**: 更新後の PLAN から、v3 前提の記述が残っていないかを再度確認する

## SPEC と PLAN の責務分離

- SPEC が実装方式を固定していない事項を、PLAN 側から SPEC 上の決定事項に**昇格させない**
- PLAN に書く実装方式は「**SPECを満たすための現時点の実装案**」と明記し、SPEC の要件とは区別する。各案に、満たすべき SPEC の節を紐づける
- 案を変更しても SPEC が変わらないこと(SPEC要件 → PLAN案 の分離)を、構造として保つ
- **PLAN作成者が SPEC の緩和を決定してはならない。** SPEC を満たせない可能性がある場合は、SPEC を変えず、未解決事項として人間に判断を戻す

## 事実の区別

PLAN 中の記述を、次の4種に分けて明示すること。

- **過去スパイクの実機結果**(旧PLANに記録された過去の観測。今回再検証した事実ではない。観測条件を併記する)
- **一次資料で確認した事実**(文書名+節。自分の言葉で要約)
- **推測・設計判断**
- **未確認(要手動確認 / 要実機)**

検証できなかったことを「確認済み」と書かないこと。過去の実機結果は、観測条件が不足する場合、一般保証として使わない。旧PLANの「確認済み(実機)」という語は継承せず、上記の区分名に置き換える。

## 必ず反映する事項

**1. Phase 3 の Recycle ゲート**
- SPEC §10.1 により、「事後検出」は事前保証の代替にならない。これを明記する
- ゲート: Recycle 実装着手前までに、完全削除へフォールバックしないことを**削除開始前に保証する条件**を確立できなければ、Recycle 機能を MVP から除外する。`--delete-permanently` を MVP に残すかは、その時点で別途決定する(今は決めない)
- 保証条件が確立できていない間の既定動作は「削除しない」(§2、§10.1)

**2. `ITargetRoot` と子要素の解決(§7.2)**
- 検証済みの親ディレクトリ個体を起点に、単一成分ずつ解決する契約として再設計する
- 第一候補の実装案(例: ハンドル相対のオープン)と、その代替案、採用に必要な確認事項を分けて書く
- 検査・再検証・削除のすべての解決に適用されることを、抽象のインターフェースに反映する

**3. target の初期化順序(§4、§7.2)**
- 最終成分の reparse 検査 → 実パス解決 → 個体の保持、の順序
- 祖先の junction を個体として固定できない場合は、終了コード 3
- 拒否リスト(システムディレクトリ配下を含む)の判定の位置づけ

**4. ディレクトリ個体の寿命(§10.2)**
- 削除したファイルの祖先ディレクトリを、同一個体として再確認する設計
- ハンドル保持、ID の記録、その寿命。ID は時間をまたぐ一意性を保証しないことを前提に書く
- 子から親への削除順序と、削除マークと実際の消滅の違い

**5. クラウド識別(§7.3)**
- 識別機構の初期化失敗は、削除開始前に終了コード 3。個別の状態取得失敗は、当該対象を `ERROR`
- 識別する前に対象の内容を読まない(ハイドレーションを起こさない)
- 保証は、識別できることを確認した範囲に限る。旧PLANの README 案「同期状態にかかわらず削除対象にならない」は撤回する

**6. 名前付きデータストリーム(§7.4)、読み取り専用(§10.1)**
- 内部 reason `NamedDataStream`(外部カテゴリは `SKIPPED_SPECIAL_FILE` のまま)。ファイルとディレクトリの両方
- 読み取り専用 + 内容一致は `ERROR`(`--delete-permanently` も同じ)。属性を無視する削除手段は採らない。旧PLANの Q-9 の推奨(一致すれば削除)は撤回する

**7. archive-level rejection の全体ゲート(§12)**
- archive-fatal / unsupported archive format / entry-local error / 内部安全性エラーの分類
- 削除開始前に、全エントリの構造検証を完了する設計(Local Header の検証を分類フェーズで行う等)
- **§12.4 の分類原則**(独立性を確認できなければ archive-fatal)に基づく、異常の分類表を作る
- APPNOTE 上可能な形式と、「MVP で意図的に拒否する形式」(§12.5)を、混同しない

**8. ZIP 読み取り方式**
- custom reader を既定路線として盲目的に維持しない。**§6.2 の4能力を満たせるか**を、Phase 1 のゲートにする
- .NET 10.0.12 で、公開 `DeflateStream` の入力 EOF が、Deflate の正常終端を保証しない経路があること(旧調査・一次資料)を反映し、正常終端の確認方法を設計に含める
- **撤退条件**(次の文言を、そのままPLANに入れる):

  > §6.2 の能力を満たせない場合は、別方式を検討する。それでも満たせない場合は、SPECを変更せず、Phase 1 のゲート未達として停止し、「SPEC変更が必要となる可能性がある未解決事項」として人間に判断を戻す。PLAN作成者がSPEC緩和を決定してはならない。

- 対象バージョンの確認は、ブランチではなく、該当するタグのソースで行う

**9. リソース制限(§6.1)**
- メタデータ総量、1エントリの名前長、パスの深さの上限を追加する
- **具体値は、測定条件付きの実測が得られるまで確定値として扱わない**。旧PLANの「約35 MB」は名前長が不明で、根拠にしない
- 上限は、性能値であると同時に、MVP の受理範囲を定める互換性上の上限であることを書く

**10. Shell 結果の状態機械**
- `GetAnyOperationsAborted` の呼び出しと扱い、`FOF_NO_CONNECTED_ELEMENTS` の要否、Post コールバック欠落・結果取得失敗・中断・関連項目の追加への対応
- 成功を積極的に確認できた場合だけ「削除済み」とする
- 内部安全性エラーの reason を分離する(完全削除の発生 / 対象の同一性の不一致 / 構造検証で検出されなかった異常)

**11. Ctrl+C とキャンセル**
- PLAN 上の設計検討に留め、SPEC 要件として扱わない。削除 API のキャンセルポイントと状態遷移を調べてから案を書く

**12. NativeAOT**
- 未検証のまま採用条件にしない。配布形態は framework-dependent または self-contained single-file を基本とし、NativeAOT は実機確認後の判断とする
