<a id="filesystem"></a>
## 処理モデルとファイル安全性

<a id="current-state"></a>
### 現在状態と同じハンドル

[実行契約](SPEC.md#execution)は、analyzeやentriesを削除の許可証にしない。analyze後には内容だけでなく個体・名前・権限も変わり得るため、deleteが現在状態を検証する。確認待ちに数万件のハンドルを保持すると資源を消費し他アプリを長時間妨げる。1件の検査・比較・削除を同じハンドルへ限定して、検査した個体と削除する個体を一致させる。比較は各操作で1回であり、先行analyzeの観測を引き継がない。

OpenFileByIdではtarget外へ移した個体も開けるため、結局最終パス確認が要る。親を別のパスopenで確認すると対象openとの間に別の名前解決が入る。同じハンドルで得るUSN親IDを使う理由はこの隙間を避けるためである。USNジャーナル非アクティブのNTFSでも取得できたことは、機能のないFSの保証ではない。

Core S05/S06は呼び出し順・同じハンドル・ZIP Open回数、A08はメタデータを書き戻した内容変更と同名再作成を確認する。ハンドル構成・寿命・API変更時はWinの個体保証も再確認する。重要な原観測: PoC 4 (2026-10-02、Windows 11 10.0.26300、NTFS、自作USN非アクティブVHD、.NET 10.0.12)。

<a id="identity-path"></a>
### 親IDと最終パスを省かない理由

[削除順序](spec/filesystem.md#delete-flow)で両方を確認する。同名の別親へ同じ個体を移すとFile IDと最終パスは同じでも親IDが変わる。途中のjunction化・大小文字だけの改名では親IDが同じでも最終パスが変わる。片方だけの最適化はそれぞれを見落とす。Core/WinのS22・S23、最終確認S27が回帰を担う。経路解決や同一性のAPIを変えるときは両ケースを再確認する。

<a id="hardlink-parent-id"></a>
### hardlinkの親IDは開いた名前の親とは限らない

[非削除例外](spec/filesystem.md#hardlink-parent-id)は、USNがどのリンクの親を返すかを保証しない観測への対応である。2026-10-03のWindows 11実測では別ディレクトリの2名をそれぞれ削除用に開いても元の名前の親が返り、追加名では親が一致しなかった。CIのS20にも不一致がある。返すリンクの環境差の理由は未確認。

リンク数を確認した非dir・非削除保留の対象を非削除へ倒す場合にだけ例外を認める。一般の削除候補を親不一致で続行させる根拠にはならず、取得失敗も緩めない。Core/Win `S20_HandleChecksAreNotSkipped`、`S20_HardLinksInDifferentParents_AreBothSkipped`とCoreの`S20_ParentCheckIsRequiredExceptForConfirmedHardLinks`と[現在の実装](../src/Unextract.Core/Deletion/SequentialDeleter.cs)を確認し、OS/USN取得・検査順序変更時にリンク別の値と非削除を再確認する。

<a id="sharing-limits"></a>
### 共有モードで防げる変更と残る窓

[ハンドル構成](spec/filesystem.md#handles)はデータアクセスを伴う共有モードを使う。FILE_READ_ATTRIBUTESだけの保持では改名を防げず、root保持にLIST_DIRECTORYを含める。削除用openは既存writerやDELETE非共有readerと競合し、開いた後の書き込み・改名・削除openも妨げる。一方、属性・ADS・hardlink追加は排除できないため、比較後にM0全項目を再確認する。

Fastの最終確認はM0取得直後で冗長に見えるが、省略するとモード別の安全性分岐が増える。両モードで同じ最終確認を残す。最終確認から指示までの競合窓は消せず、メモリマップも未確認である。[限界](spec/filesystem.md#limitations)と[未確認範囲](OPEN_ISSUES.md#observations)を越える保証にしない。

V5のroot改名は同一プロセス別ハンドル、PoC 5/6は別プロセス。2026-10-02、Windows 11 Home 10.0.26300、NTFS、SDK 10.0.401 / .NET 10.0.12、当時の削除用ハンドル構成での観測である。現行回帰はWin S24・S25・S27、root保持はHandleOpenerTests。構成・共有モード・Windows変更時は再確認する。

<a id="disposition"></a>
### 削除指示と成立を分ける理由

[指示・成立確認](spec/filesystem.md#delete-flow)はAPI成功だけでDELETEDにしない。DELETEなしのflagsでもAPI成功を返し何も削除しない観測があるため、同じハンドルのDeletePendingを確認する。指示後NumberOfLinksが0になる観測は公式の裏付けがないため、成立条件にしない。

POSIX semanticsを含める理由は名前消失の時点である。DELETEだけではDELETE共有の他ハンドルが閉じるまで名前が削除保留で残り、同名open/作成がアクセス拒否になる。採用flagsでは自分のcloseで名前が消え、他のreaderは読み続けられる。read-onlyを無視しないので最後の防壁が残る。指示後に成立が分からないSTOPは対象残存を保証できない。

2026-10-02のPoC 1〜3/5、Windows 11 10.0.26300、NTFS、.NET 10.0.12、他者の操作は別プロセスで観測。現行[Core逐次S28/S31/S32/S33](../tests/Unextract.Core.Tests/SequentialDeleteTests.cs)と[Win DeletionHandleTests](../tests/Unextract.Windows.Tests/DeletionHandleTests.cs)が回帰を担う。API/flags/成立判定変更時は名前消失とDeletePendingを再確認する。

<a id="open-failures"></a>
### 識別確認で分かることとS09

[失敗境界](spec/filesystem.md#failure-boundary)は、共有違反・アクセス拒否以外を推測で続行しない。アクセス拒否はACL、dir/junction差替え、削除保留で同じコードになり理由を区別できない。別openによる識別確認は拒否された個体や理由を証明しないが、一致しても非削除で続行するだけなので採用できる。失敗・不一致は停止する。analyzeは分類を確定できないためFATALである。

分類のために比較用ハンドルで開き直すと処理経路が増えるため行わず、削除用openに失敗した対象の内容一致・不一致は判定しない。

ZIP自身は保持中のDELETE非共有により削除用openが共有違反となり、識別確認一致でDELETE_FAILEDとなる。専用の事前SKIPPED分岐は一般則を重複させるため設けない。後続は独立に検証できるので続行する。2026-10-03に明示的に確定した扱いであり、判断待ちではない。回帰は[Core](../tests/Unextract.Core.Tests/SequentialDeleteTests.cs)/[Win](../tests/Unextract.Windows.Tests/Integration/SequentialDeleteIntegrationTests.cs)の `S09_ArchiveItselfIsNotDeleted`、S16〜S18。openエラー・識別確認の範囲を変えるときに再確認する。

<a id="acl"></a>
### ACLを比較対象にしない理由

[ハンドルの権限](spec/filesystem.md#handles)はWindowsの通常の権限判定を受け入れる。対象DELETE拒否だけでは親DELETE_CHILDによる削除を防げない。安全に検証した個体をWindowsが削除できるなら、ACL自体を追加の比較対象にはしない。指示時の拒否から原因を確定できず、検査後の前提も崩れ得るので、その失敗はSTOPを維持する。

ACL・権限判定・検査順序を変更するときは、[S34の観測範囲](OPEN_ISSUES.md#observations)を確認する。再現時は親DACLが子のChangeTimeを変える[fixture上の罠](TESTING.md#reproduction)を避ける。

<a id="real-names"></a>
### 実名解決と列挙結果の再利用

[実名確認](spec/filesystem.md#real-names)は検証済みdirの列挙をOrdinal照合する。8.3名を返さない列挙なら短名だけの一致を自然に避け、名前・属性・tag・128bit IDを同時に得られる。FindFirstFile検索は短名でも一致し、毎回パス解決し、見つからない/親消失/アクセス拒否の振り分けと追加実名比較が必要になる。巨大dirに少数の候補がある場合は列挙が遅くても、一貫性と安全性を優先した。UNCではサーバー側のFS名・IDの安定性・共有意味論をクライアントから保証できず対象外にする。

列挙中の改名には見落としや旧名と新名の両方があり得る。同名重複は最初を採用して決定的にし、後で開いたID/最終パスを確認する。見落としは非削除なので安全側。照合しなかった名前を保持・表示しないことで無関係ファイルに作用しない。

逐次削除でも照合結果を再利用する。事前ZIP構造検査により削除した最終名を後続が最終成分や親として再使用せず、dirは削除せず、dir内の削除開始前に列挙を終える。POSIX closeで自分の削除保留名も残らない。古い「存在」はopen/照合で検出し、古い「不存在」は非削除となる。再列挙は安全性を増やさず総量を二乗に増やし得る。

V7/PoC 8 (2026-10-02、同Windows・NTFS・runtime) の列挙観測を現行T06/T14/T15/S35/S36で回帰する。列挙直後改名の組合せは推定として[未確認](OPEN_ISSUES.md#observations)に残す。列挙API/キャッシュ/名前照合変更時に再確認する。

<a id="special-precheck"></a>
### 事前判定は非削除だけに使う

[特殊判定](spec/filesystem.md#special-files)を列挙属性で先に行うのは、dirへ削除用openを試みるとアクセス拒否→識別確認不一致で全体STOPになり、通常のdir不一致に過剰に停止するためである。削除用へBACKUP_SEMANTICSを足す案は検証済み構成を変え、dirをDELETEで開くことになる。別openの識別確認からSKIPPEDを追加する案も根拠が弱く分岐を増やす。

古い列挙でも先行判定は非削除側にだけ働く。通過した個体をハンドルで再検査するので、属性一致の一般保証に依存しない。許可リストは通常のローカル読み取りが可能な属性に限定し、未知ビットは保守的に非削除へ倒す。Core/Win S19/S20とT16、属性ビットはFileAttributeRulesTests。属性/API変更時はS38の限定付き観測も確認する。

<a id="zip-runtime"></a>
## ZIPとruntime

<a id="zip-decoding"></a>
### 公開APIで得られない情報への保守的対応

[復号規定](spec/zip.md#decoding)はCP437を明示する。未指定ではフラグなしもUTF-8になり、不正UTF-8は例外なしに置換される。生名が公開されないため正当な置換文字まで含めて拒否する。作成元OSも公開されないため、種別をExternalAttributesと末尾区切りから保守的に判定し、矛盾した種別を受け入れない。

2026-10-02、SDK 10.0.401 / runtime 10.0.12、Windows 11 Home 10.0.26300でのV1観測。Z06/Z07とEntryTypeTests、ZipArchiveSourceTestsが回帰を担う。SDK/runtimeや復号API変更時に再確認する。

<a id="zip-content"></a>
### CRC・長さ・暗号化をruntime任せにしない

[内容検証](spec/zip.md#verification)の補助検査は、runtimeがCRC不一致を検出しない、Deflate途中切れを例外なしに短く返す、暗号化フラグ付きでも平文fixtureを読める、宣言Lengthで出力が切られるという観測を補う。公開Crc32とIsEncrypted、実測バイト列で検査でき、独自構造パーサ/reflectionは不要。StoredのLength超過と不足、Deflateの不足も区別する。

CRCは作成者がデータと一緒に書き換えられるので敵対的ZIPへの防御ではない。Strictの根拠は全バイト一致である。内容不一致でもZIPを終端まで読むのは、不一致位置によってMODIFIED/FATALが入れ替わらないようにするため。Local HeaderとCD/DDの照合、圧縮領域の重なりなどの健全性証明は目的外である。ZIP64/DD/SFXも公開ライブラリへ委譲し、独自形式判定を足さない。

V2/V3は2026-10-02、同Windows・SDK・runtime、ヘッダーを変更したfixtureの観測。C01/C03/C07を単体ZipArchiveで読むC13、C/Z系列が継続確認する。パッチ更新でも結果が変わり得るため、runtime更新時は観測と製品の検出を分けて再確認する。

<a id="zip-limits"></a>
### 受理範囲と上限

[ZIP上限](spec/zip.md#limits)はMISSINGや選択外にも宣言側を適用する。target/操作/entriesから独立に受理を決め、作成者が書ける巨大宣言値の桁あふれを早期拒否し、受理範囲を固定するためで、読まないデータそのものが危険だからではない。実際に読む量も独立に検査する。Central Directory事前割当を独自パーサなしで制限できない限界は残る。R03/R06/R07/R08/R09を確認し、上限の対象・計上単位・時点を変えるときは選択外とMISSINGのfixtureも再確認する。

<a id="rar"></a>
## RAR

契約は[RAR仕様](spec/rar.md)。ここには方式・受理範囲・委譲の判断と、それを支える観測だけを置く。観測は2026-10-08〜09、Windows 11 Home 10.0.26300、.NET SDK 10.0.401 / runtime 10.0.12、UnRAR.dll 7.23.0 (`RARGetDllVersion`=10、x64)、WinRAR 7.23 (Rar.exe / UnRAR.exe)、SharpCompress 0.50.4、7-Zip 24.01 (照合用)。観測は製品外の使い捨てのPoC (3方式の比較と、[DLLの使い方](#rar-dll-usage)の確認) で行い、PoCと生の出力は残していない。判断に必要な観測・条件・限界は本節に要約したものが全てである。PoCの比較はメモリ上のtargetに対するもので、製品経路 (実ハンドルのanalyze/delete) は[TESTING](TESTING.md#rar)の自動試験と実物のRARのローカル検証が確かめる。**DLLの版を変えるとき、または下の判断の前提を変えるときは、[TESTING](TESTING.md#rar)の版の変更の手順で観測を新しい版で再確認する。**

<a id="rar-backend"></a>
### UnRAR.dllを採る理由

同じfixture・同じ規則で3方式を比べた (WinRAR製の実物、SharpCompressの実物RAR4、自作の異常系の39件)。要求と一致しなかったのは、SharpCompress 10件、UnRAR.dll 1件 (下のNTFSストリーム)、UnRAR.exe 1件。

- **SharpCompress** (MITのC#移植。依存なしで配布とCIが最も簡単): 作成元OSを読み捨てるため属性の意味を決められず、WinRAR 7.23 が「インデックス対象外」のファイルに保存する 0x2020 を Unix の文字デバイスと区別できない。保守的な規則では WinRAR 製で受理すべき7件中6件を拒否した。ほかに、Unix名の `\` を `-` に変換する (どの展開ツールの名前とも一致しない)、password check の無い暗号化を検出しない、BLAKE2 の値を CRC 欄に入れて CRC 不一致になる、辞書サイズが事前に分からず 2 GiB 以上で例外になる、末尾の切り詰めを一部見逃す (`RarHeader.TryReadBase` が例外を捕捉して列挙を終える)。多くは非削除に倒れる誤拒否だが、受理範囲を要求どおりにできない。属性規則を緩めれば受理できるが、「判定できないエントリを通常ファイルとみなさない」を弱めることになる。再評価するなら 0.50.4 のソース上の原因 (`FileHeader.cs` の Host OS・名前変換・暗号化判定・BLAKE2、`Unpack.unpack_cpp.cs` の辞書確保) から確認する。
- **UnRAR.exe (CLIの子プロセス)**: 出力のラベルが `rar.lng` で翻訳され、日本語の言語ファイルがあると解析器が0件のまま成功を返した (言語を固定するスイッチが無い)。属性は記号表記だけ。エントリを `p` で取り出すたびに先頭から走査するので、10万件の全件比較は1件0.58秒 (全体で約16時間) かかった。名前をマスクとして扱う照合の意味論も委ねることになる。切り詰めは終了コード1で最もよく検出したが、単独では使えない。
- **UnRAR.dll (rarlab公式、WinRARと同じコード)**: 判定に必要な情報 (作成元OS、生の属性、暗号化 (password checkの無いものを含む)、ハッシュの種類、辞書サイズ、リダイレクト、Solid、分割、ヘッダーの暗号化) が公開APIで揃い、名前の変換がWinRARの展開と一致する。新たに持ち込むのは、プロセス内のネイティブ解析 ([下記](#rar-in-process)) と、DLLの入手・版の管理である。

性能 (10万件のStored RAR5): Prepare 0.68秒、全件のStrict比較 92秒 (1件約0.9 msの固定費)。256 MiB (-m3) の比較は0.28秒。

<a id="rar-pinning"></a>
### 版をハッシュで固定し、署名検証にしない理由

名前の変換、切り詰め・NTFSストリームの扱い、ハッシュの検出は、いずれも7.23での観測である。署名検証は rarlab が将来署名する未検証の版も受け入れ、観測の固定 ([ZIPのruntime](#zip-content)と同じ考え方) と合わない。また `WinVerifyTrust` (wintrust.dll) が要り、Win32の使用範囲 (kernel32とFSCTL) を広げる。版の固定はインストール先に書き込める攻撃者への防御ではなく (その攻撃者はexe自体を置き換えられる)、挙動を検証済みの版に保つためのものである。DLLはWinRARのインストール先に含まれず (7.23で確認)、rarlabが別途 `unrardll-<版>.exe` (win.rar GmbHの署名付き) として配布する。ライセンス (`license.txt`) は freeware で任意のソフトウェアで無料で使えると書かれているが、再配布 (同梱) を許す・禁じる文言は無く、rarlabの配布ページにも配布条件は無い (2026-10-09確認)。そのため、DLLをリポジトリにも製品の配布物にも含めず、利用者がrarlabから採用版を入手して読み込み元に置く方式とした (2026-10-09の決定)。開発・CIでも同じく、照合スクリプト ([TESTING](TESTING.md#rar)) でリポジトリ外に用意する。DLLが無い利用者でもZIPは従来どおり使え、RARだけが原因と置き場所を示すFATALになる ([版の固定](spec/rar.md#pinning))。DLLが無いときに別方式へ自動で切り替えないのは、受理範囲と挙動が方式で変わるためである。

<a id="rar-dll-usage"></a>
### DLLの使い方を支える観測

2026-10-09、上記と同じ環境。採用版は rarlab の `unrardll-723.exe` (Authenticode有効、署名者 win.rar GmbH) の `x64\UnRAR64.dll` で、SHA-256 は `894b7d2db8d6363eb12f30c7b89f48eab9e71963b8b438675bdd64c12dd59bcc`。いずれも7.23での観測で、版を変えたら確かめ直す。

- **照合とロードの対応**: DLLファイルを `FileShare.Read` で開いたまま `LoadLibraryExW` (絶対パス、`LOAD_LIBRARY_SEARCH_DLL_LOAD_DIR | LOAD_LIBRARY_SEARCH_SYSTEM32`) でロードできた。保持中は他者の書き込み・DELETEアクセスのopenが拒否されるので、照合したファイルとロードしたファイルが同じになる。
- **最終パスでのopen**: 保持中のハンドルの最終パス (`\\?\` 付き、351文字の長いパスを含む) を一覧用・内容読み取り用とも開け、列挙・`RAR_TEST` が成功した。DLLは既定で非共有のopenを要求するが、`FileShare.Read` の保持中でも開け、DLLが開いている間も他のRead openは成功する (DELETEは保持で拒否)。`ROADOF_SHARED` は要らない。保持を `FileShare.None` にすると開けない。
- **コールバックの中止**: データのコールバックで -1 を返すと、その `RAR_TEST` は `ERAR_UNKNOWN` を返し、以後そのエントリのコールバックは来ない。次のヘッダーの読み取りは失敗する (`ERAR_BAD_DATA`・`ERAR_UNKNOWN`) ので、中止したセッションは前進させない。close は成功する。
- **チャンクの長さ**: `UCM_PROCESSDATA` は1回に最大4 MiB (4,194,304 B) を渡した。比較用バッファ (64 KiB) より大きいので、検証器はチャンクを分けて比較する。長さはDLLの内部実装による観測で、契約ではない。
- **大きな辞書**: DLLの既定上限は4 GiB。超える辞書の `RAR_TEST` で `UCM_LARGEDICT` が1回呼ばれ (P1が辞書、P2が上限、KiB)、1を返すと続行し、0と-1では `ERAR_LARGE_DICT` になる。`RAR_SKIP` では呼ばれない。unextract は -1 を返す (1 GiB超はPrepareで拒否済み)。
- **エラーの状態はプロセスで1つ** (2026-10-09、Windows.Testsの並列実行での観測とUnRAR 7.2.3のソース。ソースは採用版7.23と同じ版と見なしたもので、DLLのバイナリとの同一性は未確認): DLLのエラーの状態は大域変数 (`global.hpp` の `ErrHandler`) で、`RAROpenArchiveEx` でだけ消去され、`RARReadHeaderEx`・`RARProcessFileW` は成功時もその状態から結果を返す。同じプロセスで別スレッドが別のハンドルを使うと、一方の中止・CRC不一致が他方の `RAR_SKIP`・`RAR_TEST` の結果 (`ERAR_UNKNOWN`) に漏れた。unextract は1プロセスで同時に1つのハンドルだけを単一スレッドで使い (一覧用を閉じてから内容読み取り用を開く。Core・Windows・CLIはスレッドを作らない)、読み取りの失敗・中止の後はそのセッションを進めないので、判定に影響しない。DLLを同じプロセスで使うテストは直列に実行する ([TESTING](TESTING.md#rar))。
- **ハッシュの無いヘッダーの `FileCRC`**: DLLはハッシュの種類によらず内部のCRC-32の値を `FileCRC` に詰めるが、ハッシュの無いエントリ (RAR5のディレクトリなど) ではその値が初期化されない (`HashValue::Init(HASH_NONE)` はCRC32を設定しない)。ハンドルの最初のヘッダーでは未初期化のメモリ、以降は直前のヘッダーの値になり、一覧と内容読み取りのヘッダーの照合が間欠的に食い違った (先頭がディレクトリのRARで観測)。そのため `FileCRC` は種類がCRC-32のときだけ値として扱う ([照合](spec/rar.md#session)の「ハッシュの種類と値」)。`Hash` はBLAKE2のときだけDLLが書くので、呼び出し側が毎回消去しておけば種類によらず比べてよい。
- **構造体**: 同梱の `unrar.h` (`#pragma pack(1)`) と sizeof・offset が一致した (`RARHeaderDataEx` 10244 B、`RAROpenArchiveDataEx` 176 B)。
- **単一ファイルpublish**: `IncludeNativeLibrariesForSelfExtract=true` ではDLLがexeに取り込まれるので、DLLの項目に `ExcludeFromSingleFile=true` が要る。付けるとexeと同じフォルダーに置かれ、`Environment.ProcessPath` はpublish先のexeを指す。

<a id="rar-names"></a>
### 名前をDLLの変換後の名前にする理由

DLLは変換前の名前を公開しない。変換された可能性のある名前を拒否するには `_` を含む名前を広く拒否するしかなく、誤拒否が実用に耐えない。観測した変換 (Unix名の `\`・`:` → `_`、`/` → `\`) は UnRAR.exe `x` が Windows で作るファイル名と一致し (同じ `ConvertFileHeader` のコード)、「WinRARで展開したファイルを消す」という主な用途に合う。7-Zipは `a\b.txt` をディレクトリ `a` と `b.txt` として展開するので、7-Zipで展開したtargetとは対応せず `MISSING` になる (非削除)。変換は1対1でないが、変換後の名前に重複・衝突の検査をかけるので、2つのエントリが同じtargetを指すことはない。Strictの削除の根拠は名前に依存しない。

RAR4のUnicodeでない名前は、DLLが実行環境の設定で復号する (どのコード ページを使うかは未確認)。ZIPでは名前の解釈を実行環境に依存させない (CP437固定) としたが、RAR4では名前の符号化を示す情報が公開APIで得られず、非ASCII名をすべて拒否すると正当なUnicode名まで拒否されるため、DLLの復号を受け入れる製品判断とした。同じ環境のWinRARの展開名とは一致する見込みが高い (推定)。Strictは全バイト一致なので削除の根拠は変わらず、Fastで対応先のパスが環境で変わることを許容する。

<a id="rar-content"></a>
### 内容検証の委譲と切り詰め

- **BLAKE2**: 公式の `System.IO.Hashing` に BLAKE2sp が無く、暗号ハッシュを自前で実装・保守するのは MVP に重い。ハッシュは削除の根拠ではなく、ZIPで自前のCRC照合を置いたのは `ZipArchive` が不一致を検出しない観測を補うためである。DLLはBLAKE2・CRC32の不一致を `BAD_DATA` で返すことを自作のRARで観測したので、版の固定と回帰で管理できる。CRC-32 は既存の照合をそのまま使えるので併用する。DLLの照合結果は全データを渡した後に返るため、判定を `RAR_TEST` の成功の後に確定する。
- **切り詰め**: DLLは切り詰めの警告を呼び出し側へ返さず、ファイル長とブロック位置がちょうど一致すると警告すら出さない (RAR 1.5互換。`dll.cpp`・`arcread.cpp`)。全位置で切り詰めると、WinRAR製の276位置中251でエラーにならずエントリが減った。UnRAR.exeでの補助検査はWinRARのインストールと外部プロセスを要し、末尾の自前確認は独自解析になる。ZIPでも「全エントリ」は `ZipArchive` が報告したものであり、健全性の証明はしない ([委譲](spec/zip.md#runtime)) ので、列挙できた範囲を全エントリとする。欠けたエントリは処理されず削除も増えないが、Fastではデータの途中で切れたエントリが `SAME_SIZE` になり得る (Fast契約の範囲)。
- **NTFSストリーム (`-os`)**: DLLは本体に続く service header のデータを同じ呼び出しのコールバックで渡す (宣言8 Bに16 B)。超過分を読み捨てると、それが本当に service データかを公開APIで区別できず、チャンク境界とファイル境界の一致も保証されないので、長さの基準を緩めずStrictでFATAL/STOPとする。ACL (`-ow`) など他の service header が混ざるかは未確認。
- **非候補の `RAR_SKIP`**: 非Solidでは `RAR_SKIP` はシークだけで展開しない (`dll.cpp`、自作のRARで、1件目の破損を読まずに2件目がMATCHEDになることを観測。製品の回帰はU65)。これによりZIPと同じく `MISSING` などの内容を読まない。
- **前進の失敗を次に処理するエントリに帰属させる**: 処理対象外・ディレクトリを通過中の失敗をその位置のエントリのSTOPにすると、`entry` を出さないエントリが原因になり、機械可読出力の出力範囲・件数とGUIの承認範囲の検査 (承認外の `entry_name` は結果不明) と矛盾する。`RAR_SKIP` の失敗も同じ経路に入れ、次に処理するエントリ (target 未接触) のSTOPとすれば既存の `STOPPED`・未処理の境界がそのまま使える。原因エントリと検出位置がずれるため、検出位置を説明に含める。コードは既存の `ARCHIVE_CHANGED` (並びの不一致) と `ARCHIVE_UNREADABLE` (読み取りの失敗) を使う。
- **一覧と内容読み取りの2回のopen**: DLLは巻き戻せないので、Prepareの全件検査と内容の読み取りは別のopenになる。内容読み取りのopenをPrepareで行うのは、開けない場合を削除0件の境界 (`run` の前) に収めるためで、Prepareはopenだけに限り、内容の読み取り・展開・全バイト検証はエントリの処理で行う (Prepareをtargetの状態や内容から独立に保つ)。保持によりアーカイブは変わらないはずだが、ヘッダーの並びの一致を独立に確かめ、対応が崩れたまま処理しない。
- **DLLが使えないときをPrepareのFATALにする**: アーカイブを開けない場合と同じく処理対象そのものを読めない状態であり、引数・target・entriesの入力エラーとは区別する。targetとentriesに触れる前に判定し、削除0件にする。利用者が自分で対処できるよう、原因・読み込み元・必要な版を説明に含める。

<a id="rar-scope"></a>
### 受理範囲の判断

- 暗号化を全エントリでPrepareに拒否するのは「暗号化は非対応で、削除処理の前に拒否する」という製品判断による。ZIPより厳しく、FastでもZIPと差が出るが、拒否が増える側である。WinRAR 7.23の `-p` は password check を書くので、password check の無い暗号化は細工されたRARでだけ起きる。
- 作成元OS別の属性規則は、ZIPのDOS属性の規則を得られる情報に合わせて置き換えたもので、緩和は無い。UnixのmodeでZIPと違い種別0を許さないのは、Unixで作られたRARの通常ファイルは S_IFREG を持つためである。RAR4のUnix symlinkもDLLはリダイレクトとして報告した。
- 辞書サイズ: DLLは辞書サイズをPrepareで報告し、8 GiB を宣言した自作ヘッダーを拒否できた。RAR 5.0形式の辞書の最大は1 GiBで、超えるのはWinRAR 7の新しい形式を明示して作った場合だけと推定し、確保量を抑えるため暫定1 GiBとした (DLL自身の既定上限は4 GiB)。小さいファイルでは `-md1g` を指定しても縮小して記録される。内容を読まないFastにも適用するのは、[受理範囲を操作・モードから独立に決める](#zip-limits)ためである。
- 分割 (ボリューム) をopen直後・列挙の前に拒否するのは、DLLが第1巻・途中の巻を列挙し終えられないためである (2026-10-09の観測、7.23。第1巻は次の巻へ続くエントリの `RAR_SKIP` が `ERAR_EOPEN`、途中の巻は `RAR_OM_LIST` では最初のヘッダーの読み取りが `ERAR_EOPEN`。最終巻・Solid・非分割アーカイブ内の分割フラグは列挙できる)。列挙の後に拒否すると、巻によって `ARCHIVE_UNREADABLE` になり拒否のコードが入力で変わる。entries・targetより先に報告され、`analyze` の件数を出さない点は列挙中の上限超過 ([上限](spec/rar.md#limits)) と同じである。Solidとエントリの分割フラグは列挙できるので、従来どおり手順6で拒否する。
- 件数・名前長・メタデータ総量を列挙中に検査して手順2で拒否するのは、長い名前を大量に持つRARで、拒否する前に大量のメモリを保持しないためである (名前のバッファは65,536文字で、そのまま保持すると10万件で約13 GBになる計算)。総件数を数えながら終端まで列挙して手順6で拒否する案は、ZIPと同じ段階・正確な件数になるが、稀な入力のための処理が増えるので採らなかった。ZIPの検査時点はRARに揃えない (`ZipArchive` がCentral Directory全体を読み込んだ後なのでメモリの利点が無く、entries・targetの入力エラーとの優先順位と `analyze` の出力が変わるだけである)。判定の計算は共通 ([EntryBudget](../src/Unextract.Core/Zip/EntryBudget.cs)) で、呼ぶ時点だけが形式で異なる。128 MiBは仕様上の計算値で、実メモリ使用量の保証ではない。
- 一覧用・内容読み取り用のハンドルのcloseの失敗に新しいコードを設けず `internal_error` (削除0件) にするのは、既存の終了処理の失敗の扱い ([資源の寿命](ARCHITECTURE.md#lifetimes)) に従えば足り、RAR仕様にcloseの文言を足さずに済むためである。
- 一覧用のopenを `RAR_OM_LIST_INCSPLIT` にするのは、`RAR_OM_LIST` が前の巻から続くエントリ (SPLITBEFORE) を黙って列挙から除き (2026-10-09の観測。非分割アーカイブ内のそのエントリも同じ)、`ENTRY_SPLIT` を検出できず、内容読み取り用 (`RAR_OM_EXTRACT`) の並びとも食い違うためである。
- 先頭署名の確認は構造の解析ではないが、DLLはSFXも開くので、SFXを非対応にするために必要な唯一の独自判定である。
- RARとして扱う入力を拡張子 `.rar` で決めるのは、`.rar` 以外の入力の経路を `ZipArchive` のまま一切変えず (RAR署名で始まりZIPとしても読めるファイルを含む)、GUIの検索 (拡張子) と一致させるためである。代わりに `.cbr` など他の拡張子のRARは扱わない。
- ハッシュを持たないファイルエントリを拒否するのは、内容検証の補助検査 (基準5) を常に成り立たせるためである。WinRARはファイルに常にCRC32かBLAKE2を記録するので、細工されたRARでだけ拒否が起きると推定している。
- DLLの読み込み元をCLIと同じフォルダーの固定名だけにするのは、引数・設定・GUIの規定を増やさず、GUIがCLIの位置を固定する ([GUIの理由](#gui-platform)) のと同じく、利用者が置く場所を1か所に決め、そこにある照合済みの版だけを使うためである。

<a id="rar-in-process"></a>
### プロセス内のDLLを受け入れる理由

UnRAR.dllはC++のネイティブコードで、WinRAR 7.23の更新履歴にも、細工したRARの展開で展開先の外を指すsymlinkが作られる問題などの修正がある。unextractは `RAR_TEST`・`RAR_SKIP` だけを使い、展開先を渡さないので、展開経路 (パスやリンクの作成) の問題は受けない。作業ディレクトリへの書き込みは観測されなかった。1ビット破壊1,500回では異常終了は無かったが、ほとんどがハッシュ・CRCで検出されたもので、展開器の深い経路の網羅性は低く、堅牢性の根拠として重く扱わない。

それでも解析器のメモリ安全性の不具合は、削除用ハンドルを扱うプロセス内で起こり得る。同じ利用者のトークンで動く補助プロセスは、偶発的なメモリ破壊が比較の状態を壊すことは防ぐが、任意コード実行に対しては境界にならない (乗っ取られた子は利用者のファイルを直接消せる)。攻撃に対して隔離するには権限を下げた子プロセス (制限付きトークン、AppContainerなど) が要り、Win32の使用範囲とプロセス管理・通信の実装が大きく増える。増えるリスクは利用者がそのRARをWinRARで開くときと同じ種類 (同じ公式コードの、より狭い経路) であるため、MVPではプロセス内で使い、リスクを[限界](spec/rar.md#limitations)に明記して受け入れる製品判断とした。敵対的なアーカイブを想定に含めるなら隔離を再検討する。

<a id="cli-modes"></a>
## CLIとモード

利用者の中止と検証・処理の失敗を呼び出し側が区別できるよう、[終了状態](spec/cli.md#arguments)を分ける。DELETE_FAILEDがあれば、内容は未確認でも要求された削除を完了できなかったため、完走しても成功とはしない。

<a id="confirmation"></a>
### 確認時点と旧CLI拒否

[確認](spec/cli.md#confirmation)はPrepare後・最初のエントリ前。最初の候補を見つけてから確認すると、そのハンドルを長時間保持するか1件だけ閉じて再比較する必要があり、逐次方式の目的を壊す。削除件数が結果的にゼロでも最大件数で確認する。

[旧CLIの拒否](spec/cli.md#arguments)は、旧形式を黙ってdeleteに割り当てて全件確認から部分削除へ意味を変えないため。dry-runだけaliasで残すとそれを外した意味が曖昧になり、旧全件方式を残すと二重比較が戻る。入力エラーと移行案内なら誤操作時も非削除となる。S03/P05/K02/K04/X20/X25、CLI形・確認時点を変えるときに再確認する。

<a id="entries-display"></a>
### exactなEntryと転記の例外

[entries](spec/cli.md#entries)は範囲を狭めるだけで、ID・ハッシュ・分類入りのplanは現在状態の検証に寄与せず許可証に見える。trim/glob/コメント/区切り補正を設けず規則を一つにする。BOM付きUTF-8は既存ツールとの実用上の互換性を保ち、UTF-16は明確に案内して拒否する。端末保存形式はM13未実測である。

[表示](spec/cli.md#result-lines)はEntryをそのまま転記できるようにする。バックスラッシュを二重化すると一致しない。危険な書式文字だけは安全にエスケープして転記不可を示す。状態列だけを固定幅にするのは長名と全角文字でTargetが遠くなるのを避けるため。Targetは確認用の対応位置で入力ではなく、MISSINGでも同じ列の意味を保つ。L14/L15/O09/O10/X23、表示・encoding変更時に再確認する。

<a id="fast"></a>
### Fastを単一の内容非読取差分にする

[モード契約](SPEC.md#modes)はSAME_SIZEという名前で内容一致を誤認させない。CRC中間モードやFast専用の復元検査は内容を読む経路と検証の組合せを増やし、Strictの保証にも届かないため採らない。[安全性共通の理由](#sharing-limits)により最終確認も残す。

[ヘッダーの警告](spec/cli.md#warning)を標準出力に書くのは、結果一覧だけを保存した場合にもFastの結果であることを残すためである。

C15/R09/T17/S06/S07/X26は非読取と同サイズ内容違いを回帰する。CRC計算自体の直接観測とbody非読取からの間接確認は[TESTING](TESTING.md#reproduction)で区別する。モード分岐・比較経路変更時に再確認する。

<a id="machine-output"></a>
### 機械可読出力と実行ログ

以前は「JSON出力・ログファイルは設けない」としていた。GUIなどのフロントエンドが日本語の文言・エスケープ・並べ替えを解析せずに済むよう、opt-inの[機械可読出力](spec/machine-output.md)で既存の概念 (エントリ、状態名、要約の件数、FATAL/STOPの原因) だけを公開する。進捗・候補サイズの合計・エントリごとのTargetパス・GUIのグルーピングは利用側が受信件数と`length`から求められ、CLIにない概念を持ち込まないので出さない。GUIとはプロセス境界で接続し、Core/Windowsを直接参照させない (内部型への結合とプロセス分離の喪失を避ける)。

フラグ名を`--jsonl`にしたのは、出力が単一のJSON文書ではなくJSON Linesであり、`--json`では全体を1文書として読む利用側を誤らせるため。`--format jsonl`は形式が1つしかない現状では値の検査と既定値の規定が増えるだけで、値なしの`--fast`・`--yes`とも揃わない。別の形式が必要になれば別のフラグで足す。

機械モードから確認の省略を推論せず、`--yes`なしを入力エラーにする。出力形式と安全上の確認は直交する契約であり、確認プロンプトはstdoutに出るためJSONを壊す。非対話の中止 (終了コード2) に任せるとstdinが端末かどうかで挙動が変わる。

完了境界は開始通知やheartbeatを足さず、`run`の有無と「`entry`を書いてから次へ進む」というレコードの意味で定義する。開始通知を足してもクラッシュ時に処理中の1件が不明になることは変わらない。書き込みの失敗を検出したら先へ進まないのは、記録できないまま削除を続けないためである。stdoutの読み手の消失を検出できることは保証しない ([未確認](OPEN_ISSUES.md#observations)) が、検出できなくてもCLIはその実行で承認された`--entries`の範囲を各エントリの再検証つきで処理するだけなので、誤削除にはならない。

実行ログ (`--log`) は「何を削除したか」を後から確認する最終手段で、監査やジョブ再開のためではない。GUIが受け取ったstdoutを自分でファイルへ写す方式はGUIのクラッシュ後の結果を残せないため、CLIが同じレコードを同じバイト列で書く。ログ専用の形式を作らないので、読み方は機械出力の完了境界の規則だけで足りる。ログを先に書いてからstdoutへ出すので、通常配送で利用側が見た結果はログにある ([ログ失敗時の例外](spec/machine-output.md#log))。プロセスの異常終了ではOSに渡したデータは失われないため、1件ごとのFlushFileBuffersは求めず (10万件規模の性能を優先)、電源断への耐性は保証しない。新規作成だけにするのは過去のログやZIP・entriesを上書きしないため。デバイス (`NUL`・`CON` など) やパイプは`CreateNew`でも開けるが後から確認できる記録が残らないため、ログとして受理しない ([実行ログ](spec/machine-output.md#log))。判定は開いたハンドルの種類 (ディスクか) で行い、予約名や`\\.\`形式などのパス表記の列挙には頼らない。機械モードのdeleteに限るのは、人間向け出力との組合せで`outcome`が増えるのを避け、目的に必要な範囲に留めるため。

複数の出力先へ終端のresultを同時には確定できず、一方への配送後に他方やログのcloseが失敗し得る。そこで既に書いたresultを変更・重複させず、実プロセスの終了コードを優先する ([終端失敗](spec/machine-output.md#result))。実行途中にログが失敗した場合は、停止の原因をまだ書けるstdoutへ残すため、そのOUTPUT_FAILEDのresultだけはログと同一配送の例外とする。

GUIの終了・クラッシュ時に実行中のCLIを強制終了しない。CLIは承認済みの範囲を再検証つきで処理するだけで、強制終了は処理中の1件を「不明」にするだけで何も守らない。一方で出力の失敗を検出すればCLIは止まるため、完走は保証しない。

出力をASCIIだけにするのは、コンソールのコードページに依存せず、危険な文字を生で出さず、JSONの可逆なエスケープで`name`をそのまま`--entries`へ戻せるようにするため。生成にreflectionベースの`JsonSerializer`や属性によるフィールド名指定を使わず`Utf8JsonWriter`で各フィールドを明示的に書くのは、reflection不使用の規則との関係を曖昧にせず、フィールド順と省略条件をコード上で読めるようにするため。版を全レコードに付けるのは、`run`がない入力エラーでもどの行も単独で解釈できるようにするため。GUIと同梱するので、複数の版を保守する版指定フラグは設けない。Fast警告の代わりに`run.mode`を必ず出すのは、[上の理由](#fast)の「保存した出力からFastと分かる」目的を機械出力でも満たすため。

J系列が回帰を担う。出力経路、確認、終了状態、ログの書き込み順序・作成条件を変えるときに再確認する。

<a id="gui"></a>
## GUI

契約は[GUI仕様](spec/gui.md)、配置は[ARCHITECTURE](ARCHITECTURE.md#gui)。ここには方式・画面構成・検証方式を変えるときに必要な判断だけを置く。

<a id="gui-platform"></a>
### WPFとCLI子プロセス

GUIの責務は、Windows専用のローカルな逐次ジョブについて、セッションを持ち、CLIの子プロセスを1本ずつ所有し、終了要求を待機に変えることである。次の比較 (2026-10-08、設計評価であり代替方式の試作・実測ではない) でWPFを選んだ。既存コード・テストへの投資は採否の理由にしていない。

| 方式 | 評価 |
|---|---|
| WPF | 単一の.NETアプリがセッションとCLIを所有し、OSのフォルダー選択・終了要求を直接扱える。UI用の別ランタイムや通信境界が要らない。Style/Template・仮想化一覧で情報設計を統一できる。採用 |
| WebView2内のWeb UI (Blazor Hybrid等) | CSSによるレイアウトとWeb部品のテストは使えるが、WebViewランタイムの配布・更新、画面側の障害、ホストとの境界が増え、Web部分のテストだけではホスト・OS操作・終了待機を検証できない。有力な代替 |
| 外部ブラウザー + ローカル.NETホスト | ローカル接続の認可、複数タブ・再読込・切断とセッションの対応、ブラウザーを閉じることとアプリ終了の区別、ホストの配布が加わり、削除中の終了待機とセッション寿命を分かりやすく保てない。不採用 |

再設計の試作では、作業一覧と詳細欄の構成が標準のListBox・Grid・GridSplitter・ContextMenu・Style/ControlTemplateだけで組め、独自描画や複雑な独自コントロールが要らず、性能測定 ([TESTING](TESTING.md#gui)) でも応答の見通しが立ったため、Web案の試作比較へは進まなかった。WPFの制約を回避するために独自描画や複雑な独自コントロールが必要になる、または品質・応答性を満たす見通しが無くなった場合は、Web案で同じ場面を試作して比較し直す。方式を変える場合も、CLIの子プロセス境界と[GUI仕様](spec/gui.md)は維持し、セッション・承認済みバッチ・CLI起動をホスト側に一元化して画面側へ削除可否の判定を複製しない。任意のコマンドやファイル操作の公開、外部コンテンツの実行、再読込によるdeleteの再送を防ぐ設計と、終了・切断・画面側クラッシュの試験を加え、配布とUI E2Eも新方式へ書き直す。終了の意味・対応環境・保存範囲など契約を変える場合は製品判断が要る。

DLL参照でなくプロセス境界にする理由と、終了・クラッシュ時にCLIを強制終了しない理由は[機械出力の理由](#machine-output)による。テスト用の `MachineProcess.Dispose` の強制終了方式を製品のrunnerへ流用せず、プロセスの所有者を1か所にしてdeleteへKillが届く経路を作らない。CLIの位置を配置先の `cli\unextract.exe` に固定し、PATHや作業ディレクトリへフォールバックしないのは、機械出力が版指定フラグを持たず同梱を前提にしている ([版](spec/machine-output.md#versioning)) ため、同梱した版以外のexeを削除に使わないようにするためである。

<a id="gui-layout"></a>
### 画面構成の判断

画面構成は契約ではなく ([利用品質](spec/gui.md#quality))、次は再設計で採った判断である。構成を変えるときは、これらが防いでいた問題が再発しないかを[画面確認](TESTING.md#gui-review)で確かめる。

- 入れ子のExpander (Archive → Target → 結果一覧) をやめ、Archive行の後にそのTarget行を並べた1つの仮想化一覧にした。旧構成では有限高の一覧の中に別の一覧があり、内側をスクロールしないと結果が見えず、長いパスで横スクロールになった。無制限の入れ子スクロールは仮想化も無効にする。
- 閲覧対象1件の詳細欄を分け、結果一覧・診断・操作・操作できない理由を集めた。行は状態バッジ・パス・要約だけにして、長いパスは折り返し、全文は詳細欄の読取専用テキストでキーボードからも選択・複写できる。閲覧対象と一括選択を別の状態にしたのは、閲覧・絞り込み・行の再生成が削除対象を変えないようにするため。
- 行はキーボードの1停止位置 (矢印で閲覧、Spaceで選択) とし、行内のチェックはフォーカスを取らない。モードのラジオも1停止位置。Tab順は宣言順で視覚順に合わせ、`TabIndex` の数値指定に頼らない (右寄せ配置で視覚と逆になった実例がある)。
- 小さい領域で一覧と詳細を切り替える案は採らなかった。1920×1080を200%で使う論理作業領域 (約960×516) でも幅は左右分割に足り、制約は高さだったため。作業一覧と詳細欄に最低限の高さ (200px。230pxでは200%相当の削除中に状態欄が押し出された) を確保できない寸法では、ウィンドウ全体を縦スクロールにする。選択の4操作を1つのメニューにまとめ、要約を1行にしたのも高さを確保するため。
- 削除は危険色で解析から離し、既定の操作にしない。削除確認は警告 → Fast → 数値 → 隠れた選択 → 全件の一覧の順で、ボタンを常に見える位置に固定する。対象0件でも同じウィンドウで理由の一覧を示す (メッセージボックスは件数が多いと画面に収まらない)。
- 状態バッジは固定幅にした (仮想化で再利用される行で文字が欠けた)。最小幅で折り返すと1文字ずつになる説明は1行に省略し、全文を別の手段でも示す。
- 意図して残した点: 200%相当では詳細欄の上部 (パス・状態・操作) を優先し、結果一覧は詳細欄のスクロールで見る (最低高を持つので操作は失われない)。最小寸法の実行中はウィンドウ全体のスクロールが出る。同名のZIP・Targetを識別するため、行のフルパスは省略せず折り返す。

<a id="gui-entries-limit"></a>
### entries上限を起動前に確かめる理由

ZIP側のメタデータ上限は「名前のUTF-16バイト数 + 1エントリ128バイト」の合計128 MiB ([ZIP上限](spec/zip.md#limits))、entriesはUTF-8のファイル全体128 MiB ([entries](spec/cli.md#entries)) で単位が違う。例えば約65,000件・各約900 UTF-16単位でほぼ3バイトのUTF-8文字の名前なら、ZIP側は約125 MBでもentriesは約176 MBになり得る (契約値からの計算で、実ZIPでは再現していない)。CLIの起動後の入力エラーに任せると、削除が始まっていなくても起動したことで `delete` 実行済みになり再解析が必要になる。起動前に説明すれば不要な再解析を避けられる。自動分割は「1 Target = 1ジョブ」・ログ番号・途中停止と再実行の状態を変え、CLI上限の拡張は既存契約の変更になるため採らない。この検査は転送形式の制約であり、安全性の判定ではない。

<a id="gui-state"></a>
### 状態・保存・大量データ

- 解析結果を削除の許可証にせず、ZIPの同一性の固定やGUI独自のハッシュも加えない。削除可否はCLIのPrepareと再検証、異常時の読み方は完了境界に任せ、GUIは受信内容に表れる変化 (`entries_total`・`index`) だけを結果不明へ倒す。
- CLIを起動した (成否不明を含む) 時点で `delete` 実行済みにするのは、起動後は何が削除されたかを解析結果から言えないため。確実な未起動と起動前の準備失敗だけが、解析結果をそのまま再利用できる。
- 設定ファイルは小さいJSONを直接書き、一時ファイルからの置換をしない。置換には削除・改名APIが要り、`src/` のパスベース削除・改名の禁止 (例外はentriesの1か所) に反するため。破損時は既定値で起動するだけで、失うのは検索ディレクトリ1件である。
- WPFのUI仮想化は画面要素を減らすが、複数Targetの全結果のメモリ量は減らさない。結果はメモリに保持し、一覧はフィルタ後のindexだけを持って行を要求時に作る。実用上足りなくなっても、結果の無断の切り捨てや保存DBを加えず、測定結果とページ表示などの妥協案を製品判断に回す。

<a id="gui-ui-tests"></a>
### UI E2Eの方式

配布形態の `unextract-gui.exe` を別プロセスとして起動し、FlaUI UIA3とxUnitでUI Automation経由で操作・観測する。GUIのプロセス内に入らず、製品はFlaUIを参照しないので、配布物そのものと実際のOS操作 (フォルダー選択ダイアログ、終了要求) を検証できる。STA上のView・バインディングのテストとVMの状態テストは役割が違い、置き換えない。PlaywrightはWPFのネイティブ画面を操作できないので選ばない (Web UIへ変えた場合は再評価し、ホスト・実CLI・OS操作の検証は別に残す)。画像差分の自動合否判定は採らず、画面写真は実装者が開いて評価するための資料とする。テスト技術は実装方式に従属し、FlaUIや既存テストのために方式を固定しない。

- テスト用データルート: 2026-10-08の確認 (.NET 10、Windows 11) で、`Environment.GetFolderPath(LocalApplicationData)` は `LOCALAPPDATA` 環境変数を変えても切り替わらなかった。環境変数だけではテストを利用者のプロファイルから隔離できないため、合成ルートだけが読む専用の環境変数で設定とログの保存先を切り替える。誤設定で利用者の設定・ログを書かないよう、通常の保存先へフォールバックせず起動を中止する。entriesの一時ディレクトリは `TMP`/`TEMP`、CLIは配置の差し替えで隔離でき、製品に追加の仕組みは要らない。
- opt-in: `IsTestProject` を条件付きで `false` にしたxUnitプロジェクトは、solutionの `dotnet build` ではビルドされ (警告ゼロの対象)、`dotnet test <sln>` では実行されず、opt-inのプロパティ付きのプロジェクト指定でだけ実行される (同日に確認)。対話デスクトップを要し人の操作と干渉するテストを、`dotnet test <sln>` とCIから外し、[標準の検証](TESTING.md#verify)の最後の段だけで実行するため。
- 偽CLI: 解放ファイルを待つことで「実行中」を決定的に作り、固定sleepに頼らない。異常出力 (途絶・未知の版・`DELETE_FAILED`) も偽CLIで到達させ、写真だけで確認済みにしない。偽CLIの正常系の出力は同じfixtureでの実CLIの出力と比較し、ずれを防ぐ。
- 機能テストの合格は完成の一部でしかない。機能的なUI E2Eが通った後の実端末の確認で、GUIとして実用的でない点が残った経緯がある。そのため画面を変える実装者が実際の画面を見て評価・改善し ([画面確認](TESTING.md#gui-review))、人間の確認は改善後の最終受入 ([M14](MANUAL_TESTS.md#m14)) とする。

<a id="verification"></a>
## 検証の構成

- [標準の検証](TESTING.md#verify)は、同節に定める文書・コメントだけの変更を除き、固定の段を毎回すべて実行する。実行者が変更内容からテストを選ぶ・省く運用は、選び方の誤りで回帰を見逃しやすく、「〜を変えたら〜も実行」の規則が増え続けたので採らない。全段で約4〜5分 (うちUI E2E約3分。2026-10-09の開発機) で、選ぶ判断より安い。
- UI E2Eはローカルの標準の検証に含め、CIでは実行しない (2026-10-09の決定)。hosted runnerの対話デスクトップ・解像度・拡大率への対応と散発的な失敗の調査に見合わず、エージェントがローカルで失敗の確認・修正・再検証を素早く繰り返せることを優先した。1回の失敗も不具合として扱い、再試行で合格にしない。連続N回の成功を求める方式は検出力が弱く時間だけを使うので、代わりに失敗時の診断 (画面・UIAの木・偽CLIの記録) を残す。
- fixtureはテストの終了後に成功・失敗を問わず削除する ([fixture](TESTING.md#fixtures))。失敗時に残す方式は蓄積 (以前は約3.9GB) と所有の曖昧さを生むので採らず、診断はテスト出力と結果ディレクトリに残す。次の実行の開始時の一括削除は、並行する別の実行のfixtureを消し得るので採らない。
- 層の重複のうち、削ると検出できなくなる種類があるものは残す。
  - E2Eを通常buildとpublish版で2回実行する: 単一ファイル版に固有の失敗はpublish版でしか検出できない。
  - Core・WindowsのStrict/Fast × analyze/delete: Fast版は、モード分岐の後に実際に発行される呼び出しで共通安全性が弱まっていないことを確かめる唯一の手段である。
  - UI E2Eのテストごとのプロセス起動: テスト間の独立と、利用者のプロファイルを守るガードの前提である。
- 逆に、E2Eはプロセス境界の代表ケースに絞る。引数の誤りやPrepareの失敗の種類で `Program.Main` の経路は分かれない (分岐は機械モードかどうかだけ) ので、種類ごとの判定はCore・CLIに置く。
- 手動の受入は、自動テストで判定できない見え方・使い勝手・利用者の導入手順だけにする ([手動に残す理由](MANUAL_TESTS.md#manual-purpose))。ConPTYからは端末が描き直した差分しか得られず、「進捗と結果行が崩れずに読める」の判定には端末のモデルが要るので、M05は自動化しない。
- [中断時の表示と実削除](spec/cli.md#interruption): 結果行はハンドルを閉じた後に書く (J07・J13の契約) ので、強制終了では最後の結果の次の1件が表示されずに削除され得る (2026-10-09の決定で、この差を現在の動作として明文化した)。結果行をcloseの前に書く案は契約を壊し、差も無くならない。Ctrl+Cを製品で処理して一致させる案は、強制終了・クラッシュでは差が残り、GUIはCtrl+Cを送らないので効果が小さく、中止の状態を保守し続けるコストに見合わないので採らない。

<a id="structure"></a>
## 実装構造

[コード配置](ARCHITECTURE.md#dependencies)はCoreをWin32から分離し、同じ解決・検査・比較を両入口で共有する。安全性の重複実装を避け、ハンドル種別と失敗の意味は呼び出し側で明示する。Fast専用の層・クラス・抽象・状態・API・ハンドル構成を作ると共通安全性を監査しにくくなるので追加しない。

RARも同じ考えで、専用のAnalyzer・Deleter・判定パイプラインを作らない。既存の型名 (`ZipEntryInfo`・`ValidatedZipEntry`・`ZipEntryRef`・`IZipContentProvider`) は[アーカイブの読み替え](SPEC.md#archive-terms)により「アーカイブのエントリ」の意味で使い、改名しない (差分とテストの書き換えが増えるだけで安全性に寄与しない)。RARの内容は `IZipEntryContent` を作り直さず別の押し込み型のインターフェース (`IRarEntryContent`) で渡し、ZIPの経路とテスト用の偽物を変えない。DLLのコールバックを別スレッドでストリームに変換する方式は、同期の押し込みで足り、スレッドと例外の境界を増やす (DLLのエラーの状態もプロセスで1つ。[DLLの使い方](#rar-dll-usage)) ので採らない。

global.jsonは観測基盤とビルドSDKを合わせるため固定し、同じ機能帯のパッチ更新を許す。設定の正本はglobal.jsonであり、変更時はC/Z回帰でruntime観測を再確認する。配置変更時は依存方向とanalyzeの型に削除能力がないことを確認する。
